#### 1.1.1 ⭐ 量化口径（2026-09-18 定 · 用户拍三条）

**载体（两层，⛔ 不改）**：个体 ＝ `UnitController.IndividualHappiness` **int 0-100**（`UnitController.cs:102`）；王国 ＝ 个体**算术平均**（`HappinessSystem.cs:154`），桶缺失**回退 50**（`:34`）。

**⚠️ 现状公式的三条硬缺陷** —— ⭐ **是"式子的形式"错了，不是数值没调好**（实读 `HappinessSystem.cs:224-232`）：

```
h = happinessBase(50) + 饱食(≤30) + 有房(20) + 教堂(≤100) + 医院(≤100) + 食品(10) − 税负(≤20)  → Clamp(0,100)
```

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | ⭐⭐ **加法式饱和** —— `50 + 30 + 20 = 100` **已顶格** ⇒ 教堂／医院／食品品质在"饱食满 ＋ 有房"时**完全不生效**（全被 clamp 丢弃）⇒ **因子的相对轻重实际失效** | `:203-232` |
| 2 | ⭐ **六个字段里两个是死参数** —— `happinessSatietyWeight(0.4)`／`happinessTaxWeight(0.1)` **全库零消费者**；在用的四个是**当"满值点数"用**（`Weight × 100` ⇒ 15/15/10/20 点）⇒ **名实不符** | `KingdomConfig.cs:67/71` |
| 3 | ⭐ **权重和 ＝ 1.10** —— `0.4+0.2+0.15+0.15+0.1+0.1` ⇒ 说明**当初就是按"加权平均"设计的（权重应和为 1），却实现成了相加、且未归一化** | 同上 |
| 4 | **同类语义两套量纲** —— "有房住"是**布尔**（房容 ≥ 人口就给满 20，不看覆盖多少）vs 教堂／医院是**计数累加 ×15** | `:203-207` |
| 5 | `50` 写在**三处**且无共享常量 —— `happinessBase`／回退 `50f`（`:34`）／出厂值（`UnitController.cs:102`） | — |

**✅ 新公式（归一化加权平均）**

```
H  = Σ wᵢ · fᵢ                 （fᵢ ∈ [0,1]，Σw = 1）
H ×= (1 − 0.2 × 税负)           （税负作乘法惩罚）
个体幸福 = round(H × 100)     → 仍是 int 0-100
王国幸福 = 个体算术平均        → 仍是 float 0-100
```

⭐ **参数零改动**：把税负的 `0.1` 从加权池**移去做乘法惩罚**后，剩下五项 `0.4 + 0.2 + 0.15 + 0.15 + 0.1` **恰好 ＝ 1.00** ⇒ 现有六个参数值**全部沿用**，只是"**用对了地方**"。

**因子归一化表**

| 因子 | `f` | 相对现状 |
|---|---|---|
| 饱食 | `min(1, Satiety / feedSatietyThreshold)` | 保持 |
| 住房 | `min(1, 房容 / 人口)` —— ⭐ **覆盖率** | 布尔 → **连续** |
| 教堂／医院 | `min(1, 座数 / 饱和座数)` | 无上限累加 → **有饱和** |
| 食品品质 | 有特食／肉 ⇒ `1` | 保持 |

⚠️ **"饱和座数"这个新参数不削弱多建价值** —— 现状因饱和，实际效果**本来就是"1 座即满"**；该参数是把**隐含行为显式化并可调**（想保留多建意义 ⇒ 设 2~3，让第 3 座才满）。数值归**数值批**。

**三条定项（用户 2026-09-18 拍）**

| # | 项 | 裁定 |
|---|---|---|
| 1 | 权重和超 1 怎么处置 | ⭐ **运行时归一化（`÷ Σw`）** ⇒ 将来加因子、漏改权重**不失衡** |
| 2 | "饱和座数"参数 | ✅ **新增**（数值归数值批） |
| 3 | 税负的编法 | ⭐ **乘法惩罚** `×(1 − 0.2 × 税负)` —— 幸福 100 时满税 ⇒ 80；幸福 50 时 ⇒ 40 ⇒ **重税对低幸福打击更狠**，且天然**不打穿 0** |

**⛔ 不动的部分**：三个出口（`GetTaxCoefficient:337`／`GetPopulationGrowthFactor:352`／`GetRetreatThresholdModifier:361`）**全部是 `h/100` 的一次映射 ⇒ 一行不改**，只换 `ComputeUnitHappiness` 内部实现。`UnitSaveData.happiness` **保留不动**（虽冗余 —— `OnNewDay` 每天全量重算；动存档面不值当）。

#### 1.3.1 ⭐ 生育现状（实读 · 三层前置 · 2026-09-18）

`PopulationSystem.OnNewDay` 注释自陈「**每日结算，三层前置（全局幸福/饱食 ＋ 房屋容量 ＋ 个体冷却）**」（`:13`）：

| 层 | 条件 | 现状 |
|---|---|---|
| ① **全局** | `AvgHappiness > birthHappinessThreshold(60)` 且 `AvgSatiety > birthSatietyThreshold(50)`（`:278-279`） | ⚠️ **读的是全国平均** ＋ **概率折算**（`growthFactor = 幸福/100` ⇒ `Next(100) < growthFactor` · `:300-315`） |
| ② **房容** | `houseCapacity > PopulationCount`（剩余容量 > 0 · `:273-274`） | ✅ 硬前置（房屋满 ＝ 禁止生育） |
| ③ **个体** | `LastBirthDay + pairCooldown > day` 剔除（`:296`） | ✅ 个体冷却 —— ⭐ **现状唯一的"个体"环节** |

**触发链**：**日界** ＋ 全局倒计时门 `BirthCooldownDays`（`:266-267`，未到直接 return）⇒ 条件不满足 **重置冷却待下轮**（`:283`）⇒ 满足则从池（`Resident`／`Worker`／`Porter` · `:294-295`）**抽 2 人** ⇒ **生 1 小孩** ⇒ 父母记 `LastBirthDay`（`:325-326`）。
⭐ 种子化：`pairRng = new Random(map.seed ^ (day × 7919))`（`:312` · 与 AI 轨同族公式）⇒ **同 seed 同 day 恒复现**。

**⭐ 速度实读（本轮 · 回答"一天抽几次"）**

| 参数 | 值 | 说明 |
|---|---|---|
| `birthPairCooldownDays` | **10** | ⭐ **实际生效** ⇒ `pairCooldown = 10`（`:264`） |
| `birthIntervalDays` | 5 | 旧档占位（`KingdomConfig:27` 注释自陈"**已被 `birthPairCooldownDays` 对齐取代**"） |
| `birthCooldownDefault` | 5 | 全局门**初值**（`:45`／读档 `:578`） |
| `birthHappinessThreshold` / `birthSatietyThreshold` | 60 / 50 | 门槛（注释写"**整体**幸福／**平均**饱食"） |

**机制**：`BirthCooldownDays--` ⇒ `>0` 直接 return（`:266-267`）；**方法末尾无条件重置** `BirthCooldownDays = pairCooldown`（`:343`）⇒ ⭐ **每 10 天最多 1 个小孩**（满速 ＝ **0.1 人/天**）。

⇒ ⛔ **不是"一天一个"，是"十天一个"** —— 现状人口增长**很慢**。

**✅ 门槛个体化（已定 · 用户 2026-09-18）**

```
候选池 ＝ { 成年居民 且 幸福 > 60 且 饱食 > 50 且 不在个体冷却 }
```
⇒ ⭐ **一步解三件**：① **生育绑个体**（用户原意）② **「幸福低的后果」** —— 幸福低／吃不饱者**进不了池** ⇒ 人口自然放缓（**不需要额外惩罚机制**）③ 概率折算段可删（门槛个体化后，它成了同一件事的第二遍表达）。

**⏳ 待拍｜⭐「生育速度」＝ 一个参数（用户 2026-09-18 提出）**

⚠️ **根因（用户判断已核实 · 参数语义挪用）**：`birthPairCooldownDays`（`KingdomConfig:30` 注释原文「**单对 10 天冷却**」）被**同时**用作**两个层级** ——

| 用途 | 位置 |
|---|---|
| ✅ **个体冷却**（本意） | `:296` `u.LastBirthDay + pairCooldown > currentDay` |
| ⛔ **全局门**（被挪用） | `:283`／`:343` `BirthCooldownDays = pairCooldown` |

⇒ ⭐ **把"一对的冷却"当成了"全王国的冷却"** ⇒ 结果：**每 10 天全场最多生 1 个**。

**✅ 方案：新增「生育速度」单一参数，并把各参数归位**

```
新增：birthRatePerDay（float · 期望出生人数／天）  ← ⭐ 唯一的"速度旋钮"

每天（日界）：
  1. _birthAccumulator += birthRatePerDay                 // 小数速度用累积器平滑
     int quota = ⌊_birthAccumulator⌋;  _birthAccumulator -= quota;
  2. 候选池 = { 成年居民 且 幸福 > 60 且 饱食 > 50 且 不在个体冷却 }
  3. 实际出生数 = min( quota , ⌊候选池/2⌋ , 房屋剩余容量 )
  4. 逐对抽取 ⇒ 每对生 1 小孩 ⇒ 两人记 LastBirthDay
```

| 参数 | 归位后的职责 |
|---|---|
| ⭐ **`birthRatePerDay`**（新） | **速度** —— 每天最多生几个（**小数**用累积器平滑 ⇒ `0.5` ＝ 每 2 天 1 个） |
| `birthPairCooldownDays` | ⭐ **回归本意**：**只做个体冷却**（这一对多久内不能再育） |
| `birthCooldownDefault` | ⛔ **退役** —— 全局门取消（其"防同日连爆"作用由 `quota` **天然承担**） |
| `birthIntervalDays` | ⛔ **删**（旧档占位） |
| `birthHappinessThreshold`／`birthSatietyThreshold` | **门槛**（不变） |

⇒ ⭐ **旋钮从 5 个收到 3 个**：**速度** ＋ **两个门槛**（＋ 个体冷却）。
⇒ **速度是上限，池子／房容决定能否达到** —— 池子大 ⇒ 顶到速度；池子小 ⇒ 生不到（⭐ **这才是门槛个体化的意义**）。
⇒ ⚠️ **房容仍是硬上限**（生满即停）⇒ 人口不会无限涨，**必须建住房**。
