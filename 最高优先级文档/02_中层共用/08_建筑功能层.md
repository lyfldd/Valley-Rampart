## 一、这一层是什么

**判定依据**：**驱动方是不是 NPC**。

| | 谁驱动 | 例子 |
|---|---|---|
| **L1 交互层**（`05`） | **要 NPC 参与** —— 走到、耗时、改数据 | 采集、搬运、建造、修复 |
| **L1.5 建筑功能层**（本文） | ⭐ **建筑自己** —— **没人也长** | 农场产粮、矿洞副产水晶、国库累积、裂隙刷怪、箭塔自动开火 |

⇒ **两者性质不同**：交互是"一次动作"，功能是"一条持续的状态机"。

**与 L1 的交界**（两边都要说清）：

| 场景 | 归哪层 |
|---|---|
| 农场**自动**每秒产粮入自仓 | **L1.5**（无 NPC） |
| 工人**去**农场仓把粮搬走 | **L1**（有 NPC ⇒ 任务层派） |
| 铁匠铺**等**矿石到齐才能加工 | **L1.5**（它自己等） |
| 工人**把矿石搬**进铁匠铺 | **L1** |
| 箭塔**自动**开火 | **L1.5 触发 → L1 战斗类（`07`）执行** |

⇒ ⭐ **一句话交界**：**L1.5 是"建筑自己在做什么"，L1 是"人来对它做什么"。**

## 三、收敛方案：三层结构（你来定的是第一层，我补后两层）

### 3.1 三层

```
① 类型 ID       building_mine / building_blacksmith / building_gate      ← 命名式，唯一
② 能力声明      provide: [craft, store]         ← 复用 05 的能力机制
③ 组件绑定      components: [comp.producer, comp.storage]   ← 数据行声明挂哪些
```

### 3.2 为什么是三层而不是一层

| 层 | 回答 | 变化频率 |
|---|---|---|
| **① 类型 ID** | "这是**哪一栋**" | 加一栋新建筑 ⇒ **加一行** |
| **② 能力声明** | "它对**外界**能做什么" | 加一种对外能力 ⇒ **加一行** |
| **③ 组件绑定** | "它**内部**跑什么逻辑" | 加一种内部行为 ⇒ **写一个组件 + 填栏** |

⇒ **分三层的原因**：`②` 是**给外界看的**（交互配对、AI 决策），`③` 是**内部实现**。混在一起就会出现"外界要读你的实现细节"（今天的 `isBlacksmith` 就是这样：**AI 靠布尔去猜它产什么**）。

### 3.3 收敛后的挂载流程（替代 2.2 的 if 链）

```
Place(building_blacksmith)
  └─ 读数据行
       ├─ provide:    [craft, store]
       ├─ components: [comp.storage, comp.craft]
       └─ requiresWorker: 2
  └─ 遍历 components ⇒ 逐个从【组件注册表】取类 ⇒ AddComponent
```

⇒ **`AttachComponents` 的 if 链整段消失** —— 变成"遍历列表"。
⭐ **D864**：遍历已落地。`comp.castle_core` 仍看运行时来源，裁留下。`comp.rift` 已删（D868）。

### 3.4 收敛后的 tick 流程（替代 2.3 的 if 链）

```
组件统一接口加一个可选方法：
  interface IBuildingComponent { void Init(Building); }
  interface ITickable : IBuildingComponent { void Tick(); }     ← 新增

ProductionSystem 遍历 b.GetComponents<ITickable>() ⇒ 逐个 Tick()
```

⇒ **`ProductionSystem` 的 4 个 if 整段消失**。加第 5 种组件**不用回来改它**。

### 3.5 ⚠️ 诚实修正一处（沿用 `05` 的口径）

我说过"加新东西 = 只填栏"——**只对一半**：

| 加什么 | 要动什么 |
|---|---|
| 用**已有组件**组一栋新建筑（如"大仓库"= `comp.storage` 加大容量） | ✅ **只填一行数据** |
| 加一种**全新内部行为**（如"传送门"） | ⚠️ **必须写一个组件**（行为是代码，声明表达不了） |

⇒ **声明可数据化，行为必然是代码。** 本层的价值不是"零代码"，是**把"改两处硬编码"降为"写一个组件 + 填一行"**。

## 六、判据（能力句，不写落点句）

1. **挂载数据化**：新增一栋建筑，**只改数据行**（不改 `BuildingFactory`／`ProductionSystem`）
2. **无类型 if**：`AttachComponents` 与 `ProductionSystem` **不再出现具体组件类名**
3. **能力可查**：任一建筑 ⇒ **能列出它 `provide` 的能力清单**（不读实现细节）
4. **布尔归零**：§4.1 那 **10** 个布尔**全部退役**（改为 ID／能力／数据栏／派生）
5. **死字段可见**：`InteractableType` 已删；**启动自检能报出任何"全库无人取"的栏**（`03` 的铁律）。Editor 侧审计**不算**本条（`D863`）
6. **tick 可扩展**：新增一个带 `Tick` 的组件 ⇒ **不改 `ProductionSystem`**，且**新组件确实被 tick 到**（观测读数）

### 10.5 行为规则（源 §8.3／§8.4／§8.5／§8.6／§8.2）

#### 10.5.1 防御塔目标选择（源 §8.3 ·【定案】）

- **策略 ＝ 最近目标**（每 tick 选距离最近的敌方单位）。
- **实现**：`FindNearestEnemy()` 遍历感知范围内敌方单位，按距离升序取首个。
- **切换**：当前目标死亡／脱出射程 ⇒ **重新选最近**。
- **不分兵**：每塔独立选目标，**多塔可能选同一目标**（⛔ 不强制分配）。
- ⚠️ **现行勘正**：源写「按 **x** 距离升序」＝ **1D 语义**；现行（`07` §二）＝ **世界空间欧氏圆** 判据 ⇒ 距离口径**以 `07` 为准**；`10` §八 #7 已裁 **`attack` 开火细节归 `07`**（含射程／伤害／冷却）。

#### 10.5.2 城门状态机（源 §8.4 ·【定案】）

```text
状态：Open / Closed
触发：
- 昼夜事件：夜晚开始 → 自动 Closed；夜晚结束（白天开始）→ 自动 Open
- 玩家点击：切换 Open ↔ Closed，置 playerOverride = true
冲突规则：
- playerOverride = true 时，昼夜事件不再自动切换（玩家手动控制）
- playerOverride 重置：每次昼夜事件后玩家若 5 分钟未操作 → 清除覆盖，恢复自动（占位可调）
字段：GateState（Open/Closed）／playerOverride（bool）／lastPlayerActionDay（float）
```

- ⚠️ **「5 分钟」超时重置时长** 源自标「占位可调」⇒ 列入 §10.7 未决。

#### 10.5.3 建筑摧毁时的工人处理（源 §8.5 ·【定案】）

- **决策**：建筑被摧毁时，内部正在工作的工人 **逃出、存活**（变无任务状态）。
- **实现**：
  1. 建筑摧毁逻辑扫描 `currentWorkers` 列表；
  2. 每个工人：① 清除 `WorkerTask` 状态（变 Idle）② **位置 +1 格偏移逃离**（避免卡在废墟格）③ **不死亡**；
  3. 工人逃出后可被重新派发任务。
- ⚠️ **现行勘正**：③ 的「+1 格偏移」为 **1D 语义**（单轴）；现行（`02` 空间与粒度）为 **2D 微格** ⇒ 偏移方向须走 `03` 的落点校验，⛔ 不得直接改坐标。

#### 10.5.4 训练中断处理（源 §8.6 ·【定案】）

- **决策**：训练建筑被摧毁时，**不退款，居民存活**。
- **实现**：
  1. 检测训练中居民列表（`currentTrainees`）；
  2. 每个训练中居民：① 中断训练 ② `occupation` 回退为 `Resident`（无职业）③ **不死亡** ④ **已投入资源／时间不退还**；
  3. `TrainingSystem` 加队列管理：**排队中 ／ 训练中 ／ 完成变职业 ／ 中断回退**。
- ⚠️ 「不退款」与 §10.2 的「**拆除全退**」**不冲突** —— 前者是**被摧毁**（无主动拆除动作、无退款方），后者是**玩家主动拆除**（走退还）。

#### 10.5.5 敌人对障碍的行为（源 §8.2）

- 沿轴前进 → 遇障碍（城墙／城门／拒马，且 `HP > 0`）→ **攻击该障碍** → `HP = 0` 通过；
- **城门开启时 ＝ 可通行**（不攻击）；
- **拒马阵 ＝ 一次性障碍**（被摧毁后消失，不阻挡）。
- ⛔ **时代语义警告**：源明写「本游戏为 **1D 横版**（仅 **x** 维度），城墙／城门 ＝ **硬屏障**，敌人**无法绕行**，必须破坏才能通过；**无需 A* 寻路**」⇒ 该段**整体属 1D 时代语义**（见 §10.6 #1）。**现行 2.5D 等轴开放地图下敌人可绕行**（`2_6` 寻路工具层 ＋ `2_8` AI 应用层在场）⇒ ⛔ **不得据此认定「城墙必须被破坏才能通过」**。本条**只保留**「障碍被打穿后可通过」与「拒马一次性」两条**机制性**结论。
