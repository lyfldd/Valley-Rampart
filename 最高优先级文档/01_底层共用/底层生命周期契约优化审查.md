# 底层生命周期契约优化审查

> **层级**：底层横切契约（启动／加载／存档／拆卸）
> **状态**：✅ 审查完成；⚠️ 优化口径待用户拍板；⛔ 本文不直接派发代码施工
> **审查范围**：`CoreBootstrap`、`GameBootstrap`、`LoadManager`、`SaveManager`、`TeardownManager`、`WorldLifecycle`、`GameSceneEntrance`、`GameStateManager`、`EventBus`、`ISaveable`
> **审查日期**：2026-09-28

## 一、结论

底层不是缺少设计，而是原有设计被分散在历史设计稿、修复记录和代码注释中，最高优先级目录只有归属声明，没有一份现行的生命周期总契约。

现行代码已经具备四个正确的骨架：

1. `LoadManager` 负责阶段化加载与资源门面。
2. `SaveManager` 使用 `ISaveable`、`Global → Scene` 分阶段恢复和 `ISaveableSpawner` 重建动态对象。
3. `TeardownManager` 提供场景清理、返回主菜单、进程退出三个出口。
4. `WorldLifecycle` 负责同场景清场后重建，不把跨轮残留交给业务系统自行猜测。

因此本轮不建议重写底层，也不建议把启动、存档、加载、拆卸重新拆成多个业务层文档。应该补一份**底层生命周期契约**，把现行骨架、失败语义、唯一入口和验收不变量集中起来。

### 2.2 需要优化的闭环

#### P0-1：启动时仍存在两套实例来源

`LoadManager` 的注释要求关键对象由场景显式提供，但实际仍通过 `SaveManager.Instance` 取对象；`Singleton.Instance` 在找不到对象时仍会自动创建 GameObject。于是“显式场景对象”和“隐式单例对象”仍可能分叉。

这不是立即崩溃，而是**未闭合的所有权契约**。底层必须明确：哪些对象必须场景提供，哪些允许自动创建，缺失时是报错停止还是降级运行。

#### P0-2：读档部分失败仍可能被视为成功

`SaveManager.DistributePayloads` 对单个模块的 `LoadState` 异常只记录日志并继续；只要外层没有抛异常，`SaveManager.Load` 仍可能返回 `true`，随后 `LoadManager` 进入 `Playing`。

需要改成带报告的加载结果：至少区分“必需模块失败”“可选模块缺失”“旧数据被过滤”“重建后校验失败”。必需模块失败时不能进入 `Playing`。

#### P0-3：加载阶段与全局状态没有单一真源

`LoadManager.CurrentPhase` 与 `GameStateManager.CurrentState` 是两套状态。当前 `GameBootstrap` 在读档失败后设置 `GameOver`，但回调随后仍会继续启用输入并清空入口参数（`GameBootstrap.cs:151-177`、`:108-114`）。

优化后必须有一个明确的终态：

```text
Booting → Loading → Ready → Initializing/Restoring → Playing
                                      └→ LoadFailed
```

`Playing` 只能由成功的最终校验进入；失败路径必须停止输入、保留错误结果，并禁止继续执行后续初始化。

#### P0-4：设计稿与代码的存档迁移口径已经漂移

历史 `2_11` 已写入 `MigrationRegistry`、最低支持版本和 `SaveIncompatibleEvent`，但当前代码检索不到这些实现；代码实际只有 `CurrentSaveVersion = 3`，并拒绝高版本存档（`SaveManager.cs:13-14`、`:331-340`）。

这属于**未取得实现证据**，不能继续把历史设计稿当作已实现契约。现行最高优先级口径应明确标记：迁移链和低版本显式拒载目前是“设计已定、代码未证实”。

#### P1-1：拆卸入口缺少重入门

`TeardownManager` 有 `CurrentPhase`，但没有“正在拆卸”的锁或请求去重。暂停返回主菜单、GameOver 返回主菜单、退出回调、同场景重建如果在同一帧或相邻帧重复触发，可能重复保存、重复重置或重复切场景。

至少需要 `Idle / Running / Done / Failed` 的请求状态和幂等规则。

#### P1-2：保存快照没有统一冻结点

`SaveManager.Save` 直接遍历 `_saveables` 并调用各模块 `SaveState`。当前没有底层契约规定保存期间是否暂停输入、暂停时间、暂停日结算、阻止实体注册变更，以及保存失败后是否恢复运行。

保存应有统一的快照窗口：

```text
RequestSave → FreezeWrites → Capture → Serialize → AtomicCommit → Unfreeze
```

#### P1-3：后置重建清单没有收进现行底层文档

存档设计已经规定地图先复现、再重建对象、再恢复派生数据，但这些要求仍在历史 `2_11` 中。最高优先级目录应直接引用并固定：阻挡位、单位区块登记、寻路场、LOD 热度、领土表现等都属于读档后的后置重建，不属于业务模块自由发挥。

## 三、现行底层总契约（优化后建议口径）

### 3.1 所有权

- `CoreBootstrap` 只负责 Core 单例存在性与首次 Booting。
- `GameBootstrap` 只负责 GameScene 流程编排，不直接恢复业务字段。
- `LoadManager` 是加载阶段唯一入口。
- `SaveManager` 是存档收集、原子写盘、版本门控和分发唯一入口。
- `TeardownManager` 是运行时清场、返回主菜单和退出清理唯一入口。
- 业务系统只实现 `ISaveable`／`ISaveableSpawner`，不自行决定全局顺序。

### 3.2 新建与读档

```text
CoreBootstrap
  → GameState.Loading
  → LoadManager.LoadStaticConfigs
  → ConfigsLoaded(success)
  → GameState.Ready
  → NewGame: WorldInit → SpawnInitialState
  → Continue: TeardownScene → ValidateSave → Global → Spawn → Scene → RebuildDerived
  → FinalValidation
  → GameState.Playing
```

任何一步失败都只能进入 `LoadFailed`，不能半初始化后进入 `Playing`。

### 3.3 保存

- 保存请求只能由 `SaveManager` 接收。
- 自动存档发生在 `DaySettledEvent` 之后，保留现行“先结算、后存档”规则。
- 保存期间必须明确写入冻结策略。
- 临时文件写入、替换、失败回滚必须保持原子性。
- 写档结果必须带 `slotId`、全局版本、模块数量、过滤数量、失败模块列表和最终状态。

### 3.4 拆卸

```text
StopInput
  → StopSimulation
  → OptionalSave
  → UnregisterSceneObjects
  → DestroySceneObjects
  → ResetRuntimeManagers
  → ClearRegistries
  → ClearEntryParameters
  → LoadNextScene / Rebuild
```

拆卸必须可重复调用而不会再次保存、再次广播业务事件或留下旧注册表引用。

### 6.1 设计哲学（源 §一）

| 角色 | 职责 | 谁担任 |
|---|---|---|
| **调度者** | 管加载时序、阶段化调度、加载完成通知 | `LoadManager` |
| **门面** | 对外统一取资源接口，其他系统只认 `LoadManager` | `LoadManager` |
| **子加载器** | 各自管自己的缓存与加载细节 | `UnitDataManager` / `UnitFactory` / `SaveManager` |
| **消费者** | 通过 `LoadManager` 取资源，不直接碰子加载器 | 其他所有系统 |

**核心原则**（源 4 条）：
1. `LoadManager` **不自己缓存资源** —— 各子加载器保持自己的缓存；
2. **委托转发** —— 其他系统调 `LoadManager.Instance.GetUnitData()`，由 `LoadManager` 转给 `UnitDataManager`；
3. **加载时序由 `LoadManager` 管**各子加载器何时加载，不靠 `Awake` 隐式触发；
4. **阶段化加载** —— 每阶段有明确入口与完成标志，其他系统**订阅加载完成事件再取资源**。

> ⭐ **与现行 §三.1 的关系**：源稿「`LoadManager` 是加载阶段唯一入口」与现行所有权条目 **一致**，不冲突。

### 6.2 加载阶段定义（源 §三 ＋ §四）

```text
Phase 0  Booting       引擎初始化；校验关键 Singleton 在场景中显式存在（不靠隐式创建）
Phase 1  StaticConfigs 静态配置加载（新建/读档**都要走**）
                        ├ UnitDataManager.LoadAll()      ← Resources/UnitData/ SO
                        ├ UnitFactory.PreloadAll()       ← Resources/UnitPrefabs/ Prefab
                        └ WorldSystem.LoadWorldConfig()  ← Resources/World/WorldConfig SO
                        发布 ConfigsLoadedEvent
Phase 2a WorldInit     仅新建：WorldSystem.InitializeWorld(NewGameConfig)
Phase 2b SaveRestore   仅读档：SaveManager.Load(slotId)
                        ├ Global 阶段：WorldSystem/TimeManager/DifficultyManager/WorldManager.LoadState
                        ├ Scene 重建：UnitFactory.SpawnFromSave（ISaveableSpawner）
                        └ Scene 恢复：单位 LoadState
Phase 3  Playing       运行时按需动态加载 LoadAsset<T>(path)
```

- `LoadPhase` 枚举（源 §四）：`Booting` / `StaticConfigs` / `WorldInit` / `SaveRestore` / `Playing`。
- **关键**：Phase 1 是新建与读档**共用**的，配置加载只做一次；Phase 2 才分叉。
- ⭐ **与现行 §三.2 的关系**：现行更高层序（`CoreBootstrap → GameState.Loading → LoadStaticConfigs → ConfigsLoaded → Ready → NewGame/Continue → FinalValidation → Playing`）**涵盖并细化**源稿三阶段 ⇒ **现行为准**，本节为设计来源与证据。⚠️ 源稿**无** `ValidateSave` / `RebuildDerived` / `FinalValidation` / `LoadFailed` 这些现行环节（它们由 §二 P0-2／P0-3 补出）。

### 6.3 门面接口（源 §四／§五 · 消费者只认 `LoadManager`）

| 门面接口 | 转发对象 |
|---|---|
| `GetUnitData(faction, occupation)` / `GetAllUnitData()` | `UnitDataManager` |
| `GetPrefab(key)` / `SpawnUnit(data, position)` | `UnitFactory` |
| `WorldConfig` | `WorldSystem` |
| `CurrentDifficultyFactor` | `DifficultyManager` |
| `HasSave(slotId)` | `SaveManager` |
| `LoadAsset<T>(path)` | 运行时动态加载（`Resources.Load`） |

- 消费者**不直接**调 `UnitDataManager.Instance` / `UnitFactory.Instance`。
- 好处（源 §五）：① 消费者不需知道资源在哪个子加载器；② 阶段 1 完成后才允许取；③ 加新资源类型只改门面，消费者无感。

### 6.6 `Addressables` 迁移路径（源 §十二 · **本文 §五 标签＝`未观察到`**）

> ⚠️ **状态 ＝ `未观察到`**：源稿为**未来路径设计**，当前代码中**无 `Addressables` 实现证据**；本轮吸收**只登记设计**，⛔ 不改变现行 `Resources` 口径、⛔ 不生成施工批次。

- **可迁移性依据**：门面模式隔离加载实现 ⇒ 迁移只改 `LoadManager` 内部，消费者代码零改动。
- **接口三分类**（源 §12.3）：

| 接口类型 | 现在实现 | 迁移时改动 | 消费者影响 |
|---|---|---|---|
| 预加载接口（阶段 1 `LoadStaticConfigs`） | 同步 `Resources.LoadAll` | 改协程 `IEnumerator` ＋ `yield return` | **无**（消费者只等 `ConfigsLoadedEvent`） |
| 缓存取资源接口（`GetUnitData` / `GetPrefab`） | 同步取缓存 | **不变** | **零改动** |
| 运行时动态加载接口（`LoadAsset<T>`） | 同步 `Resources.Load` | 改 `Task<T>` 或 `IEnumerator` | 调用处加 `await` / `StartCoroutine` |

- **核心洞察**（源 §12.3）：预加载可异步化而**消费者无感**（消费者是订阅 `ConfigsLoadedEvent` 才往下走）；**缓存取资源永远是同步的**（资源已在内存，取即查字典）；只有「运行时动态加载」迁移时需消费者配合改异步 ⇒ 源估「99% 消费者零改动」。
- **迁移决策树**（源 §12.4）：资源量 ≥200 个／需热更新或远程下载／包体 >500MB 需瘦身／团队规模扩大 —— 任一触发即迁移。**现阶段**满足「资源量小 ＋ 无远程需求」⇒ 继续 `Resources`。
- **迁移步骤**（源 §12.2 · 5 步）：① Editor 标记 `Addressable` ②阶段 1 预加载改异步 ③阶段 3 动态加载改异步 ④子加载器改异步 ⑤消费者**零改动**。

### 7.1 设计目标（源 §一）

1. **统一销毁出口** —— 消除 PausePanel / GameOverPanel / GameBootstrap 各自写清理逻辑的不一致；
2. **保证销毁顺序** —— 按依赖关系**反拓扑序**销毁，避免「销毁 A 时 A 还要访问已销毁的 B」；
3. **主动销毁代替被动清理** —— 替代 `CleanupDestroyedSaveables` / `UnitRegistry.Clear` 事后扫描兜底；
4. **管理 `DontDestroyOnLoad` 对象** —— 哪些跨场景存活、哪些该销毁，集中决策。

### 7.2 ⭐ 销毁顺序：依赖矩阵 ＋ 反拓扑序（源 §三.1／§三.2 · **现行有效核心**）

**规则**：A 销毁时需要访问 B ⇒ **B 必须在 A 之后销毁**。

| 依赖方 A | 销毁时要访问 | 被依赖 B | 顺序约束 |
|---|---|---|---|
| UI Panel | `EventBus.Unsubscribe` | `EventBus` | Panel 先，`EventBus` 后 |
| UI Panel | `SaveManager` / `RulerController` / `InputManager` | 各 Manager | Panel 先，Manager 后 |
| `UnitController` | `SaveManager.UnregisterSaveable` | `SaveManager` | Unit 先，`SaveManager` 后 |
| `UnitController` | `UnitRegistry.Unregister` | `UnitRegistry` | Unit 先，`UnitRegistry` 后 |
| `UnitController` | `EventBus.Publish(UnitDiedEvent)` | `EventBus` | Unit 先，`EventBus` 后 |
| `RulerController` | `EventBus.Unsubscribe` / `SaveManager.UnregisterSaveable` | `EventBus` / `SaveManager` | Ruler 先 |
| `TimeManager` | `EventBus.Unsubscribe` | `EventBus` | Time 先 |
| `SaveManager` | `EventBus.Unsubscribe` | `EventBus` | `SaveManager` 先 |
| `EventBus.Clear` | 所有订阅者已 `Unsubscribe` | 全体订阅者 | **`EventBus` 最后** |

**反拓扑销毁顺序（源 13 步 · 原样保留）**：

```text
①  InputManager.DisableInput()          最先：停输入，防销毁中误触事件
②  UI Panels                            反订阅 GameStateChangedEvent 等 + 销毁面板
③  UnitController 们（场景内单位）       UnregisterSaveable + UnitRegistry.Unregister + Destroy
④  RulerController.monarchUnit 引用清理  引用置 null        ← ⚠️ 见 §7.9「排除」
⑤  RulerController 反订阅                Unsubscribe<UnitDiedEvent> + UnregisterSaveable  ← ⚠️ 见 §7.9
⑥  TimeManager 反订阅                    Unsubscribe + UnregisterSaveable
⑦  DifficultyManager 反订阅              Unsubscribe + UnregisterSaveable
⑧  WorldSystem 反注册                    UnregisterSaveable
⑨  SaveManager 反订阅                    Unsubscribe<TimeDayChangedEvent> + <GameStateChangedEvent>
⑩  UnitRegistry.Clear()                  清空单位注册表
⑪  SaveManager._saveables 清理           CleanupDestroyedSaveables 或直接 Clear
⑫  EventBus.Clear()                     最后：所有订阅者已 Unsubscribe，安全清空
⑬  (仅退出时) 销毁 Singleton GameObject  进程退出自然清理，或显式 Destroy
```

⭐ **与现行 §三.4 的关系**：现行拆卸序为 `StopInput → StopSimulation → OptionalSave → UnregisterSceneObjects → DestroySceneObjects → ResetRuntimeManagers → ClearRegistries → ClearEntryParameters → LoadNextScene/Rebuild` ⇒ **现行为准**（更完整：含 `StopSimulation` 与 `ClearEntryParameters`，且后者对应 §二 P0-3 的入口参数清理）；源 13 步为本序的**原始依据 ＋ 逐项依赖**（尤以 ①②③⑩⑪⑫ 的先后不可颠倒）。

### 7.3 三个关键陷阱（源 §三.3 · 现行有效）

**陷阱 1 · `Destroy()` 是延迟的** —— `Destroy(obj)` 只标记待销毁，实际在**帧末**；同帧内 `A != null` 仍为 true，但 `A.gameObject == null`（Unity fake null）。
⇒ **对策**：销毁流程**先反注册（`UnregisterSaveable` / `Unregister`）再 `Destroy`** —— 反注册是纯 C# 字典操作、立即生效，不受延迟影响。⛔ 不得靠「先 Destroy 再访问字段」判断是否已销毁。

**陷阱 2 · `OnDestroy` 时序不可靠，不做关键清理** —— `Destroy(gameObject)` 后组件的 `OnDestroy` 在帧末执行，届时**其他对象可能已销毁**（如 `EventBus` 已 `Clear`，此时 `Unsubscribe` 会操作已清空字典）。
⇒ **对策**：`TeardownManager` **显式调用反订阅**，不依赖 `OnDestroy`；`OnDestroy` 只做未覆盖处的兜底。

**陷阱 3 · `DontDestroyOnLoad` 对象不随 `LoadScene` 销毁**（源 §三.3 清单）：

| 对象 | 跨场景存活 | 返回主菜单时该不该销毁 |
|---|---|---|
| `GameStateManager` / `InputManager` / `SaveManager` / `LoadManager` | 是 | 否（Core，保留） |
| `WorldSystem` / `WorldManager` / `TimeManager` / `DifficultyManager` | 是 | 否（业务门面，保留，状态由 `InitializeWorld` 覆盖） |
| `UnitRegistry` | 是 | 否（Core，保留，但**要 `Clear`**） |
| `UnitFactory` | 是 | 否（Core，保留） |
| `RulerController` | 是 | 否（业务，保留，状态由 `InitializeWorld` 覆盖） |
| **君主单位（`UnitController`）** | **否** | ⚠️ **`排除`** —— 君主实体已退役（`67d3b67`） ⇒ 该行不再适用 |

⭐ **源稿关键发现（现行仍成立）**：非 `DontDestroyOnLoad` 的 `UnitController` 随 `LoadScene` 被自动销毁，但其**没有 `OnDestroy` 反注册** ⇒ `SaveManager._saveables` 与 `UnitRegistry._aliveUnits` 会**残留已销毁引用**，须事后清理。
⇒ **对策**：`TeardownManager` 在 `LoadScene` **前**主动反注册 ＋ 销毁，⛔ 不靠 `LoadScene` 被动销毁 ＋ 事后扫描。

### 7.4 三级 `Teardown` API（源 §四.2／§四.3 · 现行有效）

| 级别 | API | 语义 |
|---|---|---|
| Level 1 | `TeardownScene()` | 场景级清理（读档前／新游戏前）：清场景内运行时对象，**不动** Core Manager、**不动**业务 Manager 订阅 |
| Level 2 | `TeardownForReturnToMenu(bool saveBeforeTeardown = true)` | `TeardownScene` ＋ `DisableInput` ＋ 业务 Manager 重置 ＋ `LoadScene` |
| Level 3 | `TeardownForQuit()` | 全部清理：反订阅所有 ＋ 清空注册表 ＋ `EventBus.Clear` ＋ 重置 `static` |

- `TeardownPhase` 枚举（源 §四.3）：`InputStopped` / `UnitsDestroyed` / `ManagerReset` / `RegistriesCleared` / `EventBusCleared` / `Done`。
- ⭐ **职责定位（源 §四.1）**：`LoadManager` 管构建、`TeardownManager` 管拆除，**职责对称**；`TeardownManager` 为 Singleton ＋ `DontDestroyOnLoad`、**自身最后销毁**，且**不接管业务逻辑**（不调 `Save`、不 `SetState`）—— 只管「按顺序反注册 ＋ 销毁 ＋ 清空注册表」。
- ⭐ **与现行 §三.4 的关系**：现行要求「**拆卸必须可重复调用**而不会再次保存、再次广播业务事件或留下旧注册表引用」 ⇒ 对应 §二 **P1-1 重入门缺口**（源稿**无**重入/去重设计，⛔ 不得据源稿认定已闭环）。

### 7.5 Level 2 保留／销毁／重置 决策表（源 §五.2 · 现行有效）

**关键事实**：所有 Manager 都挂在 `MainMenuScene` 的独立 GameObject 上（`DontDestroyOnLoad`），返回主菜单时它们**全都活着**；真正需「销毁」的只有**场景内运行时对象**。

| 对象 | 返回主菜单时 | 原因 |
|---|---|---|
| Core Manager（`GameState`/`Input`/`Save`/`Load`/`UnitRegistry`/`UnitFactory`） | **保留，状态不动** | 主菜单也要用；`UnitRegistry` 只 `Clear` 列表 |
| 业务 Manager（`WorldSystem`/`WorldManager`/`Time`/`Difficulty`/`Ruler`） | **保留，重置运行时状态** | Manager 不销毁，下次 `InitializeWorld` 覆盖；但状态要清空防残留 |
| 场景内 `UnitController` | **主动反注册 ＋ 销毁** | 运行时对象，不该带到主菜单 |
| 君主单位 | **主动反注册 ＋ 销毁** | ⚠️ **`排除`**（君主已退役） |
| UI Panels | **`LoadScene` 自动销毁** | 场景内对象 |
| `EventBus` | **不 `Clear`** | Manager 都保留、订阅也保留；`Clear` 了反而要重新 `Subscribe` |
| `SaveManager._saveables` | **不清空** | 业务 Manager 的 `ISaveable` 注册保留，下次存档还要用 |

⭐ **核心洞察（源 §五.2）**：业务 Manager 只需「**重置状态**」，**不需要反订阅、不需要反注册 `ISaveable`** —— 因为 Manager 都保留（不销毁），订阅与注册都要继续用；**反订阅 ＋ 反注册 ＋ `EventBus.Clear` 只在退出游戏（Level 3）才做**。

### 7.6 与 `LoadManager` 的配合（源 §六.3）

```text
GameScene 启动流程（读档模式）：
  GameBootstrap.Awake
    → TeardownManager.TeardownScene()      先清理旧场景（如果有）
    → LoadManager.LoadStaticConfigs()      再加载
  GameBootstrap.OnConfigsLoaded
    → LoadManager.LoadSave()               存档恢复
    → RulerController.BindExistingMonarch()   ⚠️ 见 §7.9「排除」（君主已退役）
```

⇒ **先拆再建**（`TeardownManager` 在 `LoadManager` 之前跑）。⭐ 与现行 §三.2 的 `Continue: TeardownScene → ValidateSave → Global → Spawn → Scene → RebuildDerived` **一致**（现行在 `TeardownScene` 与恢复之间**多出 `ValidateSave`** ⇒ 即 §二 P0-2 的补项）。

### 7.7 设计原则（源 §九 · 6 条）

1. **对称** —— `LoadManager` 管加载，`TeardownManager` 管销毁；
2. **顺序优先** —— 反拓扑序（依赖方先，被依赖方后）；
3. **主动优于被动** —— 显式反注册 ＋ 销毁，不靠 `LoadScene` 被动销毁 ＋ 事后扫描；
4. **不依赖 `OnDestroy`** —— 其时序不可控，由 `TeardownManager` 显式调用；
5. **简单优于灵活** —— 硬编码顺序，暂不引入接口 ＋ 注册表；
6. **Core 与业务分离** —— Core Manager 跨场景保留，业务 Manager 由 Teardown 重置。

> 源 §六.1 曾提 `IResettable` 接口（`void ResetState()`），但源自注「当前 Manager 约 10 个，**可以不引入接口**，直接硬编码调用顺序；等超过 15 个再考虑」⇒ 见 §7.8 #3（**`未解决`**）。
