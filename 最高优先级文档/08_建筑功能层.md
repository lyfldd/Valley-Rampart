## 一、这一层是什么

**判定依据**：**驱动方是不是 NPC**。

| | 谁驱动 | 例子 |
|---|---|---|
| **L1 交互层**（`05`） | **要 NPC 参与** —— 走到、耗时、改数据 | 采集、搬运、建造、修复 |
| **L1.5 建筑功能层**（本文） | ⭐ **建筑自己** —— **没人也长** | 农场产粮、矿洞副产水晶、国库累积、裂隙刷怪、箭塔自动开火 |

⇒ **两者性质不同**：交互是"一次动作"，功能是"一条持续的状态机"。

**与 L1 的交界**（两边都要说清）：

| 场景 | 归哪层 |
|---|---|
| 农场**自动**每秒产粮入自仓 | **L1.5**（无 NPC） |
| 工人**去**农场仓把粮搬走 | **L1**（有 NPC ⇒ 任务层派） |
| 铁匠铺**等**矿石到齐才能加工 | **L1.5**（它自己等） |
| 工人**把矿石搬**进铁匠铺 | **L1** |
| 箭塔**自动**开火 | **L1.5 触发 → L1 战斗类（`07`）执行** |

⇒ ⭐ **一句话交界**：**L1.5 是"建筑自己在做什么"，L1 是"人来对它做什么"。**

### 2.2 ⭐ 病灶一：**挂载分派是硬编码 if 链**

`BuildingFactory.cs:281-328` `AttachComponents()` 逐行实读：

```csharp
bool econStorageOnly = def.producer.rate <= 0f && def.producer.capacity > 0
    && def.role == BuildingRole.Economy
    && def.outputResource != ResourceType.Gold;     // ← 四条件与
if (econStorageOnly) → StorageComponent

if (def.producer.rate > 0f && def.producer.kind == ProduceKind.Resource && !def.isResourceNode)
{
    if (def.isSiegeWorkshop)  → SiegeWorkshopBuilding
    else { StorageComponent;
           if (def.isBlacksmith) → BlacksmithBuilding
           else                  → ProducerComponent }
}
if (def.isMineByproduct)              → MineByproductComponent
if (def.combat.attack > 0)            → CombatComponent
if (def.isConsumable)                 → PickupComponent
if (b.sourceType == BuildingType.Rift)      → RiftComponent
if (b.sourceType == BuildingType.CastleCore)→ CastleCoreComponent
```

⇒ **7 个条件嵌套**，每个条件读的是**布尔／枚举／数值**的混合。**加一种新建筑功能 ⇒ 必须回来改这个函数。**

⚠️ 还有一处重叠：`StorageComponent` **两个分支里都会被挂**（`:293` 与 `:305`）—— 说明"挂什么"的判定本身就不自洽。

### 2.3 ⭐ 病灶二：**tick 分派也是硬编码**

`ProductionSystem.cs:35-45`：

```csharp
var producer   = b.GetComponent<ProducerComponent>();   if (producer   != null) producer.Tick();
var blacksmith = b.GetComponent<BlacksmithBuilding>();  if (blacksmith != null) blacksmith.Tick();
var siege      = b.GetComponent<SiegeWorkshopBuilding>();if (siege     != null) siege.Tick();
```

## 三、收敛方案：三层结构（你来定的是第一层，我补后两层）

### 3.1 三层

```
① 类型 ID       building_mine / building_blacksmith / building_gate      ← 命名式，唯一
② 能力声明      provide: [craft, store]         ← 复用 05 的能力机制
③ 组件绑定      components: [comp.producer, comp.storage]   ← 数据行声明挂哪些
```

### 3.2 为什么是三层而不是一层

| 层 | 回答 | 变化频率 |
|---|---|---|
| **① 类型 ID** | "这是**哪一栋**" | 加一栋新建筑 ⇒ **加一行** |
| **② 能力声明** | "它对**外界**能做什么" | 加一种对外能力 ⇒ **加一行** |
| **③ 组件绑定** | "它**内部**跑什么逻辑" | 加一种内部行为 ⇒ **写一个组件 + 填栏** |

⇒ **分三层的原因**：`②` 是**给外界看的**（交互配对、AI 决策），`③` 是**内部实现**。混在一起就会出现"外界要读你的实现细节"（今天的 `isBlacksmith` 就是这样：**AI 靠布尔去猜它产什么**）。

### 3.3 收敛后的挂载流程（替代 2.2 的 if 链）

```
Place(building_blacksmith)
  └─ 读数据行
       ├─ provide:    [craft, store]
       ├─ components: [comp.storage, comp.craft]
       └─ requiresWorker: 2
  └─ 遍历 components ⇒ 逐个从【组件注册表】取类 ⇒ AddComponent
```

⇒ **`AttachComponents` 的 if 链整段消失** —— 变成"遍历列表"。

### 3.4 收敛后的 tick 流程（替代 2.3 的 if 链）

```
组件统一接口加一个可选方法：
  interface IBuildingComponent { void Init(Building); }
  interface ITickable : IBuildingComponent { void Tick(); }     ← 新增

ProductionSystem 遍历 b.GetComponents<ITickable>() ⇒ 逐个 Tick()
```

⇒ **`ProductionSystem` 的 4 个 if 整段消失**。加第 5 种组件**不用回来改它**。

### 3.5 ⚠️ 诚实修正一处（沿用 `05` 的口径）

我说过"加新东西 = 只填栏"——**只对一半**：

| 加什么 | 要动什么 |
|---|---|
| 用**已有组件**组一栋新建筑（如"大仓库"= `comp.storage` 加大容量） | ✅ **只填一行数据** |
| 加一种**全新内部行为**（如"传送门"） | ⚠️ **必须写一个组件**（行为是代码，声明表达不了） |

⇒ **声明可数据化，行为必然是代码。** 本层的价值不是"零代码"，是**把"改两处硬编码"降为"写一个组件 + 填一行"**。

## 四、逐字段收敛规格

### 4.1 7 个布尔 → 按三类归位

| 原字段 | 现有引用 | 收敛为 | 理由 |
|---|---|---|---|
| `isBlacksmith` | 5 | ⭐ **类型 ID** `building_blacksmith` + `comp.craft` | 它就是"铁匠铺"这一个类型 |
| `isSiegeWorkshop` | 4 | ⭐ **类型 ID** `building_siege_workshop` + `comp.ammo` | 同上 |
| `isBridge` | 10 | ⭐ **类型 ID** `building_bridge` ＋ 能力 `provide: bridge` | 5 处都在判"是不是桥" |
| `isGate` | 7 | ⭐ **类型 ID** `building_gate` ＋ 能力 `provide: gate` | 同上 |
| `isMineByproduct` | 2 | **能力／组件** `comp.byproduct` | 它是"挂不挂某组件"，不是类型 |
| `isObstacle` | 10 | ⚠️ **派生**（占格 ⇒ 可走，`03` 已定） | 不该是可写字段 |
| `isPlayerBuilt` | 27 | **数据栏**（来源：玩家建／地图预置） | 与 `03` 的"来源"同义 |
| `isResourceNode` | 9 | **数据栏**（来源：资源锚点） | `03` 已定"矿山锚点算资源点" |
| `isConsumable` | — | **数据栏**（`可重生`，`03` 已定） | 同义 |
| `isDestructible` | 4 | **数据栏**（`可被拆除`，`03` 已定） | 已在 `03` 差异清单第 18 项 |

### 4.2 五套枚举 → 处置

| 枚举 | 处置 | 理由 |
|---|---|---|
| **`InteractableType`** | ❌ **删** | ⭐ **零消费死字段**（`L-01` 家族） |
| **`BuildingType`**（13 项） | ⚠️ **合并入「来源」栏** | 它只服务"地图预置映射"，且**与 `FeatureType` 语义重叠**（`F-09` 那个坑的来源） |
| **`BuildingCategory`**（5 项） | ⚠️ **降为数据栏**（或并入来源） | **仅 1 处消费** |
| **`BuildingRole`**（5 项） | ⭐ **大部分派生** | 9 处消费里，多数是"判它有没有某功能" ⇒ **可由组件推导** |
| **`ModuleType`**（5 项） | ✅ **保留**（独立维度） | 解锁门槛与"有什么功能"正交，作数据行一栏 |

⚠️ `BuildingRole` 的派生可行性逐处核过：

| 消费点 | 现在读 | 可否派生 |
|---|---|---|
| `BuildingVisual:91-95`（5 个美术映射） | `role` | ⚠️ 需要**显式美术键**（派生不出） |
| `PlacementValidator:195`（是不是墙） | `role == Wall` | ✅ 可派生（有 `comp.wall` 或挡路） |
| `BuildingFactory:289`（Economy 空壳仓） | `role == Economy` | ✅ 可派生（有 `comp.storage` 且无产出） |
| `Building.cs:743`（是否工事） | `role` + `isGate` + `isBridge` | ✅ 可派生（能力声明） |

⇒ **结论**：`BuildingRole` **不能整删**，但**只该留一个用途：美术键**。其余判定改读能力／组件。

## 六、判据（能力句，不写落点句）

1. **挂载数据化**：新增一栋建筑，**只改数据行**（不改 `BuildingFactory`／`ProductionSystem`）
2. **无类型 if**：`AttachComponents` 与 `ProductionSystem` **不再出现具体组件类名**
3. **能力可查**：任一建筑 ⇒ **能列出它 `provide` 的能力清单**（不读实现细节）
4. **布尔归零**：§4.1 那 7 个布尔**全部退役**（改为 ID／能力／数据栏／派生）
5. **死字段可见**：`InteractableType` 已删；**启动自检能报出任何"全库无人取"的栏**（`03` 的铁律）
6. **tick 可扩展**：新增一个带 `Tick` 的组件 ⇒ **不改 `ProductionSystem`**，且**新组件确实被 tick 到**（观测读数）

## 七、✅ 拍板结论（`D761` · 4 处分叉已定）

### 7.1 ✅ 三套枚举怎么收 ⇒ **A 案：收成三套**

### 7.2 ✅ 能力声明用哪张表 ⇒ **A 案：与 `05` 同一张表**

| 案 | 内容 |
|---|---|
| ⭐ **A（已定）** | 能力名用 `05` 的命名式（`provide: craft`／`store`／`gate`／`bridge`），**与交互层同一张能力表** ⇒ 两边看同一处，**加能力＝加一行** |
| ~~B~~ | 建筑功能另开一张"功能表"，与交互能力分开 —— ❌ **未采纳**（同一种能力会出现两个名字） |

### 7.3 ✅ 组件绑定怎么声明 ⇒ **A 案：数据行显式列表**

| 案 | 内容 |
|---|---|
| ⭐ **A（已定）** | 数据行显式列 `components: [comp.storage, comp.craft]` —— **直观、可查、可 grep**；加组件就加一行 |
| ~~B~~ | 由能力自动推导组件（`craft` ⇒ 自动挂铁匠组件）—— ❌ **未采纳**（推导规则本身要维护，且"挂了什么"不直观） |

| 案 | 内容 |
