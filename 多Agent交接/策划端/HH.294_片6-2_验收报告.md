## 三、⛔ 搭车 `R2` —— **判为不成立**（本报告唯一 ❌）

### 3.1 结构缺陷①：**身份不可区分**（无需推断·硬缺陷）

探针 `Valley_HH294_Slice6_2Probe.cs:715`：

```csharp
verdict = chA ? a.name : b.name;      // ← 返回的是**名字**
...
:654-656  "**像素实测最前者（外部观测）**=" + frontC + "｜ 一致=" + (hitC.source.name == frontC ? "✅" : "❌")
```

而用例① 的两个对象**同名**（原件日志逐字）：

```
§G 用例①：A=Human_Player_Vagrant(...) B=Human_Player_Vagrant(...)
```

⇒ `hit.source.name == front` 在"拾取返回 A"与"拾取返回 B"两种情形下**都输出 ✅** ⇒ ⭐ **该列对"深度键符号反了"这一目标故障零鉴别力** —— 而符号反转**正是** `R2` 要防的失败形态（`D776` 立此残余的原话：「符号若反了它照样 ✅」）。

> 补充：候选窗口 r=7（15×15 格）内可能还有**第三个同名 Vagrant** 在场 ⇒ 连"返回的是 A 还是 B"都无法从日志判定。

### 3.2 结构缺陷②：**"结论明确"判据把两种情形混为一谈**（硬缺陷）

```csharp
bool chA = ColorChanged(c0, cA), chB = ColorChanged(c0, cB);
bool conclusive = chA ^ chB;          // 一个变、一个不变 ⇒ 判"变者为最前者"
```

`hideX ⇒ 像素变` 有两种成因：**(i) X 遮挡 Y**（真遮挡）／**(ii) Y 在该像素无贡献**（透明/未覆盖）——**两者签名完全相同**（`chX=true, chY=false`）。`chA ^ chB` **无法区分**。

用例① 首点即"conclusive"（`chA=true, chB=false`）而**露出的颜色是亮绿 `(0.58,0.83,0.26)`**（该隔离位背景/地形色，非单位色）⇒ 支持读法 **(ii)：该像素仅 A 有贡献** ⇒ **该点不是有效遮挡点** ⇒ 即使把 3.1 的名字问题修掉，此点也得不出"谁在前"。

### 3.3 缺陷①②的交叉后果：**两列很可能实际相反，却被判为一致**

按实现复算该点（`MapGate.cs:637-648`）：

| 量 | A（`ua`） | B（`ub`） |
|---|---|---|
| `transform.position.y`（`spriteSortPoint=Pivot` ⇒ 深度键） | **77.62** | **77.42** |
| `bounds.center.y` ± 0.19（日志：77.78／77.58） | 覆盖 [77.59, 77.97] | 覆盖 [77.39, 77.77] |
| 采样点 `(−0.13, 77.62)` 是否在内 | 是 | 是 |

⇒ 两候选**皆含**该点；`IsInFrontOf`（`DepthMajorYInFront=false` ⇒ 小 y 在前）⇒ **`PickAt` 应返回 B（小 y）**；而**像素列结论为 A（大 y）**。

⇒ ⭐ **两列指向不同对象，却因同名而打印 `一致=✅`。**

### 3.4 但**不是功能缺陷**（我另证）

`MapGate.DepthMajorYInFront = false`（小 y 在前）的**外部观测依据**我回读了片 6-1 原件：

```
§G0-A 组1：红y=0.5 蓝y=-0.5 ⇒ 重叠中心像素 RGB=(0,0,1) ⇒ 盖住的是 蓝（y=-0.5）
§G0-A 组2：红y=-0.5 蓝y=0.5 ⇒ 重叠中心像素 RGB=(1,0,0) ⇒ 盖住的是 红（y=-0.5）
§G0-A ★ 实测「谁在前」＝ 小 y 在前 ｜ 与 DepthMajorYInFront=False ✅ 一致
```

**换色交叉两组一致** ⇒ 结论稳健（构造用例为纯色精灵，无透明干扰） ⇒ **实现符号正确**；且用例②（`Chest` order 5 vs 建筑 order 1）身份**可区分**且 `order` 规则成立 ⇒ **层带规则有真实证据**。

⇒ 故本项定性＝**「证据不成立」而非「功能有问题」**：`R2` 的**目的**（外部观测闭环）**未达成**，`03` §8.7 判据 6 仍缺真实实体侧闭环。

### 3.5 修法（**必须按此三条做，否则第 3 次仍是空转**）

1. **身份可区分**：两个对象**改名**（或比较 `GetInstanceID()`），并**打印"返回者 ∈ {A,B}／（或第三方）"**——⛔ 禁按 `name` 比较同类同精灵对象；
2. **加"背景对照"**：每点做**第 4 次采样 `hide both`**；
   ⇒ 判据改为：**`chA` 且 `hideA ≠ hideBoth`** 才算"A 遮挡 B"；若 `hideA == hideBoth` ⇒ 该点无效（Y 在此无贡献），**跳下一点**；
3. **覆盖异类**：用例① 改为**异类**（单位 × 建筑／两种不同 sprite），用例② 保留跨层带；两例**各 ≥3 个有效点**（非"首点即定论"）。

## 六、收口三问

**Ⅰ 为什么会发生？**
`R2` 是**证据类**判据（不是功能类）：探针**实现了方法**（RT 像素隐藏法，方法本身有价值），但方法在"**同类同精灵 + 同名**"用例上**结构性退化** —— 身份不可区分 ⇒ 比较退化为恒真；`chA ^ chB` 条件又无法区分"遮挡"与"对方透明"。两个退化点**叠加**后，探针只要跑起来就必然输出 ✅。

**Ⅱ 是单次失误还是流程漏洞？**
**流程漏洞**，且**在签发侧（我）**：我写 `R2` 时只规定了"两列 ＋ ≥1 例"，**未要求鉴别力自检**（"若被测实现反向，本列读数会变成什么？"）。⇒ 同类家族**第 3 次** ⇒ 按本端自有纪律**升为红线复盘**。

**Ⅲ 教训库里是缺条目，还是没查？**
**条目有、没查**：`L-30`「反证须有鉴别力」在库（`D775` 立·`D776` 加维）——但**签发时未回查** ⇒ 说明"有条目 ≠ 会被用" ⇒ 本条归入 §七 的**签发前自检清单**（升格为硬性动作，而非仅条目）。

## 七、⭐ 升级的硬性纪律（本报告立 · 下一批起生效）

**签发任何「对照类」判据时（两列/两读数/前 vs 后），必须同时写足三件**：

1. **身份可区分**：两对象的标识方式禁"可能重名/同类同精灵"⇒ 须指定"按实例 ID 或先改名"；
2. **鉴别力声明**：写明「**若被测实现反向/缺失，本列读数应变成什么**」——两侧预期值**相同** ⇒ 该判据**作废重写**；
3. **对照点有效性**：区域/像素类对照须含**背景（空）对照**，证明"该点确实是有效对照点"，否则须跳点。

> 同时上升为「**'退役/替换'类改动 ⇒ 优先保留 A/B 开关，把'改前读数'实测出来**」为**惯例**（本批做得很好·见 §八 嘉奖 ①）。
