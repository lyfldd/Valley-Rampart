### 二-2 ✅ `甲′-b`（30 s 超时型）确认 ＋ ⚠️ 须补一条**它不只是"放弃"，而是"无限循环"**

⇒ ⭐ **`甲′-b` 不是"一次性放弃"，而是「30 游戏秒一轮的无限循环」**（清除与重派相隔 1~2 帧）。⇒ 与 `甲′-a` 的"同帧空转"**并列，两者都是循环**。⇒ ⭐ 这**强化 `D812` 的「无自愈」定性**（无自愈 ⇒ 不是偶发，而是**稳定复现的循环**）。

### 二-3 ⭐⭐ 本端补全 `D812` 遗留缺口 —— `dest` 覆盖的**直接读数**

报告 §五-1 自陈「`甲′-b` 的直接成因未取证（`BehaviorExecutor`/attention 抢占面）」。**本端已从落盘 `seq` 行拿到直接证据**：

### 二-4 ⭐⭐⭐ 本端重大勘正 —— `WaterHaul` 的 `B` **不是"配出来的"，是"漏配 ⇒ 兜底"**

报告 §四-3 报「`WaterHaul` 实际优先级 ＝ `B`（非 `C`）⇒ 与既有记录／`D808` 的「C 档」**不符** ⇒ **勘正**」。**本端核对配置表后发现归因须勘正**：

```
enum TaskPriority { S=4, A=3, B=2, C=1 }
enum KingdomTaskType { Repair=0, Build=1, Produce=2, Transport=3, Rancher=4,
                       WaterCarry=5, GoldMine=6, Production=7, WaterHaul=8, Gather=9, AmmoReload=10 }

TaskPriorityConfig.asset entries（**逐条实读**）：
   taskType 0(Repair)→4(S)  1(Build)→3(A)  2(Produce)→3(A)  3(Transport)→2(B)
   taskType 4(Rancher)→1(C) 5(WaterCarry)→1(C) 6(GoldMine)→1(C) 10(AmmoReload)→2(B)

⛔ **taskType 7(Production) / 8(WaterHaul) / 9(Gather) —— 三项一条都没有配**
TaskPriorityConfig.cs:27  兜底：`return TaskPriority.B;`
```

⇒ ⭐⭐ **真根因 ＝ 「漏配 ⇒ 走兜底 B」**，⛔ **不是"记录不符"**：
- `WaterHaul`(8) 与 **`WaterCarry`(5)** 是**两个枚举项**（前者 `M1-F` 起用，后者旧"挑水"）⇒ **配置只配了旧的 `WaterCarry`(C)**，新的 `WaterHaul` 漏配
- 同族：`Production`(7) 与 **`Produce`(2)** 也是两个枚举项 ⇒ 只配了 `Produce`(A)
- ⇒ ⭐ **文档（`TaskPriorityConfig.cs:7/16`）与实物不符**：文档说「生产/采集/加工 = A」、实为 **B（被降级）**；文档说「挑水 = C」、实为 **B（被升级）**

⚠️ **连带影响（须回写 `D808`）**：
- `D808` §二-1 的「`WaterHaul`（**C 档**）vs `Production`（**B 档**）刺激竞争」⇒ ⭐ **前提不成立** —— **两者实际同为兜底 `B`**（`Production` 也是漏配）⇒ 该处档位对比**作废重写**（竞争仍存在，但**不是由档位差驱动**）。
- ⭐ `WaterHaul` 被意外**升级**到与 `Transport`/`AmmoReload` 同级 ⇒ 更容易被派 ⇒ 是"派而不执行"**被放大的因素**（⛔ 非成因）。
