## 二、接缝冲突（需策划裁决的核心）
设计稿 §5.0（L232-240）要求**协作施工流程**：
```
放置目标 → 建筑发布任务（资源总需求如500石，D95规模派工=理想工人数）→
工人去王国仓库取资源→搬运→填入目标建筑"仓库"→ 仓库积满 → 触发施工期（多工人协作）→ 完成激活
```
关键语义：**资源通过任务搬运逐步积累到目标建筑**，不是放置时一次性扣。

**而步骤3 我刚落地的是"放置时凑单一次性全扣"**（`WarehouseHelper.TrySettle`）。若按设计稿改，放置时不再全扣，改为"占位 + 广播搬运任务 + 目标 StorageComponent 积累 + 积满触发施工"。这会**推翻步骤3 刚提交的凑单落地**（建造点击从"结算扣减"变为"发任务"）。

## 三、待决策项（选项 + 推荐）
1. **建造资源收取方式**：
   - A（推荐）：**分两段**——放置时仍由 `WarehouseHelper.TrySettle` 从王国仓库扣**总成本**，但扣费后的"施工"改为**目标建筑 StorageComponent 预存入该成本资源**（模拟"仓库积满"起点）→ 施工期=多工人协作推进（constructDuration 按协作人数缩短，复用现有 Constructing 态）。改动最小：不动步骤3 凑单、只给 Building 加"协作施工计时按工人数缩放"。工人协作人数从哪来（2_8 派工或固定）需定。
   - B：严格按设计稿——放置只发布搬运任务，资源经工人实际搬运逐步积累到目标建筑仓库，积满才触发施工。改动最大：重写放置流程 + 新增目标建筑仓库积累逻辑 + 与 2_8 搬运任务深度耦合，且**需推翻步骤3 凑单落地**。
   - C：本步只落"多工人协作施工"（施工耗时随协作工人数缩短），资源收取保持现有（放置即扣），"搬运积累"整个留后续步骤。
2. **协作施工的人数来源【若选 A/C】**
   - `TaskScheduler` 已派工给该建筑的工人数（`HasWorkerAssigned`），或 2_8 `ScaleTaskArgs` 规模派工给出的理想工人数。
   - 施工耗时 = `constructDuration / 协作加成`（加成 = 1 + (工人数-1)×系数，系数 SO 可配）。
3. **验收路径**：步骤4 验收（L119）"放采石场→派工人→产石→搬运入就近仓库（2D）闭环；建造/升级=仓库积满→协作施工跑通"。若选 A，验收口径需缩围为"建造/升级=扣费→协作施工跑通"（资源收取=凑单已验）。

## 四、我的倾向

- 关键待策划定：**协作施工语义**（要"真实搬运积累"还是"扣费+计时缩放"）+ 协作人数来源 + constructDuration 是否需 SO 化（当前 5f 硬编码，note 到步骤）。
