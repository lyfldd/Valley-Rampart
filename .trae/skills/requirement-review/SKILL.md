# 需求审查与澄清（Requirement Review）

以**开发者视角**审查文档需求，逐点和用户确认每个决策点，挖掘缺失需求与架构级决策，最终汇总成清单并整合进文档。

适用于：游戏开发、系统设计、技术方案评审等任何需要"把模糊需求变成可执行决策"的场景。

---

## 工作流

### 阶段 1：读取与评估

1. **完整读取目标文档**（不要只读片段）
2. **理解文档定位**：是计划性、审查性、还是设计性文档？
3. **以开发者视角评估**，问自己三个问题：
   - 拿着这份文档，我能直接开始写代码吗？
   - 哪些地方有架构方向但缺数值/边界/交互细节？
   - 哪些地方完全空白，是真正的需求缺口？

### 阶段 2：三段式分析输出

向用户输出**三段式评估**，结构固定：

```
一、文档明确的部分（✅ 已经够开发用）
   列出哪些需求清晰、架构方向明确、可直接落地

二、作为开发者，我认为还缺失的需求
   分门别类列出空白：
   - 🔢 数值与平衡（数字是空的就无法验证）
   - 🏗️ 架构细节（生命周期/接口/数据流）
   - 🎮 玩家交互与反馈
   - 🗺️ 放置/操作规则
   - 🎯 胜负与节奏

三、我想向你确认的需求（请回答）
   用 AskUserQuestion 抛出关键决策点
```

**关键原则**：
- 先肯定文档已做好的部分，再指出缺口（建立信任，避免显得否定）
- 缺失需求要分类，不要堆砌（数值/架构/交互/规则/节奏）
- 主动提需求建议，不要只当"提问机器"——你是开发者，要有自己的判断

### 阶段 3：逐点确认（核心环节）

用 `AskUserQuestion` 工具和用户确认每个决策点。

**提问规则**：
- 每轮最多 4 个问题（工具上限）
- 每个问题给 2-4 个选项，**第一个选项标注"（推荐）"** 并给出推荐理由
- 选项要**具体**（带数值/方案/影响），不要模糊表述
- 问题要标注"这决定 XXX"，让用户理解决策的工程影响

**提问优先级**：
1. **架构级决策**（影响代码结构的，如调度机制、存储方案、组件边界）
2. **时序矛盾**（发现依赖冲突必须先解决，如"方案B依赖3.10但3.10没做"）
3. **数值与平衡**（影响游戏手感的）
4. **交互与体验**（影响玩家操作的）

**每轮提问后**：
- 梳理用户决策带来的**连锁影响**（一个决策会带出新需求）
- 指出新出现的**时序矛盾**或**架构洞察**
- 继续抛出下一轮问题，直到需求闭环

### 阶段 4：挖掘架构洞察

讨论中要主动识别并提炼**架构级洞察**，这些是讨论涌现的高价值产出：

1. **统一架构**：多个功能能否共用一套底层系统？
   - 例：建造/升级/维修/资源点改造 都走 `Constructing` + 进度条，一处实现四处复用
   
2. **时序矛盾**：决策依赖未实现的系统怎么办？
   - 识别依赖链：方案B → 搬运AI → 3.10移动系统（未实现）
   - 给折中方案：首版占位模式 + 预留接口，后期切换不破坏架构

3. **连锁需求**：一个决策带出新需求
   - 例：主城 Kingdom 设计 → 带出科技树分级解锁 → 带出初始资源量 → 带出废弃城堡状态

4. **模型抽象**：把复杂业务抽象成清晰模型
   - 例：资源点 + 工具 = 产出建筑（资源点是前置，工具激活后才产出，放置即改造）

把这些洞察明确写出来，它们是讨论的核心价值。

### 阶段 5：汇总需求清单

需求讨论充分后，整理成**结构化需求清单**：

```
一、原问题决策汇总（表格：问题/决策结果）
二、新增架构需求（分章节：架构/系统/交互/数值）
三、占位数值表（即使占位也要有具体数字）
四、后续/待定需求（标注依赖）
五、实施优先级（P0/P1/P2 三级）
```

**先出清单，让用户确认无遗漏**，再决定是否写入文档。

### 阶段 6：写入文档

用户确认清单后，整合进原文档：

- **保留原文档的诊断内容**（问题分析有独立价值，不破坏）
- **新增章节**记录需求决策（如"第十节 需求讨论成果与架构决策"）
- **更新实施优先级**（旧的路线图替换为 P0/P1/P2）
- **头部加更新说明**，标注本次讨论的核心决策
- **修正笔误**（如栈是 LIFO 不是 FIFO）

---

## 关键原则

1. **开发者视角**：你是开发者，不是记录员。主动提需求建议，给推荐方案，有技术判断。

2. **逐点确认**：每个需求点都要用户拍板，不要替用户决定。但要用"推荐选项"引导，降低用户决策成本。

3. **先清单后文档**：讨论成果先汇总成清单确认，再写入文档。避免边讨论边改文档导致遗漏。

4. **数值要落地**：即使占位也要有具体数字（如 rate=10/秒、capacity=100）。"用占位数值跑通"比"以后再定"更可执行。

5. **时序矛盾必须解决**：发现依赖冲突（A 依赖 B 但 B 没做）必须当场提出折中方案，不能埋雷。

6. **保留原诊断**：写入文档时不破坏原有问题分析，新增章节集中记录决策，形成"发现问题→分析→决策"完整链路。

7. **架构洞察要显式提炼**：讨论涌现的统一架构/模型抽象是高价值产出，要单独成节强调。

## 提问技巧

### 好的提问（具体、带影响、有推荐）

```
问题：产能系统的 tick 机制你倾向哪种？这决定了 ProducerComponent 和 ProductionSystem 的代码结构。
选项：
- 集中调度器（推荐）：ProductionSystem 每秒统一遍历，性能好、易存档
- 组件自驱动 Update：实现简单但难统一暂停
- 事件驱动 tick：解耦但开销大
```

### 坏的提问（模糊、无推荐、无影响说明）

```
问题：产能系统怎么做？
选项：
- 方案A
- 方案B
- 方案C
```

### 连锁提问模式

一个决策确认后，立即追踪它带出的新问题：

```
用户选了"方案B存储" 
  → 但方案B依赖3.10移动系统（未实现）
  → 立即提问时序矛盾怎么折中
  → 用户选"先做存储留接口"
  → 继续追踪：采集单位从哪来？资源点和产出建筑什么关系？
```

不要等用户主动提，主动追踪连锁需求。

## 输出格式参考

每个分析输出遵循这个节奏：

1. **确认理解**：复述用户决策，确保理解正确
2. **指出影响**：这个决策带来的连锁影响（✅好处 / ⚠️风险）
3. **继续挖掘**：基于这个决策，还有什么要定的
4. **抛出问题**：用 AskUserQuestion 确认下一轮决策

示例：
```
收到你的决策。我先整理一下这个选择带来的连锁影响，其中有一个时序矛盾必须先解决。

## 你的决策梳理
| 决策点 | 选择 | 影响 |
|--------|------|------|
| ... | ... | ✅/⚠️ |

## ⚠️ 时序矛盾
[描述依赖冲突]

## 需要你拍板
[AskUserQuestion]
```

## 通用性

本 skill 不局限于游戏开发，适用于任何需求讨论场景：
- 系统设计评审
- 技术方案澄清
- 产品需求细化
- 任何"把模糊变成可执行"的讨论

核心方法论不变：开发者视角评估 → 三段式分析 → 逐点确认 → 挖掘洞察 → 汇总清单 → 写入文档。
