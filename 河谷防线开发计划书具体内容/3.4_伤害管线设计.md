## 一、定位与依赖

### 1.1 本模块职责

伤害管线 = **攻击判定 + 伤害计算 + 血量死亡 + 对象池**。负责"谁打谁、打中没、掉多少血、死没死、死后回收"。

### 1.2 边界（不做什么）

| 不做 | 归属 |
|------|------|
| 装备产生/属性叠加/掉落概率/拾取 | 装备系统（独立，后续） |
| 命中闪烁/击退/伤害数字/死亡动画 | 反馈层（P1） |
| 死因（物理/魔法）判定 | 抗性系统（后续） |
| 弹道视觉形态（抛物线顶点等） | 反馈层 |

3.4 **只消费护甲值**（来源不关心，基础值或装备叠加都行），**只触发掉落钩子**（掉落什么/概率是装备系统的事）。

### 1.3 依赖的现有系统（已核实代码现状）

| 系统 | 现状 | 3.4 衔接方式 |
|------|------|------------|
| **GridSystem**（3.2 已实现） | cellSize=2.26，`GetUnitsInCell` 可用 | 空间分区查目标，复用不动 |
| **UnitController**（已有完整战斗链路） | 已有 `AttackUnit`/`TakeDamage(int,UnitController)`/`Die`/`Heal(int)` + 发布四事件（UnitAttackEvent/UnitDamagedEvent/UnitHpChangedEvent/UnitDiedEvent）+ ISaveable 存档（currentHp/maxHp 进出存档）+ 旧公式 `max(1, rawDamage-Defense)` | **重构**：TakeDamage 退化为"收算好的伤害扣血"，公式搬到 DamageSystem；Heal/存档/移动保留 |
| **Building**（已有部分战斗链路） | 已有 `TakeDamage(int)`/`Die`/`Demolish`（拆除按 hp 比例退款后走 Die）+ 发 BuildingDestroyedEvent；**非 ISaveable、无 Heal** | **重构**：实现 IDamageable；Die 区分拆除/被击杀（见 6.4） |
| **EventBus + 四事件**（1.3 已实现） | UnitAttackEvent/UnitDamagedEvent/UnitHpChangedEvent/UnitDiedEvent 均已存在；UnitDamagedEvent **零订阅**；UnitDiedEvent 订阅方=RulerController（君主阵亡→GameOver）+ TopLeftHUD（清君主引用停刷新）；BuildingDestroyedEvent 订阅方=BuildingPanel | **改造**：UnitDamagedEvent 扩字段+节流复用为受击事件（不新建 UnitHitEvent）；UnitDiedEvent 字段改 IDamageable |
| **UnitData**（已有） | 已有 `attack`/`defense`/`maxHp` 三字段（全 int），defense 即护甲语义 | **复用**：护甲复用 defense 字段，不新立 armorBase |
| **BuildingDef.combat**（已有） | `CombatConfig{attack,defense,maxHp,range,damageType}` 五字段 | **复用**：建筑数值住 BuildingDef.combat |
| **NpcProfessionDef**（不存在，待新建） | 全局无此文件 | **新建**：继承 UnitData 拿基础三件套，扩展 perceptionRadius/threatSensitivity/弹速/CD/攻击范围/装备槽 |
| **UnitFactory**（已有） | 普通实例化 | **重构**：改造为对象池取/回 |
| **DamageSystem**（不存在，待新建） | — | **新建**：集中调度器，本模块核心 |

### 1.4 依赖方向与 stub 解耦（避免实现顺序循环）

**编译依赖（单向，无循环）**：
```
NPCBrain ──调用──→ DamageSystem.RegisterAttack()
AttentionSystem ──订阅──→ UnitDamagedEvent（公共事件定义）
DamageSystem ──发布──→ UnitDamagedEvent / UnitDiedEvent（公共事件定义）
```
DamageSystem 不认识 NPCBrain，只有 `RegisterAttack` 接口，谁来调都行。编译层面 NPCBrain → DamageSystem 单向，无循环。

**业务数据流（闭环，是设计目标）**：
```
NPCBrain 选目标 → DamageSystem 执行攻击 → 受击发 UnitDamagedEvent
      ↑                                            ↓
      └── AttentionSystem 收到 → 威胁 3 → 撤退 ←──┘
```
业务闭环是 3.0.1 要验证的目标，不是缺陷。

**实现顺序循环的解法——stub 攻击驱动器**：
3.4 主体（DamageSystem/IDamageable/伤害计算/HP/死亡/事件/对象池/投射物）完全不依赖 3.0.1。需要 NPCBrain 的只有"谁来发起攻击"一环。验证 3.4 时用临时 `StubAttacker`（10 行脚本，只做"查最近敌人→RegisterAttack"，无注意力/威胁/谱系），3.0.1 真 NPCBrain 完成后替换。

```
实施顺序：
  ① 3.4 主体（独立，不碰 AI）
  ② StubAttacker（临时脚本）
  ③ 3.4 闭环验证（3v3+1远程兵+1工人旁观）
  ④ 3.0.1 NPCBrain（替换 stub）
  ⑤ 3.0.1 闭环验证（受击→威胁3→撤退）
```
①②③ 不依赖 3.0.1，可独立完成。stub 是斩断实现顺序循环的那把刀。

## 二、核心架构总览

```
攻击方（CD 到点）
   ↓
DamageSystem 集中调度器
   ├─ 时间轮：CD 到点 → 进待攻击队列
   ├─ 目标查询：查攻击范围内几个格子（GridSystem）
   ├─ 过度杀伤防护：目标受击数上限 2，多余换目标
   ├─ 分帧分片：一帧最多 100 判定，余下推下帧
   └─ 分流：
      ├─ 近战 → 即时命中（查 1 格选目标判定）
      └─ 远程 → 发射投射物（委托 ProjectileManager）
                ↓
                ProjectileManager（对象池 + 统一 Update）
                ├─ 抛物线 t 插值位置（每帧轻量）
                ├─ 到达时刻判定命中/闪避（一次）
                └─ 命中 → 走伤害计算
   ↓
伤害计算：伤害 = 攻击力 × (1 - 护甲/(护甲+K))
   ↓
HP 扣血 → 血量≤0 → 死亡
   ↓
死亡 → UnitDiedEvent(死亡者+阵营+位置+击杀者) + 掉落钩子(预留) → 对象池回池重置
```

**性能破局点**：
1. 命中判定复用 GridSystem 空间分区，O(n²) → O(n×格数)
2. 攻击按 CD tick（时间轮），非每帧遍历，同帧到点的可能只有几十个
3. 分帧分片抹平 CPU 尖峰
4. 弹道逻辑/视觉分离——每帧只 t 插值（轻量），命中只在到达时刻判定一次
5. 投射物 + NPC 双对象池，零 GC

## 三、DamageSystem 集中调度器

### 3.1 时间轮（攻击 CD 统一管理）

所有单位攻击 CD 集中存储在时间轮/优先队列，**不是每个单位自己数倒计时**。冷却到点的单位进"待攻击队列"，没到的根本不碰。

```
几百个单位里，同一帧 CD 到点的可能只有几十个 → 遍历量砍一个数量级
```

### 3.2 目标查询（走空间分区）

待攻击单位找目标**不去遍历全场**，只查攻击范围内覆盖的几个格子：

- 近战：攻击范围小（1 格），查 1-2 个格子，开销极低
- 远程：攻击范围大（5 格），查的格子多，但远程数量通常少，总开销可控

查询出的候选目标可能就几个，距离计算开销可忽略。复用 `GridSystem.GetUnitsInCell` / 按感知半径算格数 `n=ceil(R/cellSize)`（见 3.0.1 7.1）。

### 3.3 分帧分片

同一帧待攻击单位太多时分几帧处理：**一帧最多 100 个攻击判定，余下推下一帧**。玩家感知不到几帧攻击延迟，但 CPU 尖峰抹平。

### 3.4 过度杀伤防护

防一堆近战同时集火同一目标导致伤害浪费：调度器维护"目标当前受击数"，**上限 2**。多余近战换目标或往前走。

### 3.5 近战 vs 远程分流

| 类型 | 判定方式 | 范围 | 开销 |
|------|---------|------|------|
| 近战 | 即时命中（攻击时刻查格选最近敌方判定） | 1 格 | 极低，数量多但单次轻 |
| 远程 | 发射投射物，到达时刻位置检测 | 5 格 | 查格多但远程数量少 |

### 3.6 受击事件节流（防订阅方刷爆）

500 NPC 互斗时一帧可能几十次 hit，UnitDamagedEvent 不节流会刷爆 3.0.1 AttentionSystem 订阅方。

- DamageSystem 维护 `victim → lastEventTime` 字典
- 同一 victim 每 0.5s 最多发一次 `UnitDamagedEvent`
- 3.0.1 威胁升级本身有滞回（0.3s 持续确认），节流不破坏逻辑
- 节流间隔住 DamageConfig（0.5s）
- 字典项在对象池回池重置时清理（见 6.6），防新 NPC 继承上辈子状态

### 3.7 注册表死亡清理（自清责任）

DamageSystem 订阅 `UnitDiedEvent` 自清内部三张表（attacker→target 映射、过度杀伤计数、节流字典）。详见 6.6。这是 DamageSystem 的责任，不是 victim 或 attacker 的责任——集中管理即集中清理。

## 四、ProjectileManager 投射物集中管理

### 4.1 逻辑命中 vs 视觉弹道分离（核心）

```
发射时刻（逻辑层，一次）：
  - 锁定目标位置（非目标对象）+ 算飞行时间 t = 距离/弹速
  - 算抛物线参数（起点/顶点/终点）
  - 入池取投射物

飞行中（视觉层，每帧）：
  - pos = 抛物线插值(currentT)   ← 仅几个浮点运算
  - 不做碰撞检测，不追踪原目标

到达时刻（逻辑层，一次）：
  - 位置检测：查目标位置 0.5 格半径内非己方单位
  - 按 MaxHits 取最近 N 个命中（单发箭 MaxHits=1，投石机 MaxHits=N）
  - 无单位在范围内 = miss（原目标跑了且无人补位）
  - 有单位 = 误伤命中（Faction 二元判定，含友军）
  - 命中 → 走伤害计算；投射物回池
```

**关键**：抛物线每帧只 t 插值（3 个浮点），不是物理碰撞。500 投射物每帧 = 500 次插值，可控。贵的检测只在到达时刻做一次。投射物发射后独立，不追踪原目标也不追踪发射者。

### 4.2 MaxHits 参数（承接 3.0 总览 AoE 契约）

3.0 总览明确伤害管线契约含"范围伤害（投石机）+ Range+MaxHits 解耦"。单发命中数与范围分离：

| 投射物类型 | 到达检测范围 | MaxHits | 说明 |
|-----------|------------|---------|------|
| 单发箭（弓兵） | 0.5 格半径 | 1 | 命中最近一个 |
| 投石机（未来） | 2 格半径 | N | 范围内最多 N 个 |

- MaxHits=1 即单发，首版主力；MaxHits=N 即 AoE，投石机/爆炸物用
- DamageConfig 配全局上限，NpcProfessionDef 配职业实际值
- 首版只实现 MaxHits=1（单发），AoE 留接口（P2 投石机时实装）

### 4.3 对象池

- 投射物入池/取池复用，零 GC
- 限数降级：超过上限时降级处理（如 oldest 直接判定命中回池）

### 4.4 集中 Update

所有投射物在 ProjectileManager 统一 Update，**不是每个投射物自己 MonoBehaviour.Update**。和 DamageSystem 同一套集中调度思路。

## 五、伤害计算模型

### 5.1 百分比减伤（替代旧线性公式）

```
减伤率 = 护甲 / (护甲 + K)
伤害 = 攻击力 × (1 - 减伤率)
```

- 替代旧公式 `max(1, 攻击-防御)`（线性减防在高攻时防御无用、防御堆再高也 max(1)）
- 无 0 伤害问题（护甲再高减伤率也 < 1）
- 高甲难破但非无敌
- K 是平衡常数（占位 100），住 DamageConfig
- 公式从 `UnitController.TakeDamage` 内部搬到 DamageSystem 集中算

### 5.2 护甲来源（复用现有 defense 字段）

```
护甲 = UnitData.defense（现有字段，复用）+ 装备叠加(预留，首版 0)
```

- **复用 `UnitData.defense`**（已核实存在，语义即护甲），**不新立 armorBase** 制造重复字段
- NPC 护甲住 `NpcProfessionDef`（继承 UnitData，含 defense）
- 建筑护甲住 `BuildingDef.combat.defense`
- 装备怎么叠加是装备系统的事，3.4 只消费 defense 值

### 5.3 int 取整策略（HP 链路保持 int）

新公式天然产 float，现有 HP/攻击/防御/事件字段全 int。取整规则定死，int 链路不动，UI/存档零影响：

```
DamageSystem 内部：
  float rawDamage = 攻击力 × (1 - 护甲/(护甲+K))   // float 运算
  int finalDamage = Mathf.RoundToInt(rawDamage)     // 四舍五入取整
  finalDamage = Mathf.Max(1, finalDamage)           // 保底 1（防取整为 0）
  → victim.TakeDamage(finalDamage)                  // 传 int
  → UnitDamagedEvent.ActualDamage = finalDamage     // 事件字段 int
```

- 取整方式：四舍五入（Mathf.RoundToInt），不用向下取整（会系统性偏低）
- 保底 1：防低攻高甲场景取整为 0 导致打不动
- 全程只有 DamageSystem 内部出现 float，对外接口和链路全 int

## 六、血量、受击与死亡

### 6.1 HP 现状与 IDamageable 抽象

**现状（已核实）**：
- `UnitController` 已有 `CurrentHp`/`MaxHp`（int）+ `TakeDamage(int, UnitController)` + `Heal(int)`（实装可用）+ ISaveable 存档（currentHp/maxHp 进出存档）
- `Building` 已有 `hp`/`maxHp`（int）+ `TakeDamage(int)` + `Die`；**无 Heal、非 ISaveable**
- 旧减伤公式在 `UnitController.TakeDamage` 内部：`Mathf.Max(1, rawDamage - Defense)`（线性减防）

**IDamageable 接口（新建，统一抽象）**：
```csharp
public interface IDamageable {
    int CurrentHp { get; }
    int MaxHp { get; }
    Vector2 GetPosition();
    Faction GetFaction();
    void TakeDamage(int finalDamage);   // 收 DamageSystem 算好+取整后的伤害，只扣血
    void Heal(int amount);               // 预留，UnitController 已实装，Building 补空实现
}
```
- `UnitController` 实现 IDamageable：现有 `TakeDamage(int, UnitController)` 重构为 `TakeDamage(int finalDamage)`（去掉 source 参数和内部公式，公式搬到 DamageSystem）；`Heal` 已有
- `Building` 实现 IDamageable：现有 `TakeDamage(int)` 签名兼容；补 `Heal` 空实现（建筑不回血）
- **HP 链路保持 int**（UI/存档零影响），float 只在 DamageSystem 内部运算（见 5.3）

### 6.2 受击事件：改造 UnitDamagedEvent（不新建 UnitHitEvent）

**现状**：`UnitDamagedEvent{ UnitController Unit, UnitController Source, int ActualDamage }` 已存在且**零订阅**。新建 UnitHitEvent 会造出语义重复事件。

**改造方案**：扩字段复用为通用受击事件，3.0.1 ThreatStimulus 订阅它触发威胁 3。
```csharp
// 改造后（字段名沿用现有 Unit/Source/ActualDamage，新增 Position）
public readonly struct UnitDamagedEvent {
    public readonly IDamageable Unit;      // 类型从 UnitController 改 IDamageable（建筑也走此事件）
    public readonly IDamageable Source;    // 攻击方（可为 null）
    public readonly int ActualDamage;      // 取整后伤害（int）
    public readonly Vector2 Position;      // 新增：受击位置
}
```
- **节流**：DamageSystem 维护 `victim → lastEventTime` 字典，同一 victim 每 0.5s 最多发一次（见 3.6）
- 3.0.1 ThreatStimulus 订阅 `UnitDamagedEvent` → 触发威胁 3 致命
- 威胁升级本身有滞回（0.3s 持续确认），节流不破坏逻辑
- 现有零订阅，改造无破坏性

### 6.3 死亡事件：UnitDiedEvent 改造 + 死因区分

**现状**：`UnitDiedEvent{ UnitController Unit }` 已存在，订阅方 = RulerController（君主阵亡→GameOver）+ TopLeftHUD（清君主引用停刷新）。

**改造方案**：
```csharp
public enum DeathCause { Killed, Demolished }   // 被击杀 / 玩家拆除

public readonly struct UnitDiedEvent {
    public readonly IDamageable Unit;      // 类型从 UnitController 改 IDamageable（建筑也走此事件）
    public readonly Faction Faction;
    public readonly Vector2 Position;
    public readonly IDamageable Killer;    // 击杀者（可为 null）
    public readonly DeathCause Cause;      // 新增：区分被击杀/拆除
}
```

**现有订阅方影响（已核实，改动可控）**：
- `RulerController.OnUnitDied`：判断 `evt.Unit == monarchUnit` → 改为 `evt.Unit as UnitController` 判等（君主是 UnitController）
- `TopLeftHUD.OnUnitDied`：判断 `evt.Unit != _monarch` return → 同上加类型判断
- 建筑被打爆也走此事件（不再单独发 BuildingDestroyedEvent，见 6.4）

### 6.4 拆除 ≠ 被击杀（修复现状缺陷）

**现状缺陷**：`Building.Demolish()`（玩家主动拆除，按 hp 比例退款）和 `TakeDamage` 致死都调 `Die()`，发同一 `BuildingDestroyedEvent`，不区分死因 → 击杀统计/全灭判定会被拆除污染。

**修复方案**：
- `Die(DeathCause cause)` 加参数：被击杀 `Die(DeathCause.Killed)`，拆除 `Die(DeathCause.Demolished)`
- 拆除流程：`Demolish()` → 退款 → `Die(DeathCause.Demolished)` → 发 `UnitDiedEvent{Cause=Demolished}`
- 被击杀流程：`TakeDamage` 致死 → `Die(DeathCause.Killed)` → 发 `UnitDiedEvent{Cause=Killed}`
- 订阅方按 Cause 过滤：击杀统计/全灭判定只认 `Killed`，忽略 `Demolished`
- `BuildingDestroyedEvent` 退役（BuildingPanel 改订阅 `UnitDiedEvent` 且 `Cause==Killed` 时关面板；拆除时面板也应关，可不过滤 Cause）

### 6.5 死亡订阅方（倒推事件数据）

| 订阅方 | 用途 | 需要数据 | Cause 过滤 |
|--------|------|---------|-----------|
| RulerController（现有） | 君主阵亡→GameOver | Unit | 不限 |
| TopLeftHUD（现有） | 清君主引用停刷新 | Unit | 不限 |
| NPC 决策/AI（3.0.1） | 威胁解除/重选目标 | Unit | Killed |

### 6.6 注册表死亡清理（DamageSystem 责任）

victim 死亡后，DamageSystem 内部三张表的清理责任（订阅 `UnitDiedEvent` 自清）：

| 表 | 清理动作 | 时机 |
|----|---------|------|
| `attacker → target` 注册映射 | 删除以 victim 为 target 的映射项；若 victim 是 attacker，整项删除并取消 CD 回调 | victim 死亡 |
| `target → 当前受击数`（过度杀伤计数） | 删除 victim 计数项 | victim 死亡 |
| `victim → lastEventTime`（节流字典） | **回池重置时清**，否则新 NPC 复用实例继承上辈子"最近被打"状态 | 对象池回池重置 |

**对象池回池重置清单**（UnitFactory 改造时必须含）：清 currentHp 重置为 maxHp、清状态/焦点、清 lastEventTime 字典项、清注册映射项。回池实例复用做字典 key，必须重置干净。

### 14.2 核心架构决策详解

#### 决策 1+5+6：IDamageable 统一抽象（建筑与 NPC 共用伤害管线）

**现状（已核实）**：UnitController **已有完整战斗链路**（AttackUnit/TakeDamage(int,UnitController)/Die/Heal(int) + 四事件 + ISaveable 存档），Building 已有部分（TakeDamage(int)/Die/Demolish + 非ISaveable/无Heal）。两者都有 TakeDamage 但签名不同、公式分散。

**决策**：
- 提取 `IDamageable` 接口（`TakeDamage(int finalDamage)` / `CurrentHp` / `MaxHp` / `GetPosition()` / `GetFaction()` / `Heal(int)`）
- `UnitController` 实现 IDamageable：现有 `TakeDamage(int, UnitController)` **重构**为 `TakeDamage(int finalDamage)`（去 source 参数、去内部公式，公式搬 DamageSystem）；Heal 已有保留
- `Building` 实现 IDamageable：现有 `TakeDamage(int)` 签名兼容；补 Heal 空实现（建筑不回血）
- `UnitDiedEvent.Unit` 和 `Killer` 改为 `IDamageable` 类型，加 `DeathCause Cause`（见决策 23）
- 建筑被打爆复用 `UnitDiedEvent`，BuildingDestroyedEvent 退役

**连锁影响**：
- ✅ 一套 DamageSystem 管所有可受伤对象
- ✅ 箭塔作为可受伤实体注册（只受击不主动攻击，不调 RegisterAttack）
- ⚠️ UnitController.TakeDamage 重构是动已有可用代码（【重构】非新建），需回归测试存档/Heal
- ⚠️ 现有 UnitDiedEvent 订阅方（RulerController/TopLeftHUD）取 Unit 要加 `as UnitController` 类型判断
- 📌 后续若出现建筑自己攻击（如弩箭塔），建筑也调 RegisterAttack 即可，架构已支持

#### 决策 2+8：NPCBrain 主动注册 + 回调式执行

**问题**：NPCBrain 怎么告诉 DamageSystem"我要攻击"？这是 AI 与伤害管线的核心接口契约。

**决策**：
- `NPCBrain` 选定目标后调 `DamageSystem.RegisterAttack(attacker, target)` 进队列
- `DamageSystem` 持有 `attacker → target` 映射，CD 到点回调 `attacker.ExecuteAttack()`
- 换目标调 `UpdateRegistration(attacker, newTarget)`
- 撤销攻击调 `Unregister(attacker)`
- 首次攻击：注册后立即打一次，然后进 CD（战斗开局不僵）

**为什么不用 DamageSystem 每帧查意向**：与 3.0.1 焦点驱动一致——AI 主导决策，DamageSystem 只管执行 + 性能优化（时间轮/分片/空间分区）。DamageSystem 不关心"为什么打"，只关心"到点了帮你打"。

#### 决策 3+7：改造 UnitDamagedEvent + 节流（3.0.1 闭环硬依赖）

**现状（已核实）**：`UnitDamagedEvent{ UnitController Unit, UnitController Source, int ActualDamage }` **已存在且零订阅**。新建 UnitHitEvent 会造出语义重复事件。

**决策**：
- **改造 UnitDamagedEvent**（不新建）：Unit/Source 类型改 IDamageable，加 `Vector2 Position`
- 节流：同一 victim 每 0.5s 最多发一次（DamageSystem 维护 `victim → lastEventTime` 字典）
- 3.0.1 ThreatStimulus 订阅 `UnitDamagedEvent` 触发威胁 3
- 3.0.1 威胁升级本身有滞回（0.3s 持续确认），节流不破坏逻辑
- 现有零订阅，改造无破坏性

**为什么不新建 UnitHitEvent**：复用现有零订阅事件，避免两个语义重复的事件并存。审查意见正确指出这一点。

#### 决策 4+18：时间轮 0.1s tick + CD 取整

**决策**：
- 时间轮 tick = 0.1s（10 帧 tick 一次）
- CD 向上取整到 0.1s 倍数（1s=10 槽，1.5s=15 槽，1.3s=13 槽）
- 500 NPC × 10 tick/s = 5000 检查/s，可接受
- 单层时间轮，CD 最大值决定槽数（如最大 10s CD = 100 槽）

**为什么不用 1 帧 tick**：500×60=30000 检查/s，开销大且 CD 1s 要 60 槽内存浪费。0.1s 精度玩家感知不到误差。

#### 决策 9+10+12：位置驱动投射物 + 到达时刻位置检测 + 误伤

**问题**：投射物飞行中目标死了/跑了怎么办？友军误伤怎么处理？远程对移动单位是否有效？

**决策**：
- 投射物**位置驱动**：发射时锁定目标位置（非目标对象），算 `t = 距离/弹速`
- 飞行中**纯插值**（抛物线，3 个浮点运算），**不做碰撞检测**
- **到达时刻**做一次位置检测：目标位置 **1 格**半径范围内的非己方单位，命中最近一个（MaxHits=1）
- 原目标跑了 + 无其他单位在范围内 = miss
- 原目标跑了 + 友军/其他敌人在范围内 = 误伤命中（Faction 二元判定，非己方即打）
- 无闪避率，仅靠位移躲远程（目标跑出 1 格范围 = miss）

**联调修正（审查指出）**：原占位弹速 10/s + 判定 0.5 格 → 箭飞 1.13s 目标必出圈 → 远程必 miss。联调后弹速 25/s + 判定 1 格（见 10.4），最大射程能命中移速 3/s 的目标。

**架构洞察**：这个模型调和了"碰撞性误伤"和"只插值不碰撞"两个看似矛盾的需求——飞行中零碰撞（轻量），到达时刻一次位置检测（实现误伤）。500 投射物每帧 = 500 次插值，可控；贵的检测只在到达时刻做一次。

**关键边界**：投射物发射后独立存在，不追踪原目标，不追踪发射者。发射者和原目标的后续状态都与投射物无关。

#### 决策 13+19：近战选最近 + 过度杀伤硬上限换目标

**决策**：
- 近战查 1 格内敌方，选距离最近的一个
- 过度杀伤硬上限 2：某目标被 2 个近战锁定后，多余近战查格选**次近**敌方
- 若无其他目标，近战往前走接近（不排队等待）

**为什么硬上限**：防一堆近战集火同一目标导致伤害溢出（100 血被打 200）。硬上限强制分流，提升整体杀伤效率。

#### 决策 16：Heal 复用（已实装，对接粮食消耗）

**现状（已核实）**：`UnitController.Heal(int)` **已实装可用**（含存活校验+UnitHpChangedEvent 发布），非"预留"。Building 无 Heal。

**决策**：复用 UnitController 现有 Heal(int)；Building 补空实现（建筑不回血）。首版不触发回复（无粮食消耗驱动），后续资源系统对接 Heal 接口。

**架构洞察**：血量回复不是伤害管线的事，是资源系统的事。Heal 接口已就绪，只等资源系统调用（粮食消耗→回血/医疗建筑回血都走 Heal）。

#### 决策 21-27：审查修订新增决策

- **21 int 取整**：DamageSystem 内 float 算百分比减伤 → RoundToInt + 保底 1 → int 链路不动（UI/存档零影响）。详见 5.3。
- **22 MaxHits**：承接 3.0 总览 Range+MaxHits 解耦契约，首版=1（单发），投石机=N（P2）。详见 4.2。
- **23 拆除≠被击杀**：Building.Die 加 DeathCause 参数。Demolish→Demolished，被击杀→Killed。击杀统计只认 Killed，防拆除污染。BuildingDestroyedEvent 退役。详见 6.4。
- **24 死亡清理**：DamageSystem 订阅 UnitDiedEvent 自清三表（attacker→target 映射/过度杀伤计数/节流字典）。回池重置时清节流字典项防继承。详见 6.6。
- **25 stub 解耦**：3.4 主体独立于 3.0.1，StubAttacker 斩断实现顺序循环。详见 1.4。
- **26 护甲复用 defense**：复用 UnitData.defense / CombatConfig.defense，不新立 armorBase。详见 5.2。
- **27 三轨数值**：NPC→NpcProfessionDef(继承UnitData) / 建筑→BuildingDef.combat / 全局→DamageConfig。详见九。

### 14.5 性能与交互决策要点

**性能侧**：
- 时间轮 0.1s tick：500 NPC × 10/s = 5000 检查，同帧到点的可能只有几十个
- 分片 100/帧：抹平 CPU 尖峰
- 投射物飞行纯插值：500 投射物 = 500 次浮点运算/帧，可控
- 检测只在到达时刻：贵的位置检测每投射物只做一次
- 双对象池（NPC + 投射物）：零 GC
- UnitDamagedEvent 节流 0.5s：防订阅方刷爆

**交互侧**：
- 无 RNG（无浮动无暴击无闪避）：验证场景可预测，3.0.1 威胁评定不受随机影响
- 仅靠位移躲远程：玩家能理解"跑开就躲箭"
- 投射物误伤：友军挡在前排会被自己弓箭手射中，战术深度
- 受击闪红 + 死亡消失：最轻量反馈，3.0.1 验证够用（看 NPC 是否撤退）
- 君主不攻击：3.4 首版范围明确，只管 NPC vs NPC
- 拆除≠被击杀：玩家拆除不污染击杀统计
