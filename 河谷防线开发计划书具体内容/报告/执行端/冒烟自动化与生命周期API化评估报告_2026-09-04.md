## 一、结论先行

1. **冒烟自动化完全可行，且改动量很小**——你担心的「缺失的 API」大部分**已经存在**，只是散在多个门面里，没有封装成冒烟专用的一条龙入口。
2. **不需要「全模块 API 化」大重构**——现有架构（Singleton 门面 + EventBus 事件解耦 + LoadManager/TeardownManager 生命周期总管）已是「半 API 化」，冒烟/工具/外部调用所需接口基本齐备。真正的缺口只有 **1 个**：同场景内「清场→重建」的封装门面。
3. **建议路线**：保留现有架构，补一个 `WorldLifecycle`（生命周期门面）+ 一个 `SmokeApi`（冒烟专用建局/清场），即可实现「用户零手动进局」的自动冒烟，同时为未来工具/测试/Mod 提供统一外部调用面。

### 2.2 清场链路（已存在，三级 API）

[TeardownManager.cs](file:///c:/Users/trs/Desktop/Valley%20Rampart/Valley%20Rampart/Assets/_Game/Systems/Loading/TeardownManager.cs) 三级 API：

- **Level 1 `TeardownScene()`**：场景级清理（反注册+销毁所有单位+清君主引用），读档/新建前用。
- **Level 2 `TeardownForReturnToMenu(bool save)`**：停输入→恢复 timeScale→(可选存)→TeardownScene→**业务 Manager 全家 ResetState**（Time/Difficulty/Ruler/KingdomManager/PopulationSystem/RanchSystem/SiegeProductionSystem/WorldManager/SaveManager）→清 UnitRegistry→**LoadScene 回主菜单**。
- 配套重置/清空散点：`WorldManager.ResetState()`（清 ActiveMap）、`GridSystem.ClearAll()`、`BuildingFactory.ClearAllBuildings()`、`ChestManager.ClearAll()`、`KingdomRegistry.ResetState()`、`MapRenderService.ClearAllTiles()`、`AttentionSystem.ClearAll()`。

### 2.3 现有架构的「半 API 化」特征

- **统一生命周期门面**：LoadManager（加载时序）/ TeardownManager（销毁时序）——已把「进/出」封装成对外门面。
- **事件解耦**：EventBus（`ConfigsLoadedEvent`/`UnitDiedEvent`/`TimeDayChangedEvent`…）——系统间松耦合调用。
- **单例门面**：各系统 `Instance.xxx()`——外部直接可调，无需了解内部实现。
- **场景桥**：GameSceneEntrance——跨场景传参标准化。

> 结论：冒烟/工具/外部调用真正需要的，不是「再造接口」，而是 **「把已有接口编排成一条龙」**。

## 三、冒烟自动化的可行方案（改动量小）

### 3.1 方案：`SmokeApi` + `WorldLifecycle` 门面

```
冒烟容器（Editor 脚本，Menu 触发）
   │
   ├─ SmokeApi.EnterGame(NewGameConfig{raceId, seed固定, ...})   // 新建门面
   │     └─ 复用 InitializeNewGame（等价用户进局，走真实链路）
   │
   ├─ 跑探针（现有容器逻辑不变）
   │
   ├─ SmokeApi.ResetWorldForNext()        // 新建门面（本报告核心缺口）
   │     └─ Level 1.5 同场景重建：
   │        停输入 → TeardownScene → 业务 ResetState 全家
   │        → GridSystem.ClearAll / BuildingFactory.ClearAllBuildings
   │        → ChestManager.ClearAll / KingdomRegistry.ResetState
   │        → MapRenderService.ClearAllTiles / UnitRegistry.Clear
   │        → WorldManager.ResetState（清 ActiveMap，解锁二次建局）
   │        → SaveManager.ResetSessionState
   │        （不 LoadScene，留在 GameScene）
   │
   ├─ 循环「建局→探针→清场」N 轮（多轮回归/跨族验证）
   │
   └─ 全部完成 → TeardownForReturnToMenu(false) 或退出
```

### 3.2 为什么可行（实证依据）

1. `WorldManager.ResetState()` 已清 `_world=null` → **ActiveMap 置空**；批2 实测的「二次初始化卡死」只发生在 ActiveMap 仍存在时再 `InitializeNewGame`。清场后重建即解锁。→ **同场景多轮建局技术上通**。
2. `InitializeNewGame` 已支持 `raceId` 直填 → **选族 API 化，无需 UI**。
3. 批2 冒烟已验证「等 Ready→InitializeNewGame→等 ActiveMap」全链路可跑。
4. 固定 seed → 世界稳定 → **比用户随机进局更可复现**（批2 已吃用户世界 70+ 野怪噪声的亏，自动化反而更稳）。

### 3.3 需要新增的代码（均为薄封装，复用现有接口，不碰业务逻辑）

| 新增 | 内容 | 体量 |
|---|---|---|
| `WorldLifecycle`（门面） | `ResetWorldForNext()`：编排 2.2/2.3 的现有 ResetState/ClearAll 序列 | 约 60 行 |
| `SmokeApi`（冒烟专用） | `EnterGame(config)` / `ResetWorldForNext()` / `QuitSmoke()` 薄封装 | 约 40 行 |
| 冒烟容器改造 | 现有 2_20/2_20B 容器开头改调 `SmokeApi.EnterGame`，结尾改调 `SmokeApi.ResetWorldForNext` | 每容器约 20 行 |

> 不新增业务逻辑、不改现有系统内部，只「编排」已存在接口。**回归风险极低**。

### 3.4 需要策划端裁决的点

1. **冒烟是否要求「固定 seed 多轮 + 跨四族全覆盖」**（推荐：每轮固定 seed，四族各建一局，共 4 轮自动跑）？
2. **自动化冒烟与「用户真机进局冒烟」的关系**：是取代（自动化为主、真机为辅）还是并存（真机保留为最终验收）？——建议并存：自动化负责日常回归，真机保留为每批最终验收。
3. `SmokeApi` 是否允许进「主流程代码」还是限定 `Assets/Editor`（Editor-only，不进构建）？——建议 Editor-only，零运行时开销。

## 四、模块 API 化设计的评估（你问的核心问题）

### 4.1 两种路线对比

| 维度 | 路线 A：门面补全（推荐） | 路线 B：全面模块 API 化（服务注册/依赖注入） |
|---|---|---|
| 内容 | 保留 Singleton，把高频跨模块调用编排成有限门面（WorldLifecycle/SmokeApi） | 每模块改「接口契约 + 服务注册表/DI 容器」，消费方只依赖接口 |
| 优点 | 改动小、回归风险低、立即见效；与 LoadManager/TeardownManager 现有思路同构 | 可测性最强（可 mock）、模块可替换、未来 Mod/多端/热更友好 |
| 成本 | 每个门面 40~60 行 | 全部系统接口化+注入改造，涉及现网全部 `Instance.xxx` 调用点，量级巨大 |
| 风险 | 极低 | 高：大规模回归、重构期功能冻结、双份心智（接口+实现） |
| 适配现状 | 现有 EventBus 已解耦事件；门面只补「时序编排」 | 与现有直接引用体系冲突，需迁移期 |

### 4.2 评估结论

- **现状已是「半 API 化」**：生命周期进出（LoadManager/TeardownManager）、事件（EventBus）、跨场景（GameSceneEntrance）、单例门面——外部调用所需大部分接口**都在**。缺的只是「编排」层。
- **全面 API 化对本项目当前阶段的净收益为负**：单机单团队、无多端/热更/Mod 需求、重构期功能冻结不可接受。**不建议现在做路线 B**。
- **建议**：走路线 A（门面补全）。它本身是路线 B 的「轻量前奏」——门面即接口，未来若真要服务化，门面可直接演化为接口实现，迁移成本低。
- **若策划端仍倾向路线 B**，建议至少满足三个前提之一再动：① 出现明确的多端/Mod 需求；② 单测覆盖率达到可兜底重构回归；③ 抽出独立时间窗（不与其他批并行）。

## 七、策划端裁决记录（2026-09-04，D520）

**实盘复核**：四项关键声明全属实——`LoadManager.InitializeNewGame` 门面（WorldSystem.InitializeWorld+SpawnMonarch+EnterPlaying 直读）/`TeardownManager` 三级 API 直读/`WorldManager.ResetState` 清 `_world=null`（ActiveMap 置空实证）/批2 冒烟 `Valley2_20_Smoke_Race.cs` 直调 InitializeNewGame 含「二次建局卡死仅发生在 ActiveMap 未清时」注释原话。**加分发现**：`TeardownForReturnToMenu` 的 Manager 重置清单不含 GridSystem/BuildingFactory/ChestManager/KingdomRegistry/MapRenderService 散点（靠 LoadScene 换场景兜底）——报告 §3.1 WorldLifecycle 编排清单已全部列入，同场景重建缺口识别无遗漏。

**四项裁决（用户拍板，D520）**：

| # | 裁决点 | 结论 |
|---|--------|------|
| ① | 总路线 | **路线 A+接口纪律条款**：门面补全（WorldLifecycle+SmokeApi）+新系统接口纪律软条款；全面模块 API 化（路线 B）否决。否决理由：sim 同源架构已是更彻底的前后端分离（纯 C# 决策核=后端，Unity/harness=双前端消费者）；DI 容器与 Unity 场景生命周期天然冲突（场景重载后注入引用失效）；白盒单测职责已由训练仓 harness 承担，Unity 侧缺黑盒冒烟不缺 mock。B 保留三前提（多端/Mod 需求、单测覆盖兜底、独立时间窗），触发时门面可直接演化为接口实现 |
| ② | 冒烟策略 | **四族固定 seed 各建一局（4 轮）+周批回归追加换 seed 1~2 轮**——单固定 seed 把世界多样性缺陷面压缩到 1/N（寻路1 微格契约/寻路2 出生口袋吸附均为 seed 相关缺陷实证教训） |
