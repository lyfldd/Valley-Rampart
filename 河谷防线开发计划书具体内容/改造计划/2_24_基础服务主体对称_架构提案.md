# 2.24 基础服务主体对称——架构提案（✅ 已拍板定稿）

> 类型：架构原则提案（D545 立项 → **D605 用户拍板通过，2026-09-10 定稿**；实施计划=《2_24_基础服务主体对称_实施计划.md》）
> 日期：2026-09-06 · 起草：策划端 · 触发：P1 三考后用户架构指示（「底层基础模块不应硬编码为玩家、AI 走特殊通道，应改为全局可调用」）
> 关联：HH.79/80/80 三考三卡死点 · HH.84 依赖完整性审计总纲（主体耦合度清单联动）· D520 接口纪律条款 · AI 北极星

## 一、原则陈述（一句话版）

**底层基础模块对王国主体的服务必须对称——`kingdomId` 是一等公民参数（0=玩家 / >0=AI / -1=无主），同一条 API 通道服务所有主体；基础模块层禁止「玩家硬编码路径 + AI 特殊通道」的双轨形态。**

- 「对称」≠「无差别」：阵营敌对/玩法规则差异（野怪敌意/玩家 UI 专属）仍在更上层（规则层/AI 决策核）处理——本原则约束的是**基础设施服务**（资源/人口/建筑/水网/税收/任务/存档/事件），不是游戏规则。
- 「全局可调用」的边界：模块间通信仍走 D520 裁定（EventBus+门面），本原则不改通信形态——改的是**模块对主体的服务签名与内部路由**（主体参数化，去特权路径）。

## 二、问题：双轨形态=断链温床（P1 三轮实证）

现状模式：基础模块为玩家设计（硬编码 kingdomId=0/Faction.PlayerCamp/桶 0 专属/玩家侧全局读数），AI 消费时逐个「开特殊通道」（AI 桶/AI 分支/守卫绕行/per-kingdom 补丁）——**每修一层暴露一层**（P1 大考逐层显形实况：粮→人口→招工/住房）。

| 双轨形态案例（已实锤） | 断链后果 |
|----------------------|---------|
| WaterNetwork 玩家单桶 → AI 补 AI 桶+AI 井分支（HH.73） | AI 农田断水停产（二轮熔断根因） |
| PopulationSystem 玩家专属繁殖（Faction.PlayerCamp 硬编码+桶 0 配对池+玩家侧全局读数）→ AI 补 OnNewDayPerKingdom（HH.78） | AI 人口零再生（二轮熔断） |
| VagrantCampSystem 流浪 kingdomId 硬编码 0（「未入籍=-1」设计从未实装）→ AI 招工恒拒（HH.81 修 -1） | 招工静默失败（三轮熔断） |
| HappinessSystem 玩家全局幸福/房容 → AI 补 per-kingdom 读口（HH.79） | AI 生育条件读错主体 |
| PlaceVagrantCamps 幽灵引用（HH.78） | 补员链永不触发 |

**结构性结论**：每条「玩家轨+AI 特殊通道」都是一次语义分叉，分叉点=断链候选点；特殊通道的开通依赖人工记忆（挂账），记忆失效=断链（P5 模式）。**双轨形态本身是缺陷生成器。**

## 三、目标态

1. **单轨参数化**：基础模块公开 API 一律携带 `kingdomId`（或 KingdomState/主体句柄）参数——调用方声明主体，模块内部按主体路由，无主体特判分支（除明确设计语义：如阵营敌对判定）。
2. **无主态一等公民**：`-1`（无主/未入籍）与 `0`（玩家）/`>0`（AI）同为合法主体态——生成端必须显式声明（禁止依赖默认 0）。
3. **条件数据 per-kingdom**：模块内部的状态桶（幸福/饱食/房容/水/冷却）一律 per-kingdom，读口带 kingdomId（批3a/HH.79 基建模式推广）。
4. **失败可见**：主体路由的每个拒绝分支必须日志（含主体 id+原因）——静默失败禁令。
5. **玩家=普通调用方**：玩家侧回归保障从「玩家轨不动」改为「冒烟全集兜底」（现网冒烟容器=玩家路径回归测试集）。

## 四、分级推进（控回归风险）

| 级 | 范围 | 规则 |
|---|------|------|
| 即时 | **新代码** | 接口纪律条款（D520）扩展：新系统/新 API 强制主体参数化，禁玩家硬编码（评审把关项） |
| 短期 | **已暴露模块** | P1 三考已双轨化的模块（WaterNetwork/PopulationSystem/VagrantCampSystem/HappinessSystem）维持双轨运转，**参数化改造归入审计耦合度清单排序**——不立即返工（沉没成本），按暴露面+P0 数据排批次 |
| 中期 | **存量普查** | HH.84 审计主体耦合度清单=改造原料清单（每处标记量级：小=守卫改判定/中=分支合并/大=数据源重构），按清单立架构批 |
| 长期 | **全量对称** | 与 2_23「资源第一性」域合流——基础服务对称是资源第一性的前置地基 |

## 五、与既有决策的关系

- **D520（冒烟自动化与架构 API 化路线）不推翻**：D520 否决的是「模块间通信全面 web 式 API 化」（通信形态）；本提案约束「模块对主体的服务对称性」（主体参数化）——正交且互补（D520 接口纪律条款直接扩展复用）。
- **AI 北极星下沉**：北极星要求 AI 与 sim 全同源——sim 侧（harness）本就无玩家特权（纯 C# 对所有王国同构），Unity 侧玩家硬编码=15_账本 #7/#8 类差异的源头。主体对称=Unity/sim 同构度提升=**训练回灌保真提升**（本提案最硬的论据）。
- **2_23 资源第一性同构**：「资源第一性，模块派生」要求资源服务对主体对称——本提案是其基础设施层前置。

## 六、风险与回归策略

- 玩家回归：参数化改造=玩家路径也要动，回归风险真实存在——策略=每批参数化必须过现网冒烟全集（玩家路径回归测试集）+P1 式长局抽查；改造批次小步走（一模块一批）。
- 工程量：存量双轨点=审计耦合度清单计数（预计 10~20 处，量级小中为主——大件仅数据源类）；不设死线，随批携带。
- 命名预留：本提案若拍板，原则名=「基础服务主体对称」（文档版本历史记用户原话出处）。
