### 步骤 3：WorldSaveData → v3 + 种子复现读档主链路

**文件**：`Systems/World/WorldManager.cs`（旧 v2 迁移）+ `Systems/World/WorldState.cs`

旧 v2 字段（`mapSeed/worldSeed/worldSize/activeMapId/mapsMeta/conqueredMapIds/difficulty`）→ v3：

```csharp
[System.Serializable]
public class WorldSaveData
{
    public int version;           // = 3
    public int worldSeed;         // 底图复现种子（2_1 确定性契约）
    public int worldSize;         // (int)WorldSize / MapSizeConfig 2D 档位 id
    public int activeMapId;       // 恒 0（单图冻结）
    public string mapsMeta;       // 壳保留（单元素），加载后忽略多岛字段
    public string conqueredMapIds;// 冻结（恒空）
    public string mapHash;        // 新增：存档时刻 MapData 摘要（§3.1 校验）
    public int difficulty;
}
```

**读档主链路（新步骤，Global 阶段）**：
```
WorldManager.LoadState（Global 阶段）：
  1. 按 worldSeed + 尺寸档位重生成 MapData（含地形/水域/资源节点底/kingdomSpawns 预留，2_1）
  2. 校验 mapHash：一致 → 正常走；不一致 → 生成器被改动破坏确定性/存档损坏 → 走 §3.3 显式提示流程
  3. 禁止静默用不一致的底图读档（建筑坐标会落错地）
```

**配套**：
- `SpawnDef`（威胁/王国出生点）**不落档**：由种子复现派生；`faction` AI 王国值仅预留
- `WorldState.maps` 壳保留永远单图（doc 1 §2.5 冻结决策存档侧兑现）
- `mapHash`：存档时对 MapData 关键字段（尺寸/地形数组摘要/资源节点数量与坐标）取稳定哈希。**mapHash 算法（占位）：SHA-256，输入=seed + mapSize + resourceSeed 依序拼接（字段顺序固定，保证确定性）（2026-08-14 终审修订，D2XX）**

**验收**：同 seed + 档位重生成底图与存档 mapHash 一致（S3）；生成器被改后读档走显式提示（S4 变体）。

### 步骤 4：saveVersion 升 2 + 显式清档流程

**文件**：`Systems/Save/SaveManager.cs` + `Core/SaveableContracts.cs`

旧 `CurrentSaveVersion = 1`（只拒高版本）→ 升级：

```csharp
public class SaveManager : Singleton<SaveManager>
{
    private const int CurrentSaveVersion = 2;               // 1（1D）→ 2（2D）
    private const int MinimumSupportedSaveVersion = 2;      // 新增：低于此版本拒载
    // 其余（槽位/JSON/原子写盘/自动存档/DaySettled/GameOver 死档标记）全保留，零重构
}
```

**ISaveable 澄清（2026-08-14 终审修订，D2XX）**：接口不变（`LoadState/SaveState` 签名不动）；版本迁移在 SaveManager 层由 MigrationRegistry 于 LoadState 前做 JSON 文本级逐级改写，`ISaveable` 模块不感知版本。

**显式清档流程（§3.3 / D242~D244）**：
```
Load(slot) → saveVersion < MinimumSupportedSaveVersion（即 1D 旧档）
  → 拒载（不设 CurrentSlotId，防死档标记污染——沿用现有 LC-G3 修复）
  → 发 SaveIncompatibleEvent(slotId, 存档版本, 当前最低版本)
  → UI 弹窗："该存档为旧版本（1D），与当前 2D 版本不兼容"
     → [删除该存档] → SaveManager.Delete(slot)
     → [保留不玩] → 返回存档列表（文件保留，标记不兼容）
```

- **禁止**静默转换 1D→2D（y=0 横排世界无映射面）；**禁止**静默删档（玩家数据处置必须玩家确认）
- 改造期（阶段 0~3）开发档全部视为可作废：每次 saveVersion 升档后，开发用旧档走同一显式流程，不特殊豁免
- 迁移失败 → 显式提示 + **备份旧档不覆盖**（D244）

**验收**：拿 1D 旧档（saveVersion=1）读档 → 拒载 + 显式不兼容弹窗 + 可选删档（S4）；不静默转换、不静默删。

### 步骤 5：读档顺序铁律（三段式 + 后置重建）

**文件**：`SaveManager.cs`（加载顺序注释固化）+ 各模块 LoadState

设计 §3.2 铁律落地（现有三段式天然满足，实施时把顺序写进冒烟项）：

```
Global 阶段：WorldManager.LoadState → 种子复现 MapData + mapHash 校验
             TimeManager/Ruler/Kingdom 等常驻系统恢复
    ↓
Spawn 阶段：BuildingFactory.SpawnFromSave（需要 MapData 判可放/复盖阻挡位）

    ↓

```

**铁律：MapData 复现必须先于一切 Spawner。**

**验收**：读档顺序冒烟项通过——底图先复现，建筑/单位重建判位正确，后置重建清单全绿（S6）。

### 步骤 7：MigrationRegistry 迁移链（P1）

**文件**：新建 `Systems/Save/MigrationRegistry.cs`

设计 §3.3 迁移体系落地：

```csharp
public static class MigrationRegistry
{
    // 注册：(模块 saveId 前缀或类型名, fromVersion) → 迁移函数（JSON 文本级改写）
    public static void Register(string typeName, int fromVersion, Func<string, string> migrator);
    // LoadState 前调用：把 payload.json 从旧版逐级迁到当前版
    public static string Migrate(string typeName, int fromVersion, string json);
}
```

**迁移链规则**：
- 逐级执行（v2→v3→v4…），任一环节缺失 → 视为不可迁移 → 走显式提示流程（D242）
- **注册时机（2026-08-14 终审修订，D2XX）**：SaveManager.Awake 静态注册（一次性，全模块迁移器表）
- JsonUtility 特性利用：**新增字段缺省值天然向前兼容**（旧档读新字段得默认值），迁移器只处理三种情况：字段改语义、字段拆分/合并、旧值需要换算。纯加字段的版本升不需要迁移器
- 全局版本（`GameSaveRoot.saveVersion`）管跨模块大版本；模块版本（`SavePayload.version`）管模块内小版本

**验收**：模块版本迁移链逐级可执行；缺环节 → 显式提示；纯加字段版本升无迁移器即可读。
