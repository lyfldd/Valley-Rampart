## 一、老系统与新系统的衔接

### 1.1 现状（存档架构盘点）

现有存档系统（`Systems/Save/SaveManager.cs` + `Core/SaveableContracts.cs`）：

| 组件 | 职责 | 处置 |
|------|------|------|
| `SaveManager` | 槽位（slot_1~3）/JSON 序列化/原子写盘（.tmp 替换）/自动存档（DaySettledEvent 驱动）/GameOver 死档标记 | **保留**，仅升 `saveVersion` + 接迁移器 |
| `ISaveable` | SaveId/LoadPhase/SaveState/LoadState，模块自治序列化 | **保留**（2026-08-14 终审澄清）：接口不变（LoadState/SaveState 签名不动）；版本迁移在 SaveManager 层由 MigrationRegistry 于 LoadState 前做 JSON 文本级逐级改写，ISaveable 模块不感知版本 |
| `ISaveableSpawner` | SaveIdPrefix 前缀认领，Scene 阶段前重建实例 | **保留** |
| `SavePayload.version` | 模块自治版本号（独立于全局 saveVersion） | **保留**，本篇启用其迁移语义 |
| `SaveLoadPhase` | Global（常驻系统）→ Spawn（重建实例）→ Scene（实例恢复状态）三段式 | **保留**，新增顺序约束（§3.2） |
| `GameSaveRoot.saveVersion` | 全局结构版本，当前 = 1，只拒高版本 | **升级**：加"最低支持版本"判定 + 显式清档 |

**架构结论：零重构。** SaveManager 是纯搬运层（不懂业务字段），2D 化的全部代价落在各模块的 SaveData 字段与迁移规则上。

### 1.2 现有存档数据结构盘点（1D 时代坐标字段）

| SaveData | 位置 | 坐标相关字段（现状） | 2D 处置 |
|------|------|------|------|
| `BuildingSaveData` | Building/ | `coordX`（int，读档时 `GridCoord(coordX, 0)` 硬编码 y=0） | **改**：+`coordY`、+`cellHeight`、+`gateOrientation`（2_2 §3.4）→ v2 |
| `UnitSaveData` | Unit/（UnitController.cs） | `posX/posY`（世界 float，1D 时 posY≈0）、`birthCampX/Y` | **改语义**：存等轴嵌入世界坐标（HH.3 裁决 2026-08-22，迁移待落）；正交时代测试存档随全局拒载 → v6 |
| `WorldSaveData` | World/（WorldManager.cs，已 v2） | `mapSeed/worldSeed/worldSize/activeMapId/mapsMeta/conqueredMapIds` | **改**：+尺寸档位显式化、+地图哈希；maps 壳冻结单图 → v3 |
| `TimeSaveData/RulerSaveData/KingdomSaveData/PopulationSaveData/RanchSaveData/SiegeProductionSaveData/WaterNetworkSaveData/DifficultySaveData` | 各系统 | 无坐标字段 | **不动**（空间无关系统，总计划原则"空间无关层零改动"兑现） |

### 1.3 衔接原则

1. **架构保留，字段换代**：SaveManager/ISaveable/Spawner/三段式加载全部保留，只动字段和版本判定。
2. **1D→2D 不可逆映射**：旧档坐标 y 恒 0、世界结构根本改变，**无合理映射面**——旧档显式作废（§3.3），不做静默转换（总计划原则 5）。
3. **派生数据不落档**：WalkFlags、微格阻挡、LOD 热度、寻路场、单位区块登记全部读档后重建（§3.4）。
4. **底图种子复现，只存增量**：地图底图由种子确定性重生成，存档只存玩家增量（建筑/资源消耗）（§3.1）。

### 2.2 UnitSaveData → v6

- `posX/posY`：语义改为**存等轴嵌入世界坐标**（HH.3 裁决 2026-08-22：逻辑=格基准，世界=等轴嵌入，CoordToWorld=GridToIso 同一映射，迁移待落）。字段名与类型不变，正交时代测试存档（v1~v5 档 y≈0）无法复原 → 随全局拒载。
- `birthCampX/Y`：同语义（王国战推迟后仅作为流浪汉营地锚点预留，坐标口径一致）。

- `saveDataVersion` 字段保留，升 6；v6 新增字段缺省值保证 JsonUtility 向前兼容（字段只增不删不改类型）。

## 三、新需求与新系统

### 3.1 底图种子复现 + 增量存档策略

**结论：底图不落全量，只存种子与增量。**

- 2_1 的地图生成是种子确定性的（同 seed + 同尺寸档位 → 同 MapData），这是本策略的前提（2_1 的验收项，读档时复验）。
- 存档内容 = `worldSeed + 尺寸档位 + mapHash + 玩家增量`。玩家增量只有两类：
  1. **建筑列表**（含资源点建筑）：读档后由 BuildingFactory 重建并复盖占格/阻挡/资源状态（grade/storedAmount/byproduct 已在档）。
  2. **无地形编辑玩法**：当前没有玩家改地形的机制，地形无增量；若后续加入，在此表补一行（不预设）。
- `mapHash`：存档时对 MapData 关键字段（尺寸/地形数组摘要/资源节点数量与坐标）取稳定哈希。**mapHash 算法（占位）：SHA-256，输入=seed + mapSize + resourceSeed 依序拼接（字段顺序固定，保证确定性）（2026-08-14 终审）**。读档种子复现后比对：
  - 一致 → 正常走；
  - 不一致 → 说明生成器被改动破坏了确定性（或存档损坏）→ 按 §3.3 显式提示，**禁止静默用不一致的底图读档**（建筑坐标会落错地）。
- `MapData` 可序列化结构（doc 1 §六承诺）保留用途：调试导出（`Resources/Debug/Maps` 已有先例）、2_9 sim 场景注入；**不进主存档路径**（全量落档体积大且与种子复现冗余）。

### 3.2 读档顺序约束（三段式的新增铁律）

```
Global 阶段：WorldManager.LoadState → 种子复现 MapData + mapHash 校验
             TimeManager/Ruler/Kingdom 等常驻系统恢复
    ↓
Spawn 阶段：BuildingFactory.SpawnFromSave（需要 MapData 判可放/复盖阻挡位）
            UnitFactory.SpawnFromSave（需要 MapData 判落点可走）
    ↓
Scene 阶段：各实例 LoadState 恢复业务状态
    ↓
后置重建：WalkFlags 全量复算 → 连通性复验 → LOD 热度清零 → 单位小区块登记 → 寻路场冷启动
```

**铁律：MapData 复现必须先于一切 Spawner。** 现有三段式天然满足（WorldManager 是 Global 阶段），实施时把该顺序写进 2_11 实施计划的冒烟项。

### 3.3 schema 版本迁移体系

**双层版本号**（沿用现有设计，补齐语义）：

| 层 | 字段 | 语义 | 本篇规则 |
|----|------|------|------|
| 全局 | `GameSaveRoot.saveVersion` | 根结构/跨模块大版本 | 1（1D）→ **2（2D）**；`MinimumSupportedSaveVersion = 2` |
| 模块 | `SavePayload.version` | 模块内小版本 | 各 SaveData 自治迁移（v2 之后的增量字段走 JsonUtility 缺省兼容，语义变更走迁移函数） |

**MigrationRegistry（P1 落地）**：

```csharp
public static class MigrationRegistry
{
    // 注册：(模块 saveId 前缀或类型名, fromVersion) → 迁移函数（JSON 文本级改写）
    public static void Register(string typeName, int fromVersion, Func<string, string> migrator);
    // LoadState 前调用：把 payload.json 从旧版逐级迁到当前版
    public static string Migrate(string typeName, int fromVersion, string json);
}
```

- 迁移链逐级执行（v2→v3→v4…），任一环节缺失 → 视为不可迁移 → 走显式提示流程。
- **注册时机（2026-08-14 终审修订，D2XX）**：SaveManager.Awake 静态注册（一次性，全模块迁移器表）。
- JsonUtility 特性利用：**新增字段缺省值天然向前兼容**（旧档读新字段得默认值），所以迁移器只处理三种情况：字段改语义、字段拆分/合并、旧值需要换算。纯加字段的版本升不需要迁移器（v1→v5 的 UnitSaveData 历史即此模式）。

**显式清档流程（总计划原则 5 落地）**：

```
Load(slot) → saveVersion < MinimumSupportedSaveVersion（即 1D 旧档）
  → 拒载（不设 CurrentSlotId，防死档标记污染——沿用现有 LC-G3 修复）
  → 发 SaveIncompatibleEvent(slotId, 存档版本, 当前最低版本)
  → UI 弹窗："该存档为旧版本（1D），与当前 2D 版本不兼容"
     → [删除该存档] → SaveManager.Delete(slot)
     → [保留不玩] → 返回存档列表（文件保留，标记不兼容）
```

- **禁止**静默转换 1D→2D（y=0 横排世界无映射面）；**禁止**静默删档（玩家数据处置必须玩家确认）。
- 改造期（阶段 0~3）开发档全部视为可作废：每次 saveVersion 升档后，开发用旧档走同一显式流程，不特殊豁免。

> **2026-08-14 决策对齐（D242~D244，0.6 二十三）**：逐级迁移（D242）、兼容字段+剔除作废（D243，如伐木场剔除）、迁移失败显式提示+备份旧档不覆盖（D244）。与本节 §3.3 完全一致。


> **2026-08-31 P5.3 落地（D432，随 2_20 前置批）——旧档废弃阵营/职业单位过滤条款**：
> 全局 saveVersion **2 → 3**（`SaveManager.CurrentSaveVersion`）；v3 起读档重建单位时（`UnitFactory.SpawnFromSave`），faction/occupation 查表（`UnitDataManager.GetData`）失败的单位（旧档含 Undead 等已删除资产的单位）→ **过滤丢弃不重建 + 日志计数**（`UnitFactory.FilteredSaveUnitCount`，读档前清零）。不炸档、不静默改数据，仅丢弃失效单位。落地：`SaveManager.Load` 清零计数、`UnitFactory.SpawnFromSave` 查表失败分支计数+日志。验收探针：含 Undead 单位旧档可载不炸 + 过滤计数日志在场。
### 3.4 派生数据不落档（读档重建清单）

| 派生数据 | 归属 | 读档重建方式 |
|------|------|------|
| WalkFlags 五位（Terrain/Building/Locked/Water/Bridge） | doc 1 / 2_2 | 底图复现得 Terrain/Water；建筑重建后复盖 Building/Bridge；Locked 随建筑锁 |
| 微格阻挡 | doc 1 | 由 WalkFlags 派生，不存 |
| 单位小区块登记 | 2_4 | 单位实例恢复后按世界坐标重新登记（微格查询=小区块候选+世界坐标比较） |
| LOD 热度 | 2_4 | 清零，从焦点重新扩散（1Hz tick） |
| 寻路场/流场 | 2_6 | 冷启动，首个寻路请求按需构建 |
| SpawnDef（威胁/王国出生点） | 2_1 | 种子复现派生，不存 |
| 连通性 | doc 1 | 底图复现 + 建筑复盖后全局复验一次（发现读档后堵死 → 告警日志 + 自动拆最近冲突建筑不可取，仅告警交人工）。**（2026-08-14 终审修订，D2XX）**：读档后连通性堵死仅告警交人工处理（拒绝读档不可取——玩家进度优先）；提供 Debug 菜单"移除堵死建筑"入口 |

### 3.5 与训练模拟器的边界

2_9 sim 的 `TuningSnapshot`/goldenReplay 走独立 JSON 通道（不经过 SaveManager/槽位），本篇不管；sim 需要地图时用种子复现同一契约（§3.1），保证训练与实战同源。
