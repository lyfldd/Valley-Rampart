# 3.0.1_5 多将军协作与管理（设计定案）

> 日期：2026-08-02
> 状态：设计定稿（用户决策，待实施）

> 本文解决：**编队自主协作**——多编队如何像多个人一样协作（玩家减负），军队 vs 个体决策如何分工（军队能承受更多代价）。

## 一、现状（单将军）

- **FormationController 挂在将军 GameObject 上**：将军死 → 组件销毁 → 编队解散（3.0.1_3 §15.1）
- 热键调试绑"将军编队"，将军死失效（已改为动态检测，见 §三）
- AIDebugSpawnController 可生成将军并 `BindGeneralFormation` 组编队（复用同一条编组逻辑）

## 二、多将军方向（明天再干，先记方向）

| 方向 | 说明 | 涉及 |
|------|------|------|
| **多编队实例化** | 多个将军各自挂 FormationController，天然多编队（架构已支持，只需验证不互抢空闲士兵） | FormationController 招募来源（空闲池） |
| **将军间协作** | 分兵（各带一队）、会师（多队合并）、援护（一队支援另一队受威胁区） | ThreatHeat 事件 / 指挥链扩展 |
| **编队归属管理** | 士兵归属哪个将军、切换指挥（士兵改绑锚点）、多队编制（军团/师） | FormationMember 归属字段 |
| **将军死亡后的部队继承** | 将军死 → 编队解散 → 士兵是否自动归入其他将军/守城编队 | OnUnitDied 链扩展 |
| **多将军调度** | 君主对多将军的指挥界面 / 军令广播 | 君主指挥链（3.0.1_3 §6） |

## 三、已为多将军做的铺垫（2026-08-02）

- **热键动态检测将军**（CombatTestSpawner.FindActiveGeneralFormation）：每次按键按"存活将军 + 非守城 + 有成员"查找，
  不再依赖缓存引用。将军死 → 热键 1/2/3/5/6/7 失效（提示），只剩 4（守城）；新将军生成组编队 → 自动恢复。
  此设计天然支持多将军（多个活跃编队时返回第一个，多编队管理待 P1 扩展）。

## 四、多编队自主协作定案（用户决策 2026-08-02）

### 4.1 核心架构：独立 FormationBrain（军队级迷你大脑）

```
FormationBrain（军队级，独立组件，挂将军或锚点）
   ├─ 意图自决：攻 / 守 / 撤 / 支援（不等君主下令）
   ├─ 输入：ThreatHeat 热点分布 / 编队存活率 / 任务价值
   ├─ 决策节奏：秒级（意图切换、阵型、价值评估）
   └─ 输出：写 FormationController（切意图）+ 军令强度
```

- 与个体 NPCBrain **完全解耦**：士兵个体复用现有三层管线零改动（玩家减负 = 士兵不需要新逻辑）
- 多编队 = 多个将军各自挂 (FormationController + FormationBrain)，天然并存
- **协作靠热点涌现**：编队 A 受击 → ThreatHeat 热点 → 编队 B 的 FormationBrain 读到 → 意图切支援（不写编队间 if-else 耦合，符合"行为从因子涌现"铁律）

### 4.2 军队任务价值动态评估（军队敢承受多少代价）

| 状态 | 任务价值 | 军队敢承受的代价 |
|------|---------|----------------|
| 攻城中（推进中） | 高 | 带伤推进，个体撤退阈值被编队抵抗抬高 |
| 守城中（城墙） | 中 | 固守待敌，被打狠才撤 |
| 巡逻 / 待命 | 低 | 一触即撤，不恋战 |

- 基础值由**锚点类型**决定（进攻目标 / 城墙 / 巡逻点）+ **动态更新**（敌军压境升价值、任务达成降价值）
- 传导链：`任务价值 → FormationBrain 维持意图 → 军令强度 → 编队抵抗 → 个体撤退阈值`
- 与 3.0.1_8 §六 放弃任务因子联动：任务价值高 → 收益封顶不弃

### 4.3 个体 vs 军队决策分工（军队承受更多代价的实现）

```
军队定：位置 + 意图 + 任务价值（秒级）
个体定：打谁 + 撤不撤（0.1s）
```

- 军队级：将军 + FormationBrain 决定"去哪、什么战术、值不值得拼"
- 个体级：士兵只决定"打眼前哪个、撤不撤"，撤退受破阵博弈 + 编队抵抗约束
- **军队比个体更敢拼不是士兵变傻**，是军令强度压住个体撤退冲动（S 级军令 + 切阵型瞬时 6.0，3.0.1_8 §七）

### 4.4 防看戏机制（协作的最终体现）

| 层级 | 机制 | 堵什么 |
|------|------|--------|
| 军队层 | FormationBrain 意图自决（读热点） | 敌压近 → 切 Charge/支援 |
| 编队层 | 将军带头推进（TaskStimulus 注入推进目标） | Charge 下全队压上 → 敌进感知 |
| 个体层 | 战斗热点支援（CombatHotspot → TaskStimulus 0.6） | 感知范围外友军也参战 |

**边界（诚实说明）**：意图=Defense 且敌人未进感知范围且无人受击 → 固守待敌，这是守势设计不是 bug。

## 五、区块改造定案（底层支撑多编队，用户决策）

> 用户决策：单个小区块可站 **12 人**，四个小区块 = 一个**中区块**，中区块最多 **4 编队**。

```
现状：小区块堆叠上限 6（GridConfig.stackLimits，6 人/格）
改造：
  1. 小区块：堆叠上限 6 → 12（翻倍）
  2. 中区块：4 个小区块编组（2×2），最多承载 4 编队（每队 6 人，留余量）
  3. LOD 热度：ThreatHeat 以中区块为粒度聚合（热点跨编队可见）
```

- 涉及：GridConfig（堆叠上限）/ GridSystem（区块划分）/ LODSystem（热度聚合粒度）
- 目的：多编队在同区域有物理空间站下，底层不被堆叠上限卡死

## 六、E 键作战面板（先接口后 UI，用户决策）

### 6.1 交互定案

- **入口**：E 键打开作战面板（接入 UIManager 的 UI 栈，ESC 关闭）
- **选队方式（混合双选）**：
  - 点击单选：点一个编队
  - 左键长按拖框：矩形框选（类 Windows 多选文件）
  - Ctrl+点击：多选追加 / 取消
  - **全选限制：单边**（只选我方或只选敌方，不混选）
- **功能**：选中编队后下发军令（攻/守/撤/支援/解散）+ 查看编队信息

### 6.2 实施顺序（后端接口先行，UI 后接——用户已确认）

```
P1 后端接口（本次实施）：
  - FormationManager：编队注册表（查询所有编队 / 按 id 选队 / 多选集合）
  - SetIntentFor(formationIds, intent)：批量下发军令
  - 事件：FormationSelectedEvent / FormationDeselectedEvent
P2 UI（UI Toolkit，后续）：
  - 面板 UXML/USS + 框选层 + 编队列表 + 军令按钮
```

- 现有热键 1-7 保留作调试，作战面板是正式操作入口
