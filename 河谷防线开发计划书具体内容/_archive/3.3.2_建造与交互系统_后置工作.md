# 🔄 建造与交互系统 · 后置工作（3.3.2）

> 2026-07-29 续 3.3 派生。本文列出 **3.3 核心（自由建造 + 放置校验 + 升级/拆除 + 通用交互 + 基础 UI）跑通后** 再迭代增强的项。
> 前置清单见 `3.3.1_建造与交互系统_前置工作.md`；主体设计见 `3.3_建造与交互系统设计.md`。

## 定位

3.3 首版目标 = 能建、能放、能点开看、能升级/拆。以下**都不是首版阻塞项**，是"先跑通再打磨"的增量。每项标注：依赖 / 收益 / 风险 / 建议时机。排序按"依赖已满足即可做"优先。

---

## 一、存档持久化（Building 实现 ISaveable）

- **依赖**：前置已就绪（`ISaveable` / `SaveManager` / `ISaveableSpawner` 在 `SaveableContracts.cs`）。
- **要做**：`Building` 实现 `ISaveable`，序列化 `type / pos / level / faction / hp / 存储量`；读档经 `ISaveableSpawner` 重建实例并重新 `MarkOccupied`（P1）。
- **关键区分**：
  - **玩家建筑**：必须显式存（type/pos/level…），读档重建。
  - **地图预置建筑**：由 seed 复现（地图生成已负责），`Building` 读档只恢复其运行时状态（hp/已采集量），不重复生成。
- **收益**：关游戏不丢建造进度，符合 3.3 待确认体系。
- **风险**：footprint 多 cell 占用在读档时需一次性 `MarkOccupied` 全部 cell，漏标会重叠放置。
- **建议时机**：3.3 核心合入后第一个做（存档是长线刚需，早接早省心）。

---

## 二、防御建筑战斗接入（接 3.5 / 3.4）

- **依赖**：3.4 伤害管线、3.5 防御建筑自动攻击逻辑。
- **要做**：防御建筑挂 `AttackComponent`（读取 `BuildingDef.combat` 的 attack/defense/maxHp/range/damageType），由伤害管线驱动自动索敌攻击；阵亡走 `TeardownManager` 统一清理并 `Free` 占用。
- **收益**：城墙/箭塔/投石机真正发挥作用，闭合"建造→防御"玩法环。
- **风险**：自动攻击需索敌范围 + 目标选择，可能与 NPC 决策层（3.0b 注意力系统）抢目标；需明确"防御建筑索敌"与"单位 AI 索敌"是否共用一套。
- **建议时机**：3.5 排期时联动，不抢在 3.3 首版。

## 三、地图预置建筑复用（激活 3.2.1 的占位）

> ⚠️ **已前移至 3.3.1 P5（硬前置）+ 3.3 批次 0**。原列为后置工作，但 3.2.2 全链路核查发现 `BuildingFactory` 完全缺失，地图建筑实例化是 3.2.2 与 3.3 之间的断裂点，不修复则 3.3 交互/存档/UI 全部空转。以下保留原文档作背景参考。

- **依赖**：3.2.1 地图生成已产出 `BuildingPlaceholder`（GridTypes.cs）；3.3.1 P2 裁定的运行时 `Building` 类；3.3.1 P6 的 `BuildingType → BuildingDef` 映射表。
- **要做**（已在 3.3 批次 0 实现）：`BuildingFactory.InstantiateFromMap(MapData)` 把 `Region.resources`（List<BuildingPlaceholder>）转为运行时 `Building` 实例，`isPlayerBuilt = false`，复用同一 `Building` + `IInteractable`；`Rift` / `CastleCore` 同理接入交互。详见 3.3.1 P5。
- **收益**：资源点/宝箱/裂隙/主城全部"可点击交互"，呼应 3.3 通用交互层的设计初衷；地图生成 3.2.1 的占位终于"活"过来。
- **风险**（已由 P6 映射表设计解决）：`BuildingPlaceholder` 的 `BuildingType` → `BuildingDef` 的映射表要全（漏类型会生成失败）。
- **建议时机**：~~与一（存档）同期~~ → 已前移至 3.3 批次 0（最优先实施）。

## 四、产能结算完整化 + 性能（G1）

- **依赖**：`BuildingDef.producer`（`ProducerConfig` rate/capacity）。
- **要做**：
  - 每秒 `BuildingProductionTickEvent` 结算一次产出，写入建筑存储，满 `capacity` 停（避免无限囤）。
  - `BuildingRegistry` 用 Runtime Set 风格存储，避免每帧遍历；产能 tick 走定时器而非 `Update`。
  - 多产出类型（Resource / Unit）分流：产资源进 `RulerController`，产单位走 `UnitFactory`。
- **收益**：经济循环真正转起来；性能可控（百栋建筑不掉帧）。
- **风险**：Unit 产出要考虑阵营/归属与堆叠上限（接 GridSystem 单位层）。
- **建议时机**：经济闭环验证期。

---

## 五、科技 / 时代解锁（levels[].prerequisites）

- **依赖**：未来科技系统（3.x 待规划）。
- **要做**：建筑菜单按 `levels[].prerequisites` 灰显未解锁项；升级也校验前置科技。
- **收益**：建造有成长梯度，避免早期无脑堆同类。
- **风险**：科技系统未定，先留接口不接逻辑，避免空依赖。
- **建议时机**：科技系统立项后。

## 六、建造队列 / 上限 / buildTime 进度（G2）

- **依赖**：`BuildingDef` 预留 `buildTime` 字段（3.3 待确认 #4：首版不实装）。
- **要做**：首版建造即时激活；后置补 `buildTime` 进度条（放置后进入"建造中"态，倒计时结束才激活 combat/producer）；同时可建数量上限；单建筑建造队列。
- **收益**：建造有节奏感，避免瞬间满防。
- **风险**：建造中态的 `isObstacle` 应提前生效（挡路但不产出/不攻击），需明确中间态语义。
- **建议时机**：手感打磨期。

- **风险**：批量操作资源扣减需事务化（部分失败回滚）。

- **依赖**：3.10 移动与障碍处理（寻路）。

- **收益**：城墙真能改变 enemy 寻路，呼应"障碍处理"玩法。
- **风险**：频繁增删触发重算会卡，需节流/局部更新。
- **建议时机**：与 3.10 联动。
