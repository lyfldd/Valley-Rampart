## 二、问题 9：建造菜单点击任意按钮都关闭（🔴 阻塞性 bug）

### 2.1 现象

按 B 键打开建造菜单 → 点击任意按钮（tab 切换、建造、甚至点面板空白处）→ **菜单立即关闭**。

### 2.2 根因

**InteractionManager 与 UI Toolkit 点击冲突。**

调用链：
```
用户点击 UI 面板按钮
  ├─ UI Toolkit 处理点击（切换 tab / 触发建造）  ← 正确
  └─ InteractionManager.Update() 也在同一帧检测到 Input.GetMouseButtonDown(0)
       └─ InputMode 仍是 Normal（打开菜单时没切换到 Dialog）
       └─ Physics2D.OverlapPoint 在世界空间检测
       └─ UI 面板按钮不在世界空间，没有 Collider → 没命中
       └─ 走到"点空白"分支 → UIManager.CloseCurrent()  ← 菜单被关了！
```

证据：
- [BuildingMenuPanel.cs:138-160](file:///d:/Valley%20Rampart/Valley%20Rampart/Assets/_Game/Systems/Building/BuildingPanel.cs#L138) 的 `OnToggleBuildMenu` 打开菜单时**没有调 `InputManager.SetMode(Dialog)`**
- [InteractionManager.cs:25](file:///d:/Valley%20Rampart/Valley%20Rampart/Assets/_Game/Systems/Interaction/InteractionManager.cs#L25) 只在 `CurrentMode != Normal` 时跳过点击 → Normal 模式下面板点击被误判
- [InteractionManager.cs:68-69](file:///d:/Valley%20Rampart/Valley%20Rampart/Assets/_Game/Systems/Interaction/InteractionManager.cs#L68) 没命中 IInteractable → `UIManager.CloseCurrent()`

**同理 BuildingPanel 也有这个问题**——点击升级/拆除按钮也会被误判为"点空白"而关闭面板。

### 2.3 修复方案

**方案 A（推荐）：InteractionManager 检查面板状态**

在 InteractionManager.Update 的点击检测前加判断：
```csharp
if (UIManager.Instance != null && UIManager.Instance.HasPanelOpen)
    return;  // 面板打开时不响应世界点击，交给 UI Toolkit 处理
```

优点：一处修改，所有面板都受益；不需要每个面板各自管理 InputMode。

**方案 B：UIManager.Open/Close 时切换 InputMode**

```csharp
public void Open(IUIPanel panel, Interactor ctx)
{
    ...
    InputManager.Instance?.SetMode(InputMode.Dialog);
}
public void CloseCurrent()
{
    ...
    InputManager.Instance?.SetMode(InputMode.Normal);
}
```

缺点：如果同时有建造模式（Build），关闭面板时会强制回到 Normal，可能与 BuildController 冲突。

**建议用方案 A**，简单且不冲突。

### 2.4 影响范围

- BuildingMenuPanel：点击 tab/建造按钮 → 菜单关闭 ❌
- BuildingPanel：点击升级/拆除按钮 → 面板关闭 ❌
- 未来所有 IUIPanel 实现都会受影响

## 三、问题 10+11：四大资源经济循环与建筑功能组件化

> 这两个问题深度耦合，合并分析。问题 10 是"资源产出端缺失"，问题 11 是"建筑功能怎么组织"，
> 产能逻辑正好是这两个问题的交叉点。

### 3.1 现状：经济循环完全断裂

```
当前状态（断裂）：
  地图建筑（树/矿/农田）→ BuildingFactory 实例化 → def.producer 有配置
  但……没有产能逻辑 → 资源不增长 → RulerController 四资源永远是初始值
  → 玩家无法积累资源 → 无法建造 → 经济死锁

四大资源流向审查：
  产出端：❌ 完全缺失（BuildingProductionTickEvent 无人发布/订阅）
  存储端：✅ RulerController.ModifyResource 可用（但只是数字加减，无产出源）
  消费端：✅ BuildController.Place / BuildingPanel.OnUpgradeClicked 已对接
  展示端：✅ ResourceHUD 订阅 RulerResourceChangedEvent 已对接
```

### 3.2 核心架构问题：建筑功能怎么组织？

用户的核心疑问：**建筑功能太多样（生产/防御/存储/采集/裂隙/主城），不好抽象为通用接口。**

分析：当前 `Building` 类把所有功能塞在一个类里，`IInteractable` 只是交互入口。但建筑真正要做的事远不止"被点击打开面板"：

| 建筑类型 | 需要做的事 | 当前状态 |
|---------|-----------|---------|
| 树/矿/农田 | 每秒产出资源 → 写入国库或本地存储 | ❌ 缺失 |
| 箭塔/城墙 | 索敌 → 攻击 → 受伤 → 死亡 | ❌ 缺失（接 3.4/3.5） |
| 兵营 | 每秒产出单位 → 走 UnitFactory | ❌ 缺失 |
| 裂隙 | 定时刷怪波次 / 可被封印 | ❌ 缺失 |
| 主城 | HQ 面板 / 科技解锁 / 游戏失败条件 | ❌ 缺失 |
| 宝箱/遗迹 | 一次性采集 → 消失 | ❌ 缺失 |
| 木头堆/石头堆 | 一次性采集 → 消失 | ❌ 缺失 |

如果在 `Building` 类里写所有这些逻辑，会变成一个数千行的上帝类。

### 3.3 架构方案：行为组件化（Component Pattern）

**核心思想**：Building 类只管基础状态 + 交互入口，具体行为拆成独立 Component 挂在同一 GameObject 上。

```
Building (核心)
├── 基础状态：def / coord / level / hp / maxHp / grade / faction
├── IInteractable 实现：Interact() → 打开 BuildingPanel
├── 生命周期：TakeDamage / Die / TryUpgrade
│
├── ProducerComponent（产能组件）
│   ├── 触发条件：def.producer != null && def.producer.kind == Resource
│   ├── 职责：每秒按 rate × gradeScale 产出资源
│   ├── 产出去向：RulerController（方案A）或 StorageComponent（方案B）
│   └── 满载停产出：检查 capacity
│
├── SpawnerComponent（产兵组件）
│   ├── 触发条件：def.producer != null && def.producer.kind == Unit
│   ├── 职责：按 rate 产出单位，走 UnitFactory
│   └── 堆叠上限：检查 GridSystem 该 cell 单位数
│
├── CombatComponent（战斗组件）
│   ├── 触发条件：def.combat != null && def.combat.attack > 0
│   ├── 职责：索敌 → 攻击（接 3.4 伤害管线 / 3.5 防御建筑）
│   └── 死亡：hp <= 0 → Building.Die()
│
├── StorageComponent（存储组件）
│   ├── 触发条件：需要本地存储的建筑（ProducerComponent 方案B 时）
│   ├── 职责：storedAmount / capacity，满载停产出
│   └── 采集：采集单位搬运存入国库
│
├── RiftComponent（裂隙组件）
│   ├── 触发条件：sourceType == BuildingType.Rift
│   ├── 职责：定时刷怪波次 / 被封印
│   └── 对接：3.7 波次系统
│
├── CastleCoreComponent（主城组件）
│   ├── 触发条件：sourceType == BuildingType.CastleCore
│   ├── 职责：HQ 面板 / 科技解锁 / 失败条件（主城被毁 = 游戏结束）
│   └── 对接：3.8 外交 / 科技系统
│
└── PickupComponent（采集组件）
    ├── 触发条件：def.isConsumable == true（宝箱/木头堆/石头堆）
    ├── 职责：一次性采集 → 资源入国库 → 建筑消失
    └── 与 ProducerComponent 互斥：持续性产出 vs 一次性采集
```

### 3.4 组件化后的工作流

**BuildingFactory 实例化时**：
```
1. 创建 GameObject
2. AddComponent<Building>() → Init(def, coord)
3. 根据 def.producer：
   - kind == Resource → AddComponent<ProducerComponent>()
   - kind == Unit → AddComponent<SpawnerComponent>()
4. 根据 def.combat：
   - attack > 0 → AddComponent<CombatComponent>()
5. 根据 def.isConsumable：
   - true → AddComponent<PickupComponent>()
6. 根据 sourceType：
   - Rift → AddComponent<RiftComponent>()
   - CastleCore → AddComponent<CastleCoreComponent>()
7. Register → MarkOccupied → Publish(BuildingPlacedEvent)
```

**BuildingPanel 展示时**：
```
Refresh() {
    // 基础信息（所有建筑都有）
    显示 名称/等级/HP/占地/阵营

    // 条件渲染（根据挂了哪些 Component）
    if (有 CombatComponent) 显示 攻击/防御/射程
    if (有 ProducerComponent) 显示 产能速率/存储量/容量
    if (有 SpawnerComponent) 显示 产兵速率
    if (有 PickupComponent) 显示 "可采集"
    if (有 RiftComponent) 显示 波次信息/封印进度
    if (有 CastleCoreComponent) 显示 HQ 特有信息

    // 操作按钮（根据权限）
    if (isPlayerBuilt && canUpgrade) 显示 升级按钮
    if (isPlayerBuilt && isDestructible) 显示 拆除按钮
}
```

### 3.5 组件化与 IInteractable 的关系

`IInteractable.Interact()` 只负责"被点击后打开面板"，这是**所有建筑共有的行为**。

建筑功能的差异不在交互层，而在**行为层**（Component）。交互层不需要知道建筑有什么 Component，它只管打开 BuildingPanel。BuildingPanel 再去查 Component 决定显示什么。

```
InteractionManager 点击
  → Building.Interact() → 返回 ShowUI(BuildingPanel)
  → BuildingPanel.Open() → Refresh()
  → Refresh() 查 GetComponent<ProducerComponent>() 等 → 条件渲染
```

这样 IInteractable 保持通用，建筑功能差异由 Component 组合表达，符合开闭原则。

### 3.6 存储系统设计

#### 方案 A（首版推荐）：产出直接入国库

```
ProducerComponent.Update()
  → 每秒 rate × gradeScale 产出
  → RulerController.ModifyResource(type, true, amount)
  → 不存在建筑本地存储
```

- 优点：实现简单，无需搬运 AI
- 缺点：不符合 RTS 采集习惯
- 适用：首版快速跑通经济循环

#### 方案 B（后期迭代）：建筑本地存储 + 采集单位搬运

```
ProducerComponent.Update()
  → 每秒 rate × gradeScale 产出
  → 写入 StorageComponent.storedAmount（满 capacity 停）
  → 采集单位（UnitAI）走到建筑旁 → 搬运 → 存入主城/仓库
```

- 优点：RTS 深度，采集单位有活干
- 缺点：依赖 3.10 移动系统 + 搬运 AI
- 适用：经济循环跑通后的玩法深化

**建议首版用方案 A**，后期再迭代到方案 B。

## 四、问题 12：建筑美术资源占位全部缺失

### 4.1 现状

12 个 BuildingDef 的 `prefab` 字段全是 NULL：
- 箭塔、城墙、树、矿洞、农田、裂隙、主城、宝箱、遗迹、矿脉、石头堆、木头堆

- 树 → 绿色方块
- 矿洞 → 灰色方块

- 城墙 → 深灰方块
- 裂隙 → 紫色方块
- 主城 → 金色大方块
- 宝箱 → 亮黄方块

每个占位 prefab = GameObject + SpriteRenderer（彩色方块）+ 按需 Collider2D。

## 七、问题 4：InteractionManager 缺少悬停高亮

### 7.1 现象

### 7.2 修复方案

- 每帧 `Physics2D.OverlapPoint` 检测鼠标位置
- 命中 IInteractable → 高亮（修改 SpriteRenderer.color 或加 Outline）
- 离开 → 取消高亮
- 点击后保持选中态高亮，点空白取消

高亮表现首版用简单方案（SpriteRenderer.color 加亮），后期升级描边 Shader。

### 10.2 组件化架构与边界（问题 11 展开）

**核心思想**：Building 类只管基础状态 + 交互入口 + 生命周期，具体行为拆成独立 Component。

| 组件 | 本轮处理 | 触发条件 | 职责 |
|------|---------|---------|------|
| ProducerComponent | ✅ 实现 | `def.producer != null && kind == Resource` | 每秒产出资源写入本地存储 |
| StorageComponent | ✅ 实现 | 产出建筑必需 | storedAmount/capacity，满载停产出，预留搬运接口 |
| PickupComponent | ⚠️ 留接口 | `def.isConsumable == true` | 一次性采集（宝箱/木头堆），暂不实现 |
| SpawnerComponent | ⚠️ 留接口 | `def.producer.kind == Unit` | 产兵，依赖单位系统 |
| CombatComponent | ❌ 不碰 | `def.combat.attack > 0` | 依赖 3.4/3.5 |
| RiftComponent | ❌ 不碰 | `sourceType == Rift` | 依赖 3.7 波次 |
| CastleCoreComponent | ⚠️ 留接口 | `sourceType == CastleCore` | 主城解锁逻辑见 §10.8 |

**接口约定**：
- 定义 `IBuildingComponent` 接口框架，BuildingFactory 知道怎么挂组件
- 组件从 `BuildingDef` 读配置，不自己持有状态
- 留接口 = 定义接口和挂载逻辑，具体组件类先不实现

### 10.3 产能系统（问题 10 展开）

#### 10.3.1 调度机制：集中调度器

```
ProductionSystem（新建，单例）
  ├─ 每秒统一遍历所有 ProducerComponent
  ├─ 支持暂停（游戏暂停时停 tick）
  ├─ 易存档（只存 StorageComponent.storedAmount）
  └─ 性能好（O(n) 遍历，无每帧 Update）
```

#### 10.3.2 存储方案：方案B（本地存储 + 预留搬运接口）

```
ProducerComponent.Update（被 ProductionSystem 调用）
  → 检查 Building.state == Active
  → 检查 StorageComponent.storedAmount < capacity
  → 每秒 rate × gradeScale 产出
  → 写入 StorageComponent.storedAmount
  → 满载停产出

搬运接口（预留，不实现调用方）：
  IHarvestable 接口
    bool IsReadyToHarvest()  // storedAmount >= harvestThreshold
    int Harvest()            // 取走资源，返回取走量
  未来 NPC 工人轮询所有 IHarvestable，达阈值则搬运
```

#### 10.3.3 资源点 + 工具模型（核心设计）

**设计理念**：资源点是前置条件，工具是生产设备，两者结合才能产出。

```
地图生成 → 预置持续性资源点（原始矿洞/原始树林/原始农田）
              ↓ 资源点自身不产出（仅前置）
         玩家在资源点上放置"生产工具"
              ↓ 走 Constructing 进度（脚手架）
         建造完成 → 资源点被改造为产出建筑
              ↓ ProducerComponent 启动产出
         StorageComponent 本地存储
              ↓ 等搬运（接口预留）
         （未来）NPC 工人搬运 → 国库
```

**关键规则**：
- 资源点 BuildingDef 标记 `isResourceNode=true`，自身不产出
- 工具→资源点映射表（ResourceNodeMapping）：采石场↔矿洞、伐木场↔树林、农场↔农田
- PlacementValidator 新增校验：产出建筑放置时检查目标格是否有对应资源点
- 放置即改造：建造完成后，原资源点 Building 被替换为产出建筑
- 资源点改造走 Constructing 进度，和建造统一

#### 10.3.4 占位数值表

| 资源 | 初始量 | 产出 rate | capacity | 造价 |
|------|--------|----------|----------|------|
| 木 | 100 | 15/秒 | 100 | 50 |
| 粮 | 100 | 15/秒 | 100 | 50 |
| 石 | 100 | 5/秒 | 100 | 50 |
| 金 | 100 | 5/秒 | 100 | 50 |
| 升级倍率 | - | ×1.5/级 | ×1.2/级 | ×2/级 |
| 等级上限 | - | 3 级 | 3 级 | 3 级 |

#### 10.3.5 资源平衡设计

**首版**：所有资源点永久产出，用速率差异做平衡（木粮快、石矿慢）。

**后期深化**：
- 种树：伐木场消耗粮+时间种植新树林资源点（木可再生）
- 炼金：科技解锁，把木/粮转化为石/矿（用可再生换稀缺）
- 地图扩张：随波次推进，地图边缘生成新资源点

### 10.4 建造系统（问题 3/8/12/13/14 展开）

#### 10.4.1 建筑生命周期状态机（组件化底层依赖）

```
Placing → Constructing → Active → Damaged → Dead
                ↑           |        |
                └───────────┘        |
                  升级               维修（未来）
                （走 Constructing）
```

| 状态 | 说明 | 组件行为 |
|------|------|---------|
| Placing | 放置中（ghost） | 无 |
| Constructing | 建造中（脚手架） | 不产出/不战斗 |
| Active | 活跃 | 产出/战斗/可交互 |
| Damaged | 受损（HP低） | 首版不区分，等同 Active |
| Dead | 死亡 | 触发 Die()，待销毁 |
| Abandoned | 废弃（新增） | 用于主城初始形态，见 §10.8 |

#### 10.4.2 统一进度系统（一处实现，三处复用）

**建造 / 升级 / 维修 都走 `Constructing` + 进度条。**

```
Constructing 状态的进度推进（双模式）：
  模式A（首版占位）：自动累计，每秒 +20%，5秒完成
  模式B（3.10后）：需要工人走到旁边才累计，无工人暂停

视觉：
  放置后立即显示半透明骨架/脚手架（占位 Sprite）
  完成时替换为正式建筑 Sprite + state=Active
  升级时贴图换脚手架，但 storedAmount/level 等数据保留不丢

打断：
  玩家可随时拆除在建建筑，按HP比例返还资源
```

#### 10.4.3 多格占地 + R 键旋转

- `footprint: Vector2Int`（width × height），支持混合尺寸（1×1/2×2/2×3）
- R 键旋转 90°：w/h 互换
- PlacementValidator 遍历所有占用格校验（occupancy/terrain/boundaries）
- GridSystem.MarkOccupied 标记所有格
- ghost 预览显示多格半透明区域
- 吸附基准：左上角对齐小区块网格

#### 10.4.4 建造手感优化

- **小区块网格吸附**：ghost 吸附到大区块内 16 个小区块的最近格
- **建造菜单自动隐藏**：进入建造模式后菜单隐藏，结束返回
- **建造后返回菜单**：单次放置返回菜单，Shift 连续放置保持模式
- **ghost 视觉反馈**：绿色可建/红色不可建

#### 10.4.5 建造菜单 UI

- 布局：图标 + 名称 + 造价，资源不足灰显
- tab 分类：Production / Economy / Defense / Wall / Special
- tab 内布局：网格排列，超出滚动

#### 10.4.6 建筑美术占位（问题 12）

用 PlaceholderSprites 生成彩色方块：
- 树→绿、矿洞→灰、农田→黄、箭塔→蓝、城墙→深灰
- 裂隙→紫、主城→金、宝箱→亮黄
- 脚手架→半透明棕

### 10.5 存档需求（问题 1 展开）

组件化后存档范围扩大，ISaveable 下沉到组件层：

| 存档对象 | 字段 | 说明 |
|---------|------|------|
| Building 核心 | type/coord/level/hp/faction/state/footprint/rotation | 所有建筑都存 |
| StorageComponent | storedAmount | 产出建筑必存 |
| ProducerComponent | 无需存档 | 每秒重算 |
| BuildingFactory 重建 | 根据存档 type 重新挂组件 + 恢复 StorageComponent.storedAmount | |

### 10.6 UI 栈系统（新增）

#### 10.6.1 核心规则

- 所有弹窗打开时入栈，先进后出（栈结构，LIFO）
- ESC 优先关闭栈顶最上层 UI
- 父子 UI 不嵌套栈，全部同一全局栈
- 空栈时 ESC 打开暂停窗口（暂停窗口也入栈）
- 暂停窗口在栈顶时 ESC 关闭它，栈重回空
- 关闭 UI 必须主动出栈，禁止 SetActive(false) 绕过管理器
- 模态弹窗锁定：栈顶 UI 生效时，底层 UI 不接收输入（可选扩展）

#### 10.6.2 UIStack 层次

```
层0  普通游戏（无UI，自由操作）
层1  建造菜单（按B打开）
层2  建造模式（点建造按钮，菜单隐藏，虚影跟随鼠标）—— 无面板的虚拟UI层
层3  建筑面板（点击已有建筑打开）
```

建造模式作为虚拟 UI 层入栈，ESC 行为天然统一：
- 建造菜单(栈顶) → 点建造 → 菜单出栈隐藏 + 建造模式入栈
- ESC → 建造模式出栈 + 建造菜单重新入栈显示

#### 10.6.3 接口约定

- `IUIStackEntry`：让有面板 UI 和无面板建造模式都能入栈
- UIManager 实现 Push/Pop/Peek

### 10.8 主城设计（Kingdom 风格，新增）

#### 10.8.1 设计理念

参考 Kingdom 游戏：主城不是功能建筑，而是**解锁建造系统的钥匙**。

#### 10.8.2 游戏开局流程

```
游戏开始
  ↓ 地图中心预置【废弃城堡】（Building, state=Abandoned）
玩家点击废弃城堡 → 打开面板 → 显示"需要修复" + 修复造价
  ↓ 玩家有足够资源 → 触发修复
走 Constructing 进度（和建造统一）
  ↓ 修复完成 → state=Active
发 BuildingActivatedEvent
  ↓ BuildController 监听 → 解锁建造菜单
玩家可建造初始建筑（伐木场/采石场/农场/箭塔/城墙）
  ↓ 主城升级 → 分级解锁更多建筑
```

#### 10.8.3 新增状态：Abandoned

- 废弃状态，可被修复但不产出/不可用
- 可交互（打开面板显示修复选项）
- 修复后转 Constructing → Active

#### 10.8.4 科技树分级解锁

| 主城等级 | 解锁建筑 |
|---------|---------|
| 0（废弃） | 无（只能修复主城） |
| 1（修复完成） | 伐木场、采石场、农场、箭塔、城墙 |
| 2 | 市场（产金）、投石机 |
| 3 | 魔法塔、城门 |

#### 10.8.5 主城本身

- 主城也是建筑，会被交互（打开面板）、会升级
- 升级走 Constructing 进度系统
- 主城被毁 = 游戏失败

### 10.10 核心架构洞察

讨论中涌现的三个关键架构决策：

1. **统一进度系统**：建造/升级/维修/资源点改造 都走 `Constructing` + 进度条，一处实现四处复用。首版用"自动累计"占位，3.10 完成后切"工人驱动"模式，状态机和视觉一次到位。

2. **资源点+工具模型**：资源点是前置（不产出），工具激活后才产出，放置即改造。这解决了"产出建筑必须建在对应地形"的需求，PlacementValidator 新增资源点校验。

3. **主城 Kingdom 设计**：主城不是功能建筑，是解锁建造系统的钥匙。废弃城堡→修复→解锁建造，主城升级分级解锁建筑，形成科技树雏形。
