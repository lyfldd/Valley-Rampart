# 设计方法论 · 生命周期工作流

> **文档性质声明（先读）**
> 本文档只描述一种**思想方法**，不包含任何具体项目、具体引擎、具体技术栈的硬编码内容。
> 文中所有【示例】仅用于帮助理解，**是示意、不是准则**——落地时允许、也鼓励用完全不同的答案。
> 凡标注「**决策点**」之处，都是留给使用者在具体项目里填的空（相当于泛型参数）；填什么由该项目自己的技术选型决定，本文档不预设答案。
> 使用方法：新系统立项 → 填决策点 → 过八格检查表 → 按需选工具 → 用 AI 模板开工 → 验收时回填检查表。

---

## 〇、底层骨架（不变地基，与任何技术栈无关）

### 0.1 两条铁律

**铁律一：一切对象皆有生命周期，且只有四个阶段。**

任何对象（整个应用、一局游戏、一个系统、一块面板、一个实体）都走过且仅走过这四个阶段：

| 阶段 | 语义 | 该阶段"该做什么"的抽象描述 |
|------|------|------------------------------|
| `OnBirth` | 诞生 | 获得标识、读配置、声明依赖、订阅消息、注册进归属者 |
| `OnActivate` | 激活 | 开始接收、开始被驱动（tick/刷新/渲染） |
| `OnDeactivate` | 挂起 | 停止接收、停止被驱动，但**不释放任何资源**（必须可无损恢复到 Activate） |
| `OnDeath` | 死亡 | 退订全部消息、从归属者注销、清算引用、释放资源 |

**铁律二：所有权闭环。**
谁创建，谁回收。有创建必有销毁、有订阅必有退订、有注册必有注销——成对出现，缺一不可。
初始化自底向上（被依赖者先就绪），销毁自顶向下（**严格按初始化的反序**）。

### 0.2 三条推论（铁律的直接展开）

1. **反向空指针**：不只"有生必有死"，反过来也成立——任何**使用点**都必须保证对象已诞生。"代码写好了但资源没接上"与"只有开始没有结束"是同一种病的两种症状。
2. **可重入性**：第二次 OnBirth 必须等价于第一次。若对象来自池/缓存复用，OnDeath 必须把它复位到"从未活过"的状态，否则残留状态就是下次诞生的污染。
3. **死亡 ≠ 消失**：终结态本身也是一种状态，可以有自己的逻辑与表现（废墟、遗产、回放记录……）。OnDeath 是"转换到终结态"，不一定是"从世界上抹掉"。

### 0.3 顺序表（决策点：具体服务清单与先后）

骨架只约束**形式**：存在一张显式的初始化顺序表，销毁顺序是它的严格反序。
一个常见的抽象层次（从底到顶）是：

```
资源/配置 → 通信 → 持久化 → 世界/空间 → 业务管理器 → 表现层
```

> 决策点：你的项目有哪些全局服务、各自插在哪一层、同层之间谁先谁后——落地时填成自己项目的顺序表。
> 禁令（与项目无关，普遍成立）：**任何对象在 OnDeath 阶段不得访问可能已销毁的其他服务**。销毁侧只做"退订/注销/释放"，不做"查询别人"。

### 0.4 八格检查表（每个系统/实体过一遍，空格 = 下一个 bug）

| # | 环节 | 必答问题 |
|---|------|----------|
| 1 | 诞生 | 触发源唯一吗？谁负责创建它？ |
| 2 | 归属 | 统一管理它的是谁（注册表/管理器/父对象）？ |
| 3 | 更新 | 谁驱动它？降频/休眠时它的逻辑还推进吗？ |
| 4 | 挂起/恢复 | 被暂停、被打断、被切走时，它处于什么状态？能恢复吗？ |
| 5 | 正常终结 | "完成/死亡/关闭"的判定条件是什么？ |
| 6 | 异常终结 | 中途被打断的路径走通了吗？（取消、覆盖、强制退出） |
| 7 | 清算 | 消息退订了吗？还引用它的人被通知了吗？它的资源归谁？ |
| 8 | 持久化 | 它的状态（含终结态）需要保存吗？保存的数据以后版本变了怎么迁移？ |

**反向三问**（使用时的快速自检）：每个使用点问"它诞生了吗"；每个诞生问"它怎么死"；每个死亡问"谁还拿着它"。

## 一、EventBus / 事件总线（模块解耦通信）

**解决的问题**：模块间直接持有引用 → 引用失效就是空指针。改为广播消息，发送方不知道谁在听，接收方不知道谁在说。

**嵌入生命周期**：

| 阶段 | 动作 |
|------|------|
| OnBirth | 订阅自己需要监听的全部消息 |
| OnActivate | 正常接收 |
| OnDeactivate | 临时退订（暂停期间不收） |
| OnDeath | **强制退订全部（重中之重）**——已死对象收到回调是最经典的崩溃源 |

**附属纪律**（同样与项目无关）：
- 订阅与退订成对：入口订、出口退。
- 发布侧也守生命周期：一个诞生若无消费者，不广播（防消息洪泛）。
- 消息只携带数据，不携带"可调用对象"（否则解耦失效）。

**决策点**：消息的载体形态（枚举/结构体/字符串）、同步还是异步派发、是否有优先级。

**AI 辅助**：让 AI 列出该系统该订阅/发布哪些消息；生成消息定义与成对的订阅/退订代码；**扫描"订了没退"的位置**；输出"谁发送、谁监听"的对照文档。

【示例，非准则】某"王国"对象灭亡时不直接调用 UI 或存档，只广播一条"王国灭亡"消息；UI、存档、地图各自监听并各做各的处理——三者互相无引用。

## 二、简易 MVC（界面专用）

**解决的问题**：界面改动污染核心数据；数据变了界面不刷新。把数据（Model）、画面（View）、粘合逻辑（Controller）拆开。

**嵌入生命周期**（一个面板 = 一个独立生命周期实体）：

| 角色 | OnBirth | OnActivate | OnDeactivate | OnDeath |
|------|---------|------------|--------------|---------|
| Model | 准备本面板所需数据 | — | — | 清空缓存数据 |
| View | 绑定控件 | 刷新一次显示 | 隐藏 | 解绑全部交互回调、清空引用 |
| Controller | 粘合 View↔Model，订阅数据变更 | — | — | 切断 View 与 Model 的关联 |

**附属纪律**：View/Controller 只读数据、只发消息，**不直接改游戏状态**。

**决策点**：界面技术栈是什么（决定"控件"和"绑定"的具体形态）、面板之间是否有栈/层级管理。

**AI 辅助**：给面板名，AI 输出三角色职责拆分、基础模板、完整生命周期步骤；并检查"界面直改数据"的违规写法。

【示例，非准则】"详情面板"打开=OnBirth+Activate（读数据、刷新显示），切走=Deactivate（隐藏但保留），关闭=OnDeath（解绑回调、清引用）——打开/切走/关闭是三种不同的终结深度，混用会导致残留回调污染下一个面板。

## 三、轻量 ECS（大批量实体专用）

**解决的问题**：成百上千个同类实体（小兵、子弹）逐个走完整面向对象生命周期太贵；数据与行为拆开后可批量更新、批量增删。

**使用边界（通用原则）**：**不做全局 ECS**，只给"数量巨大的同类动态实体"用；单例级、决策重的对象不适合。
另有一条项目相关的通用推论：若你的项目存在"同一份逻辑要在两个环境编译运行"的约束（如同源仿真），ECS 的具体实现方案必须通过该约束的审查——**决策点：确认所选 ECS 方案不破坏你最重要的跨端/同源约束。**

**嵌入生命周期**：

| 角色 | 生命周期 |
|------|----------|
| Entity | 仅是 ID。OnBirth=发 ID+挂组件+注册；OnDeath=摘全部组件+**回收 ID 供复用**（呼应可重入性） |
| Component | 纯数据，**无生命周期**，依附实体 |
| System | OnBirth=建过滤器+注册进更新管线；OnActivate=批量遍历实体执行业务；OnDeactivate=停更；OnDeath=清缓存 |

**AI 辅助**：描述"实体有哪些数据、有哪些行为"，AI 拆实体/组件/System、生成基础代码，并**判断哪些对象适合进 ECS、哪些不适合**。

【示例，非准则】子弹：数量大、行为单一（飞、命中、消失）→ 适合。王国大脑：全局一个、决策复杂 → 不适合，留在常规对象层。

## 四、FSM 有限状态机（行为组织）

**解决的问题**：复杂 if-else 行为无法审阅、无法验证完备性。拆成状态后，"有哪些行为、什么条件下怎么切换"变成一张可检查的表。

**嵌入生命周期**：

| 阶段 | 动作 |
|------|------|
| OnBirth | 创建状态机、注册全部状态、设初始状态 |
| OnActivate | 当前状态 `Enter()`，开始执行状态逻辑 |
| OnDeactivate | 当前状态 `Exit()`，暂停（可恢复） |
| OnDeath | **强制退出当前状态、清缓存、销毁状态机** |

分工：**生命周期管"状态机能不能跑"，状态机管"活着时干什么"。**

**决策点**：状态机代码放在哪一层——通用推论：若存在"逻辑要在多环境同源运行"的约束，状态机应放在能被所有环境共享的那一层，而不是放在表现层。

**AI 辅助（六工具中收益最大）**：自然语言描述行为，AI 输出：① 状态全列表；② 每个状态的切换条件；③ 状态流转图；④ 代码模板；⑤ **死状态检查**（进得去出不来的状态、没有 Enter/Exit 清理的状态）。

【示例，非准则】一个对象的行为可描述为"平时做事→被打扰就挂起→打扰结束恢复→条件满足则放弃"——这四个状态及其互切条件，就是一张最小完备的状态表；"挂起"状态的 Exit 若忘了恢复现场，恢复后行为就会错乱。

## 五、ServiceLocator / 全局服务

**解决的问题**：各模块到处拖全局对象的引用，依赖关系变成乱麻。改为：全局能力做成服务，集中登记，需要时按名获取。

**嵌入生命周期**：每个全局服务本身就是顶层生命周期实体，插入 §0.3 顺序表：

| 阶段 | 动作 |
|------|------|
| OnBirth | 初始化、登记进服务容器 |
| OnDeath | 从容器注销、释放资源；**禁止此时访问其他服务** |

**决策点**：服务的具体承载形态（容器/单例/框架内置机制均可，思想不变）；服务清单与顺序表的内容。

**AI 辅助**：给系统清单，AI 帮你：① 规划服务集合；② **排初始化/销毁顺序**（顺序错乱 = 空指针，这是该工具最大的风险点）；③ 生成基础代码；④ **检测循环依赖**（A 依赖 B、B 又依赖 A）。

【示例，非准则】顺序表若排成"存档先于地图销毁"，则地图 OnDeath 时还能安全写档；若排反，地图销毁时去调已死的存档服务即崩溃——顺序表的价值全在销毁侧。

## 六、数据驱动（配置外置）

**解决的问题**：数值写死在代码里 → 调参要改代码、改代码要重编译、多份拷贝会漂移。改为：数值全部外置，代码只执行逻辑。

**通用原则**：
1. 一切影响行为的数值外置，代码中无魔法数字。
2. 实体在 OnBirth 时按标识读取自己那份配置来初始化属性。
3. 配置属全局底层资源：实体 OnDeath 不影响配置；配置自身随应用级生命周期加载/释放。
4. 若同一参数存在多份拷贝（多环境/多载体），必须有**显式的同步规则**保证不漂移。

**决策点（本工具最大的一个）**：配置的载体形态——文件（JSON/表格）、引擎资产、数据库皆可，按项目生态选择；以及"哪些参数可调、可调参数登记在哪里"。

**嵌入生命周期**：

| 角色 | OnBirth | OnDeath |
|------|---------|---------|
| 配置 | 应用启动阶段加载并缓存 | 应用退出时释放缓存（配置源本身不销毁） |
| 玩法实体 | 按标识读配置初始化属性 | 只销毁自身，不碰配置 |

**AI 辅助**：描述"这类对象需要哪些参数"，AI 输出：配置结构定义、字段文档、**全仓扫描硬编码数值并提醒外置**、以及多载体同步清单。

【示例，非准则】同一"攻击速度"若既写在代码默认值、又写在配置、又写在调参面板里，三处迟早不一致——数据驱动纪律要求指定唯一真源，其余皆为派生。

## 七、组合关系总览

```
底层地基（不变）
  四阶段生命周期契约（OnBirth / OnActivate / OnDeactivate / OnDeath）
  + 所有权闭环（谁创建谁回收，初始化与销毁严格反序）
      ↓
中层可插拔工具（按需选用，全部作为插件嵌入地基，不推翻地基）
  EventBus（解耦通信）｜简易 MVC（界面）｜轻量 ECS（大批量实体）
  FSM（行为组织）｜ServiceLocator（全局服务）｜数据驱动（配置外置）
      ↓
上层业务模块（你的游戏内容，随项目任意变化）
```

选用原则：工具是**插件**，为地基服务；任何工具的引入若要求破坏四阶段契约或所有权闭环，说明用错了工具或该场景不该用它。

## 八、统一 AI 工作流模板（复制后填空）

```
我的底层框架规则：
- 一切对象走四阶段生命周期：OnBirth / OnActivate / OnDeactivate / OnDeath。
- 所有权闭环：谁创建谁销毁；初始化自底向上，销毁严格反序。
- 本项目的约束（每次按实际填写，例：逻辑需跨环境同源 / 界面技术栈是X / 配置载体是Y / …）：
  【填约束1】【填约束2】…

现在需要开发【模块名】。
请帮我完成：
1. 判断该模块适合嵌入哪几种中层工具（EventBus / 简易MVC / 轻量ECS / FSM / ServiceLocator / 数据驱动），说明理由
2. 写出该模块四阶段各做什么（必须含异常终结路径；若对象会被复用，说明 OnDeath 如何复位）
3. 列出它依赖哪些全局服务，以及它在初始化/销毁顺序表中的位置
4. 列出它发布、订阅哪些消息（谁发送、谁监听）
5. 若它有复杂行为：梳理状态机（状态列表 / 切换条件 / 流转图 / 死状态检查）
6. 列出涉及的全部参数及其配置归属（唯一真源在哪、是否需要多载体同步）
7. 输出最小可运行基础模板，不填充复杂业务
```

## 九、使用方式（闭环）

```
立项 → 填决策点（顺序表、配置载体、界面栈、约束清单）
     → 过八格检查表（§0.4），找出"有生无死/有死无生"的空格
     → 按需选工具（§七）
     → 用 §八 模板开工
     → 验收 = 回填八格检查表，空格清零才算完成
```
