## 一、审计范围

### 1.1 退出路径三级 API

| 级别 | 方法 | 触发场景 | _isQuitting |
|------|------|---------|-------------|
| Level 1 | `TeardownScene` | 读档前/新游戏前（运行时主动调） | false |
| Level 2 | `TeardownForReturnToMenu` | 返回主菜单（运行时主动调） | false |
| Level 3 | `TeardownForQuit` | 退出游戏（OnApplicationQuit 回调） | **true** |

**关键**：Level 1/2 是运行时主动调用，`_isQuitting=false`，所有 Instance 正常，无退出陷阱。**只有 Level 3 撞 `_isQuitting` 机制**。本报告聚焦 Level 3，Level 1/2 仅作对照。

### 1.2 Level 3 (TeardownForQuit) 调用链

```
TeardownManager.OnApplicationQuit()        ← Unity 退出时调用（顺序不确定）
  ├─ base.OnApplicationQuit()              ← Singleton 基类设 _isQuitting = true
  └─ TeardownForQuit()
       ├─ InputManager.Instance.DisableInput()        ← 【已修】_inputActions null 检查
       ├─ TeardownScene()                              ← 复用 Level 1
       │    ├─ FindObjectsOfType<UnitController>()
       │    ├─ foreach unit:
       │    │    ├─ SaveManager.Instance.UnregisterSaveable(unit)
       │    │    ├─ UnitRegistry.Instance.Unregister(unit)
       │    │    └─ Destroy(unit.gameObject)
       │    ├─ RulerController.Instance.ClearMonarchReference()
       │    └─ SaveManager.Instance.CleanupDestroyedSaveables()
       └─ EventBus.Clear()
```

## 二、InputManager NRE 根因回顾（已修）

### 2.1 问题

方案三修好 Instance getter 后，暴露第三层问题：对象活着，但内部字段被自己的 OnApplicationQuit 清空。

```
时刻1: InputManager.OnApplicationQuit 先执行
         └─ CleanupInputActions() → _inputActions = null
时刻2: TeardownManager.TeardownForQuit() 调 InputManager.Instance.DisableInput()
         └─ _inputActions.Disable() → NRE（字段已是 null）
```

### 2.2 修复

`EnableInput()` / `DisableInput()` 开头加 `if (_inputActions == null) return;`，与 `CleanupInputActions()` 已有防御一致。**已修复，待烟测验证。**

### 2.3 问题本质

这是"对象存活但内部状态已被 OnApplicationQuit 清理"的典型。方案三的 fake null 防范（OnDestroy 清 _instance + getter try-catch）防不住这类——因为不是 fake null，是**真 null**（字段被主动赋 null）。

## 三、逐方法审计结论

### 3.1 Level 3 退出路径方法（重点）

| 方法 | 访问的字段/调用 | 风险类型 | 结论 |
|------|---------------|---------|------|
| `InputManager.DisableInput` | `_inputActions.Disable()` | 访问被 OnApplicationQuit 清理的字段 | **已修**（null 检查） |
| `InputManager.EnableInput` | `_inputActions.Enable()` | 同上（防御性，Level 3 不调） | **已修**（null 检查） |

### 3.3 ISaveable.SaveId 实现审计

`UnregisterSaveable` 访问 `saveable.SaveId`，需确认所有 ISaveable 实现不依赖 Unity 对象：

| 类 | SaveId 实现 | 类型 | 退出时访问安全 |
|----|-----------|------|--------------|
| RulerController | `=> "RulerController"` | 常量字符串属性 | 安全 |
| TimeManager | `=> "TimeManager"` | 常量字符串属性 | 安全 |
| DifficultyManager | `=> "DifficultyManager"` | 常量字符串属性 | 安全 |
| WorldManager | `=> "WorldManager"` | 常量字符串属性 | 安全 |
| WorldSystem | `=> "WorldSystem"` | 常量字符串属性 | 安全 |
| UnitController | `{ get; private set; }` 实例属性，Initialize 时赋 GUID 字符串 | string 自动属性，getter 不访问 Unity 对象 | 安全（fake null 下也能读字段值） |

**结论**：所有 SaveId 实现都是 string，getter 不访问 Unity 生命周期对象。即使 saveable 是 fake null，访问 SaveId 也不抛 MissingReferenceException。

### 3.4 OnDestroy base 调用合规性

方案三第一层防范（OnDestroy 清 _instance）依赖子类调 `base.OnDestroy()`：

| 类 | override OnDestroy | 调 base.OnDestroy() | 合规 |
|----|-------------------|---------------------|------|
| InputManager | 是 | 是 | ✓ |
| SaveManager | 是 | 是 | ✓ |
| DifficultyManager | 是 | 是 | ✓ |
| RulerController | 是 | 是 | ✓ |
| GameBootstrap | 是（不继承 Singleton） | 不需要 | ✓ |
| 其余 9 个 Singleton 子类 | 否（靠基类） | — | ✓ |

**结论**：全部合规。第一层防范（OnDestroy 清 _instance）在所有子类生效。

## 四、剩余风险评估

### 4.1 已识别并已修

- `InputManager.DisableInput/EnableInput`：访问被 OnApplicationQuit 清理的 `_inputActions` → 已加 null 检查

### 4.2 审计后确认安全（无需改）

Level 3 退出路径调用的 7 个方法，除 InputManager 外全部安全。安全依据：
1. **纯字段/字典操作**：Unregister/Clear/ResetSessionState/ClearMonarchReference 都是不访问 Unity 生命周期的幂等操作
2. **fake null 已处理**：CleanupDestroyedSaveables 的 `is ... && == null` 写法合规
3. **SaveId 不依赖 Unity**：所有 ISaveable 的 SaveId 是 string，getter 不访问 Unity 对象

### 4.3 理论残留风险（低，可接受）

1. **动态顺序组合未测**：静态分析覆盖了"方法本身安全"，但 OnApplicationQuit 各对象执行顺序的动态组合未做集成测试。极端顺序下可能有未预见路径。
   - 缓解：见第五章验证清单，需 Play Mode 实测各退出路径

2. **未来新增方法**：新加的 Singleton 子类若在 OnApplicationQuit 里清理字段，又在退出路径被调，会重蹈 InputManager 覆辙。
   - 缓解：见第六章编码规范，新增退出路径方法必须 null 安全

3. **EventBus.Publish 在退出路径**：TeardownScene 里各单位销毁时，如果某订阅者在退出时已半残，Publish 可能触发异常。但 EventBus.Publish 内部有 try-catch（EventBus.cs 第 71-79 行），单处理器异常被捕获不扩散。安全。

## 六、长期建议：退出路径编码规范

基于本次排查，确立退出路径方法的编码规范（补充进方案三文档第十一章）：

1. **退出路径方法必须 null 安全**：方法内部访问的每个字段，若可能被 OnApplicationQuit/OnDestroy 清理，开头加 null 检查
2. **退出路径方法必须幂等**：重复调用不产生副作用（Unregister/Clear/Reset 已是范例）
3. **OnApplicationQuit 里清理的字段，对应业务方法必须防御**：InputManager 的 `_inputActions` 是范例（CleanupInputActions 清 null，DisableInput 加 null 检查）
4. **新增 Singleton 子类若 override OnApplicationQuit 清理字段，需同步审计所有调用该方法的外部路径**
5. **退出路径方法尽量不访问其他单例 Instance**：必须访问时加 null 兜底（TimeManager.GetSunrise 的 `WorldSystem.Instance != null ? ... : 6f` 是范例）

### 7.2 新发现（不影响正确性，建议后续改进）

**发现1：UnitRegistry.Unregister 使用 `?.` 访问 Unity 对象（代码风格，非 Bug）**

[UnitRegistry.cs](file:///d:\Valley%20Rampart\Valley%20Rampart\Assets\_Game\Systems\Unit\UnitRegistry.cs#L40) 第 40 行：

```csharp
Debug.Log($"[UnitRegistry] 注销: {unit.Data?.faction}_{unit.Data?.occupation}，当前剩 {Count} 个单位");
```

`unit.Data` 是 `UnitData`（ScriptableObject 继承 UnityEngine.Object）。`?.` 运算符不触发 Unity 的 `==` 重载，违反编码规范 11.1.1。

**为什么不是 Bug**：此处 `unit.Data` 是 ScriptableObject 资产引用（非场景对象），在 TeardownScene 调用时 unit 仍存活（Destroy 在 Unregister 之后），Data 要么是有效引用要么是真实 C# null，不会出现 fake null。且仅在 Debug.Log 中使用，不影响业务逻辑。

**建议**：改为 `unit.Data != null ? unit.Data.faction.ToString() : "null"` 以符合规范。

**发现2：Level 2 (TeardownForReturnToMenu) 的 null 检查不一致（代码风格，非 Bug）**

TeardownForReturnToMenu 中部分 `X.Instance` 调用有 null 检查，部分没有：

| 步骤 | 调用 | 有 null 检查 |
|------|------|-------------|
| ① | `InputManager.Instance.DisableInput()` | ❌ 无 |
| ③ | `SaveManager.Instance.CurrentSlotId` / `.Save()` | ❌ 无 |
| ⑤ | `TimeManager.Instance.ResetState()` 等 5 个 | ✅ 有 |
| ⑥ | `UnitRegistry.Instance.Clear()` | ❌ 无 |
| ⑦ | `SaveManager.Instance.CleanupDestroyedSaveables()` | ❌ 无 |

**为什么不是 Bug**：Level 2 在运行时调用（`_isQuitting=false`），Singleton getter 会自动创建缺失的实例，Instance 不会返回 null。自动创建的实例 Awake 同步执行，字段已初始化。

**建议**：统一加上 null 检查，与 Level 3 保持一致，防止未来 Singleton 基类行为变化时暴露问题。
