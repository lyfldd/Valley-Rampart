## 〇、总览结论

**架构基础面良好**（对象池/Think 分片/LOD 分频/伤害时间轮/chunk 视域加载/LINQ 仅 3 处/物理查询全事件驱动），但存在 **1 个决定性热点**：

> **GridSystem 单位查询无反向索引**——`GetUnitsInCell/GetUnitsInSubCell` 每次调用 = 全量 O(N) 线性扫描 + new List（GC），而塔/机器/野怪索敌与投射物命中检测**每帧/每发**高频调用它。静态推演 300~400 单位战斗期每帧 50 万级字典迭代 ≈ 5~8ms/帧，占 16.6ms 帧预算 30~50%。**不修，战斗期 60FPS 大概率不达标。**

另发现 **1 个功能级嫌疑**（审计中撞见）：塔/机器/野怪索敌仍是 `y∈{0,1}` 双行扫描——与 2_21 阶段A 已修的 PerceptionSystem 同族 1D 残留（D485），但**这三处没修**。

## 一、🔴 高危热点（战斗期帧率决定性）

### H1. GridSystem 单位查询 O(N) 无反向索引 + 每调用 new List

**位置**：`Systems/Grid/GridSystem.cs` L344-362

```csharp
public List<UnitController> GetUnitsInSubCell(GridCoord sub)
{
    var result = new List<UnitController>();   // ← 每次调用 new List（GC）
    foreach (var kv in _unitSubCells)          // ← 全量遍历所有单位（O(N)）
        if (kv.Value == sub) result.Add(kv.Key);
    return result;
}

public List<UnitController> GetUnitsInCell(GridCoord cell)
{
    var result = new List<UnitController>();
    var cellIs = cell == default;              // ← 死变量（半成品痕迹，声明未用）
    foreach (var kv in _unitSubCells)          // ← O(N) + 每 entry SubToCell（除法/取模）
    ...
}
```

`_unitSubCells` 是 `Dictionary<UnitController, GridCoord>` **正向映射**（写入侧 O(1)，查询侧 O(N)）。PerceptionSystem 头注（2_21 D485 修订背景）早已自认"GetUnitsInCell 每次调用 O(N)/格"。

**放大链（谁在高频调它）**：

| 消费方 | 调用模式 | 量级推演（N=400） |
| --- | --- | --- |
| `UnitController.FindNearestEnemy`（L1062-1090） | dx∈[-cellRange,cellRange] × y∈{0,1}，射程 8 格 = **34 次查询/帧/单位** | 34×400 = 1.36 万迭代/帧/单位 |
| `BuildingComponents.Update` 防御塔（L63-91，L76） | **每帧** FindNearestEnemyInRange | 同上 × 塔数 |
| `MonsterController.FindNearestHuman`（L103-121） | 野怪 Raiding/Guarding 每帧 | 同上 × 野怪数 |
| `ProjectileManager.QueryNearbyUnits`（L302-322） | 每发投射物到达：`(2×subRange+1)²` 次查询（hitRadiusCells=0.25、subDiv=4 → subRange=1 → **9 查询/发**）×O(N)+new List+AddRange 拷贝 | 9×400=3600 迭代/发 + GC |

**战斗期推演**（20 塔 + 40 野怪 + 几十发投射物齐飞）：每帧 **50 万级**字典枚举迭代；按单次迭代 ~15ns 估 **5~8ms/帧**（帧预算 16.6ms 的 30~50%）+ **千级 List 分配/帧**（GC 尖峰）。

⚠️ 量级为静态推演非实测（边界见 §八）。

**修复方向**（P0）：
1. 建**反向索引** `Dictionary<GridCoord, List<UnitController>>`，写入侧 `TryEnter`/跨格/死亡离开时维护（已有 `_gridRegistered`/`_lastGridSub` 同微格早退机制，维护点集中）；查询改 O(桶大小)。
2. 查询接口增加**复用 buffer 重载**（`FillUnitsInRect` 已有先例 L375），消灭每次 new List。
3. GridSystem 是 Core 面（寻路/染色/占格共享基础设施），改动须过 compatibility-audit + 行为级回归（寻路双探针/染色/投射物命中）。

### H2.（功能嫌疑+性能浪费）塔/机器/野怪索敌 y∈{0,1} 双行 = 1D 残留第三处未修

**位置**：
- `UnitController.FindNearestEnemy` L1069-1070：`for (int y = 0; y <= 1; y++)`（头注自称"y 地面+飞行两层"）
- `MonsterController.FindNearestHuman` L116-117：同款

**背景**：2_21 阶段A/D485 已裁定 `y∈{0,1}` = 1D 横版"双层"残留（"2.5D 全图单位仅最南两行可被发现，GameScene 实跑失明"），修了 PerceptionSystem。但**静态单位索敌/机器索敌/野怪索敌三处同款模式未修**——若 y 语义在 2.5D 已是宏格行坐标，则塔/弩炮/战争机器/野怪在 2.5D 下只能索敌最南两行，**战斗表现大概率失明或半失明**。

- 性能面：双行扫描同时是"扫描面积浪费"（扫不该扫的、漏该扫的）——与 H1 同串修复时一并重设计为全向邻近格。
- 行为面：**本审计为静态推演，未进局验证失明**；若坐实则 P1 考跑"塔无战果"类观察项可交叉解释。
- 建议：登记 DZ（D485 同族 1D 残留第三处+第四处），归修复批与 H1 同串处理。

### H3. 静态单位/机器/塔每帧索敌无节流

**位置**：
- `UnitController.Update` L724-739：isStatic/crewRequired 分支**每帧**跑 StaticAttackThink / CrewMachineThinkCore（机器每帧 **2 次** FindNearestEnemy：fireTarget + moveTarget）
- `BuildingComponents.Update` L63-91：每帧 FindNearestEnemyInRange + AimAt

**对照**：NPCBrain 感知有 0.2s 节流 + LOD 分频；静态侧零节流。塔/机器数量少时（<20）单靠 H1 修复即可消化；数量上升后（2_22 P0 批B 机器入池、城墙塔群）建议索敌节流 0.2~0.5s（与感知口径对齐）。

## 四、动画消费端现状与批5 接入前瞻（用户点名域）

**现状**：单位=静态色块，**零动画消费端**（唯一"动画"=DamageFeedback 受击闪红 tint，L46-61，每帧轻量）；死亡无动画直接走 Die 链回池；渲染层已备 spriteSortPoint=Pivot（y 排序）。当前动画开销=0。

**批5 接入前瞻审计**（143 Sheet ≈ 2288 帧，D568 右向单套口径）：

| # | 事项 | 审计意见 |
| --- | --- | --- |
| 1 | 逐帧赋值方式 | `spriteRenderer.sprite = frames[i]` 引用赋值，轻量；12FPS × 400 单位 = 4800 次赋值/秒，可接受 |
| 2 | 播放器形态 | **建议代码帧动画**（集中式 Manager 或每单位轻组件，像 ProjectileManager 集中推进）；**禁 Animator 状态机**（400 个 Animator = 内存+开销重灾） |
| 3 | 合批面 | 同 sheet 16 帧同纹理天然合批；**跨状态切换（idle→walk）换 sheet 纹理=断批**——建议 SpriteAtlas 按角色合并各状态（或同族同 PPU 合图） |
| 4 | 帧数据结构 | 每角色 SO（Sprite[] + fps + 事件帧），启动期预载；禁运行时 Resources.Load/字符串拼路径（so-data-driven 铁律） |
| 5 | flipX | 用 `renderer.flipX`，**禁负 scale**（破坏合批+碰撞） |
| 6 | run 并 walk 代码加速 | 实现位=播放器帧推进 dt × speedMul（纯播放倍率，零额外帧图） |
| 7 | 死亡模板 4 帧全族复用 | 播完回池；**对象池 Return 时必须重置 sprite/flipX 状态**（池化单位残留上一次动画帧=视觉 bug 温床，池化纪律补条目） |
| 8 | 坐骑系人兽双体 | 2 SpriteRenderer/单位（DC×2）+ 双体同步播放器；绘制最贵（D568 已知），接入时单独验证 |

**结论**：动画接入本身开销可控（12FPS 帧切换是轻操作），风险集中在 **SpriteAtlas 打包策略**与**池化状态重置**两点，接入前定标尺即可，不构成 60FPS 威胁。

## 五、存读档链路与 Load 卡死嫌疑

**架构现状**（健康）：SaveManager.Load 三阶段恢复（Global → Scene spawner 重建实例 → Scene LoadState）+ 版本门控 + isFinished 死档拒绝 + try/catch 兜底（L308-428）；LoadManager 暖 boot（PlaceholderSprites.PreloadAll + UnitPrefabs 预热，L61-63）；单位重建走对象池。

**45 日大世界读档卡死 6min+（P1 三考风险清单挂账，根因=独立诊断批至今未立）静态嫌疑点清单**：

1. **Console.Log 海量输出**（嫌疑最大）：Editor 下 Log 是慢 IO；读档期逐单位注册/逐模块 LoadState 日志若未分频，分钟级延迟可由纯日志贡献（P1 观测日志量级已知偏大）
2. SpawnFromSave 逐单位重建链的隐藏开销（注册链/视野 MarkExplored/A* 初始化）
3. WorldManager.LoadState 重建世界面（若读档触发全图级铺设而非 chunk 增量）
4. 各系统 LoadState 内隐藏 O(N²)（逐单位查询类）
5. JsonUtility 大 JSON 解析（秒级，非主因）

⚠️ 静态审计不下定论——建议独立诊断批走 Profiler Deep Profile 实测（该项本就在挂账池）。

## 八、审计边界与方法论注记

- **纯静态审计**：所有量级为代码推演非 Profiler 实测；"ms/帧"为迭代次数×单次操作经验值的量级估计，用于排序优先级，不可当验收数字。
- **行为级嫌疑需进局验证**：H2（塔/野怪 2.5D 失明）是静态推演，需行为级探针坐实后才能定缺陷（对齐"路由类改动验收必须行为级探针"纪律）。
- **一手证据**：全部结论带文件+行号，直接读码取证；未派子代理（用户既定纪律）。
- **顺带发现**：`GridSystem.GetUnitsInCell` L355 死变量 `cellIs`（半成品痕迹）；`VagrantCampSystem.ScanArrive` L318 仅判 x 轴距离（抵达判定单轴，功能疑点非性能，列报不裁）。
- 本报告未取 D 号（分析报告非裁决件）；优化批立项时按 vr-id-ledger 取号，报告引用时补链。
