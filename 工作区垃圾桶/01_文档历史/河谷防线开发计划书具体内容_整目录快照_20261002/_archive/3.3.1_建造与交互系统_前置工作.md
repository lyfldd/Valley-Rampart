## 二、硬前置（必须实现，否则 3.3 无法编译/运行）

### P1 · GridSystem 建筑占用子层扩展

- **现状**：`GridSystem` 已实现 NPC 单位堆叠（`TryEnter` / `ExitCurrentCell` / `GetUnitsInCell` / `GetUnitCoord`），`GridCell` 仅持有 `List<UnitController>`。**完全没有建筑占位、地形查询、`isObstacle` 概念。**
- **为什么前置**：`PlacementValidator` 的 5 项校验（区块占用 / 地形合法 / 阻挡冲突 / 资源 / 边界）全部依赖"某 cell 是否被建筑占用 + 是否 obstacle + 是什么地形"。没有它，建造放不下，地图资源点也占不了。
- **要做**：
  - 在 `GridSystem` 增加**与单位堆叠层解耦**的建筑占用层：
    - `bool IsOccupied(GridCoord coord)`
    - `void MarkOccupied(GridCoord coord, Building building)`
    - `void Free(GridCoord coord)`
  - `GridCell` 增加 `Building occupant` 字段与 `bool isObstacle`。
  - `TerrainType GetTerrainAt(GridCoord coord)`：由 coord → `CellToRegionIndex` → `MapData.regions[idx].terrain`。
  - footprint 多 cell 占用：`MarkOccupied` 遍历 `BuildingDef.footprint` 覆盖的所有 coord 全标记。
- **验收**：同一 cell 放第二栋建筑被拒；障碍建筑标记 `isObstacle` 后该 cell 不可再放；`GetTerrainAt` 与地图生成 terrain 一致。
- **注意**：现有 `GridCoord.y` 是"地面(0)/空中(1)"子层，建筑默认 `y=0`，**不要把建筑塞进空中层**。
- **涉及**：`Assets/_Game/Systems/Grid/GridSystem.cs`、`GridTypes.cs`

### P2 · 运行时 Building 类 与 BuildingCategory 枚举冲突裁定（架构分歧，必须拍板）

- **现状（关键）**：`GridTypes.cs` 已存在一套 Building 体系：
  - `enum BuildingCategory { ResourceProducer, ResourcePickup, SpecialPoint, Rift, CastleCore }`（地图来源/大类）
  - `enum BuildingType { Tree, Mine, Farmland, StonePile, WoodPile, OreVein, TreasureBox, Ruins, Interactable, Rift, CastleCore }`
  - `class BuildingPlaceholder`（地图生成产出的"占位"，注释明写：**"运行时由 BuildingFactory（建造系统⬜）转为 Building 实例"**）
- **冲突**：3.3 的 `BuildingDef.cs` 提案里**又定义了一套同名不同义的 `enum BuildingCategory { Defense, Production, Economy, Special, Wall }`** 和 `ProducerConfig / CombatConfig`。两套分类维度不同（一套是"来源分类"，一套是"玩法功能分类"），且同名极易混淆。
- **为什么前置**：数据层若两套枚举并行，`Building` 运行时类、存档、交互选项（`InteractableType`）、升级面板都会精神分裂。必须先把"运行时 Building 用什么分类"裁定清楚，3.3 才能写 `BuildingDef` / `BuildingRegistry`。
- **建议裁定（供阿铁选）**：
  - **方案 A（推荐）**：保留 `GridTypes` 的 `BuildingCategory` 作"来源/大类"，**新增 `BuildingRole` 枚举**（`Defense / Production / Economy / Wall / Special`）作"玩法功能标签"，`BuildingDef` 挂 `role`；`BuildingType` 继续作具体类型。→ 不新增同名冲突，地图侧零改动。
  - **方案 B**：用 3.3 的 `BuildingCategory` 彻底取代 `GridTypes` 的，改地图生成侧代码。→ 改动面大，不推荐。
- **还要定**：运行时 `Building` 类放 `Assets/_Game/Systems/Building/Building.cs`，它如何同时持有 `BuildingDef`（玩家建筑配置）+ `BuildingPlaceholder`（地图建筑来源）+ 运行时状态（level/hp/存储）。
- **验收**：地图生成的 `BuildingPlaceholder` 能无歧义 map 到运行时 `Building`；玩家建筑有清晰 `role`。
- **涉及**：`GridTypes.cs`、3.3 `BuildingDef.cs`（待写）

### P3 · 通用交互层骨架（IInteractable + InteractionManager）—— 你点名要的

- **现状**：全仓无任何交互派发框架。3.3 第十一节批次 1 把它列为"先做"，但它是被建筑/资源点/裂隙/主城/NPC **共同依赖**的底座，应明确为前置独立交付。
- **为什么前置**：建造 UI 只是 `InteractionResult.ShowUI` 的一种。若先写建筑再回头抽交互，建筑代码会耦合点击逻辑；且资源点/裂隙未来也要用同一套。先做框架并单测（用一个临时可交互物验证"点击 → 结果派发 → 开 UI/执行动作"闭环），再让 3.3 消费。
- **要做**：
  - `IInteractable` 接口 + `Interactor` + `InteractionResult`（见 3.3 第六节，直接搬）
  - `InteractionManager`（Singleton）：订阅点击/选择 → 射线/点选命中 Collider → 若实现 `IInteractable` 则 `Interact(ctx)` → 按 `InteractionResult` 派发
  - **悬停高亮**：选中/悬停轮廓高亮
  - **点空白取消**：关闭面板 / 取消选择
- **验收**：放一个临时 `IInteractable` 测试物，点击能正确弹 UI/执行动作，点空白能关闭，不改 `InteractionManager` 即可再挂新实现者。

### P4 · UI 面板框架（IUIPanel + 最小 UIManager）—— 你点名要的

- **现状**：仅零散 HUD MonoBehaviour（`ResourceHUD` / `TopLeftHUD` / `GameOverPanel` / `LoadingPanel`），**没有通用面板生命周期（Open/Close/Refresh）和 `IUIPanel` 接口**。3.3 的 `BuildingPanel` 依赖 `IUIPanel`。
- **为什么前置**：`BuildingPanel`、未来 NPC 对话、侦察面板都要挂到统一面板宿主上；没有它每个面板各写一套开关逻辑，会重复且易错。
- **要做**：
  - 定义 `interface IUIPanel { void Open(Interactor ctx); void Close(); void Refresh(); }`
  - 最小 `UIManager`：面板注册/单例打开关闭、同屏互斥（同时只开一个交互面板）、事件驱动的 `Refresh` 订阅点
  - 一个最简 Canvas 面板宿主（UXML 或 UGUI），`BuildingPanel` 直接实现 `IUIPanel` 挂上去
- **验收**：`BuildingPanel` 实现 `IUIPanel` 后，经 `UIManager.Open(panel)` 能开、点空白能关、升级后 `Refresh` 刷新数值。
- **涉及**：`Assets/_Game/Systems/UI/UIManager.cs`、`IUIPanel.cs`
- **备注**：3.3 待确认 #5（UI 框架沿用 1.7）在此落实——若 1.7 已有面板基类，则本项退化为"确认接口契约"，否则新建。

### P5 · `BuildingFactory`（地图预置建筑实例化）—— 解除 3.2.2 断裂

- **现状**：3.2.2 全链路核查确认 `BuildingFactory` **不存在**。`WorldManager.GenerateWorld` 只做了 GenerateMap → PopulateFromMap → 发事件，Building 实例化这步完全缺失。地图上的树/矿洞/农田/裂隙/主城都是 `BuildingPlaceholder` 占位数据，运行时没有任何实际游戏对象。
- **为什么前置**：3.3 的交互层（P3）、存档（ISaveable）、UI 面板（P4）全部以 `Building` 运行时实例为操作对象。没有 BuildingFactory，地图上没有建筑实例，交互/存档/UI 全部空转。**这是 3.2.2 地图生成与 3.3 建造系统之间的断裂点**，必须在 3.3 批次 0 修复。
- **要做**：
  - 新建 `BuildingFactory` 类（`Assets/_Game/Systems/Building/BuildingFactory.cs`）
  - `InstantiateFromMap(MapData map)`：遍历 `map.regions`，对每个 region 的 `resources`（List<BuildingPlaceholder>）：
    1. 查 P6 映射表，把 `BuildingPlaceholder.type + grade + isConsumable` → `BuildingDef` SO
    2. 实例化 `Building` 运行时对象，`Init(BuildingDef, placeholder, GridCoord)`
    3. `isPlayerBuilt = false`（地图预置标记）
    4. `BuildingRegistry.Register(building)`
    5. `GridSystem.MarkOccupied`（标记占位，footprint 按 `placeholder.cellWidth`）
    6. `EventBus.Publish(new BuildingPlacedEvent(building))`
  - 在 `WorldManager.GenerateWorld` 末尾（PopulateFromMap 之后）调用 `BuildingFactory.InstantiateFromMap(playerMap)`
- **验收**：新建游戏后，场景里出现树/矿洞/农田/裂隙/主城的 Building 实例；`BuildingRegistry` 能查到；点选能命中（接 P3 交互层后）。
- **依赖**：P2（Building 类定义）、P6（映射表）、P1（GridSystem 占用接口）
- **涉及**：`Assets/_Game/Systems/Building/BuildingFactory.cs`、`WorldManager.cs`（末尾补调用）

### P6 · `BuildingType` → `BuildingDef` 映射表设计（数据桥接）

- **现状**：未设计。地图生成的 `BuildingPlaceholder` 字段是 `{ BuildingType type, BuildingCategory category, ResourceGrade grade, bool isConsumable, int cellWidth, int localCellX }`；3.3 的 `BuildingDef` SO 字段是 `{ id, faction, role, footprint, allowedTerrain, producer, combat, levels }`。**两边数据模型不对齐**：
  - `ResourceGrade`（Barren/Normal/Rich）如何影响 `BuildingDef` 的 `producer.rate` / `combat.maxHp`？
  - `isConsumable=true`（一次性资源如 WoodPile）和 `isConsumable=false`（持续性资源如 Tree）是同一个 BuildingDef 还是两个？
  - 11 种 `BuildingType` 对应几个 `BuildingDef.asset`？
- **为什么前置**：P5 的 `BuildingFactory` 需要查这张表才能实例化。表没设计好，Factory 写出来无从下手。
- **建议方案（供阿铁确认）**：
  - **方案 A（推荐）**：`BuildingDef` 加 `BuildingType sourceType` 字段（标记能由哪种地图占位转换来）+ `float gradeScale` 三档缩放系数（Barren=0.7, Normal=1.0, Rich=1.5），作用于 `producer.rate` 和 `combat.maxHp`。映射表用 `BuildingMappingTable` SO 集中配置：
    ```
    Tree    + any grade → BuildingDef "tree"      (rate × gradeScale)
    Mine    + any grade → BuildingDef "mine"      (rate × gradeScale)
    WoodPile (一次性)   → BuildingDef "wood_pile"  (无 producer，pickup 模式)
    ...
    Rift                  → BuildingDef "rift"    (无 producer，combat/rift 逻辑)
    CastleCore            → BuildingDef "castle"  (无 producer，HQ 面板)
    ```
  - **方案 B**：为每种 `BuildingType × Grade` 组合单独建一个 `BuildingDef.asset`（11×3=33 个 asset）。改动小但 asset 膨胀，调参痛苦。
- **要做**：
  - 定义 `BuildingMappingTable` SO（`Assets/_Game/Data/BuildingMappingTable.cs`）：`BuildingType → BuildingDef` 查找表 + `gradeScale` 三档
  - `BuildingDef` 加 `BuildingType sourceType` + `bool isConsumable` 字段（标记是否一次性）
  - 编写 11 种 BuildingType 的映射规则文档（可直接写在 SO 的 Inspector 注释里）
- **验收**：给定任意 `BuildingPlaceholder`，能通过映射表查到唯一 `BuildingDef`；Rich 等级的树产出 > Normal 等级。
- **涉及**：`Assets/_Game/Data/BuildingMappingTable.cs`、`BuildingDef.cs`（加字段）

### P7 · `RulerController` 补 `ResourcePack` 重载（硬前置，升级自原 C1）

- **现状**：3.2.2 核查确认 `RulerController` 方法签名是 `ModifyResource(ResourceType type, bool isIncrease, int amount)`——**单个资源类型逐个操作，没有 `ResourcePack` 结构体**。3.3 的 `BuildingDef.cost` 是 `ResourcePack`（金/石/木/粮四元组），现有 API 无法一次性扣一个 Pack。
- **为什么前置**：`BuildController.Place()` 和 `BuildingPanel.Upgrade()` 都需要 `CanAfford(cost) → Spend(cost)` 两步原子操作。没有 `ResourcePack` 重载，要么循环 4 次调 `ModifyResource`（无法原子校验：扣到第 3 个发现不够，前 2 个已扣），要么每个调用方各写一套四资源循环。
- **要做**：
  - 定义 `ResourcePack` struct（`int gold, stone, wood, food`）+ `bool IsZero` + `static ResourcePack Zero`
  - `RulerController` 加：`bool CanAfford(ResourcePack cost)` / `void Spend(ResourcePack cost)` / `void Refund(ResourcePack cost, float ratio = 1.0f)`
  - `Spend` 内部循环 4 次调 `ModifyResource`，但 `CanAfford` 先做四资源校验（原子性保证）
  - 保留现有 `ModifyResource` 不破坏旧调用方
- **验收**：`CanAfford` 返回 false 时不扣任何资源；`Refund` 按比例退还（拆除 50% 时 `ratio=0.5`）。
- **涉及**：`RulerController.cs`、新增 `ResourcePack.cs`（或并入 `WorldConfig.cs`）
